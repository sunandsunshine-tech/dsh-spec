# Agent Note: 批量编辑把 frontmatter 当作一个块，而不是一个段落

Status: implemented

[English](2026-09-18-frontmatter-is-a-block-not-a-paragraph.md) | 中文

## 问题

一次全语料的段落重排把包内各部分的 YAML frontmatter 从三行块改写成一行，产出 `--- name: … description: … ---`，这不是合法的 YAML。损失留在了作者树和已安装副本里，因为没有任何东西读 frontmatter：路由表是手写的，因此一个塌缩的块没有造成任何可见后果，每道门禁也一直是绿的。

工具按空白行切分正文，而它分不出围栏和句子：一个 `---` 行、若干 `key: value` 行、一个收尾 `---`，对段落重排器来说就是一个段落。这个错误有两个复合因素——规则修正落在工具上而不是工具先前的输出上，被修好的脚本又被信任为已经让语料处于它所描述的状态。

## 决策

**frontmatter 是一个围栏块**：单独成行的 `---`、若干 `key: value` 行，以及单独成行的收尾 `---`。围栏行不携带别的内容，块是一个映射。

**批量编辑把围栏区域当作不透明单元处理**，在处理之前先掩蔽掉，而不是在之后再修复它们：YAML 块、围栏代码块和生成区域是正文之外的单元，一个按空白行切分的编辑没有关于它们的模型。

**修正一次批量编辑的规则并不修复先前那条规则写出的输出。** 一次此类处理被修好之后，重新通读语料，并测量出错的版本到底写了什么。

## 考虑过的替代方案

**靠解析 YAML 的人来发现问题。** 不加门禁，而真正的 YAML 解析器一旦出现就是权威。它输掉是因为这里没有东西解析 frontmatter，而损失正是这样留下来的。

**只在工具的规则里修掉，靠修复后的重跑。** 最便宜的修正，而且工具已经不再产出那个形态。它输掉是因为这次重跑是手动的：同一批文件在下一次全语料编辑中仍带着这个缺陷，而修好的规则如果只作用于新输出，就检测不到既有输出。

**让每个批量处理显式跳过文件开头。** 对 frontmatter 来说足够，对围栏代码块和生成区域不够。它输掉是因为它把这条规则绑在一个位置上，而不是绑在一种单元上：造成损失的编辑按段落切分，因此它需要的是「围栏区域」这个概念，不是「文件开头」这个概念。

## 后果

一次全语料编辑的成本是多花一点功夫处理两类区域；回报是一处损失不再可能无声地留下，因为一个其含义就在于行结构的块，不会被按段落切分的编辑重写。

残余风险属于评审：这里没有任何门禁读取 YAML 语义，所以一个结构良好但含义错误的 frontmatter 块仍然会让每道门禁保持绿色。
