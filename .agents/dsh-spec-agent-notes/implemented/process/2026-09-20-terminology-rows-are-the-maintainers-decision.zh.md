# Agent Note: 术语表的行由维护者决定

Status: implemented

[English](2026-09-20-terminology-rows-are-the-maintainers-decision.md) | 中文

## 问题

`docs/terminology.md` 是每一对双语文档共同遵守的词汇表，也是翻译简报用来匹配改动片段的表，因此它的每一行都是一个决定：它固定了配对两侧共同书写的用词。无论这张表本身，还是随它一起发布的配对约定，都没有说明这些决定由谁做出。一张没有标明归属者的决定表会长出没人决定过的行——在当时的编辑者看来，这次编辑似乎有用——此后每一次翻译都在遵循没有任何维护者要求过的用词选择。表中就有这样一行：`architecture map`，定义为根 `README.md`。并不存在这样的产物。根 `README.md` 就是一份 README，而一张给某个产物起了它所有者从不使用的名字的表，会教读者去书写并不存在的东西；为一个已删除之物保留术语，术语表就是这样腐烂的。

## 决策

增删或修改 `docs/terminology.md` 的任何一行都是维护者的决定，须由维护者在对话中提出，绝不由正在编辑的人自行推断。负责处理的 agent 提出一行，但不自行添加。

这条规则写在 `docs/AGENTS.md`，即拥有这张表的目录的常设指令，因此它出现在即将编辑这张表的人面前，既不在表内重复，也不写进描述机制、而非某个项目流程的配对约定。

`architecture map` 一行已删除：没有任何文档链接到它，这棵树里也没有别的东西依赖该名称，因此删除不破坏任何引用。`corpus` 与 `aggregate` 两行保留：二者命名的东西，门禁和本仓库都确实拥有。

### 为什么没有门禁

门禁无法分辨被要求的一行与自行推断的一行。它读的是这张表，而不是产生这张表的对话，因此唯一可用的机械检查只能是一份已批准行的清单——那是这张表的第二份清册，会与它脱节，然后又为脱节作证。本技能集合（skill set）把关于含义的判断留给能做出该判断的读者，而靠猜的门禁恰好在它看不见的那些条目上报告绿色。

## 曾考虑的替代方案

**保留该行并重新指向。** 根 `README.md` 或许仍然值得有一个术语，把该行重新指向这个文件的真实身份，可以为它保留一个词汇位置。它落选，是因为这棵树里没有任何地方书写该术语：修正后的一行仍然是没有文档遵守的决定，而这张表自己的前言说，不影响译者措辞的行不属于本表。

**删掉这一行，什么也不说。** 这是最小的改动，仅删除就已修好这张表。它落选，是因为它移除了症状却留下了病因：这一行进入的是一张没有标明归属者的决定表，没有这条规则，下一位编辑就会推断出下一行。

**只在配对约定里陈述这条规则。** 约定是翻译工作者在动一份配对之前会读的东西，而且已经拥有这张表的权威；前言则可以少一条。它落选，是因为两份文件有不同的读者——约定由翻译配对的人读，表由编辑表的人打开——这条规则应当同时出现在两者面前。

## 后果

- `docs/terminology.md` 少了一行，由 `docs/AGENTS.md` 说明余下的行由谁决定。
- 这条规则的归属是项目自己的：它随表同处一个目录，而不再写在随包发布的配对约定里，约定也不再陈述它。
- 验证：`dsh-spec.ts check --all --root .` 以 `check notes: ok` 与 `check notes-archived: ok` 结束，`md-links check` 与 `translation-pair check` 在本次改动留下的文件上以零退出。

这一决定的代价是一条没有门禁执行的规则：未经维护者首肯而添加的一行能通过所有检查，因为这项检查就是对话本身。它换来的是：这张表的每一行都是维护者做出的决定，而它的下一位编辑在添加之前会被告知这一点。
