# Agent Note: 交付的技能文本是一次抽取

Status: implemented

[English](2026-09-21-the-shipped-skill-text-is-an-extraction.md) | 中文

## 问题

`skills/` 是从 `submodules/dsh/` 里的技能抽取而来，而这次抽取就是本套件可评审的依据：任何人都能把一个技能与它来源的那个版本对 diff，看到本技能集合改了什么。漂移会毁掉这一点，而已经积累了三类。有些规则的主体属于整个技能集合、而不属于承载它们的那份技能，却被写进了技能正文——`dsh-prose-standard` 里的门禁清单、`dsh-pre-push-checks` 里的 manifest 记录段落与选择表、`dsh-archive-agent-notes` 里的目录树校验小节、`dsh-translate-docs` 里的审批门、以及配对约定里的术语表归属条目。有些句子被无缘无故改写，于是同一句话与它的来源说法不同。还有些缺陷一直留着，因为没有门禁会读它们：中段被改写吃掉的句子、行内代码被反复包裹到不再能解析的切换行示例、指向本技能集合并不交付的文件的字面引用，以及本仓库自己的 `--store-dir` 变通办法出现在一条对外发布的命令里。

一份没有记录原因就漂移的派生文本不再可评审。与来源的 diff 不再回答「本技能集合有意改了什么」——而这正是抽取存在的意义，它让这个问题变得廉价；而分不清有意通用化与意外的读者，只能逐行重读。

同一类缺陷还存在于下一层。`init` 安装的模板带有两个来自源项目引擎目录的路径、一个因为无人替换而留存在每个初始化项目里的引擎占位符，以及一行指向 `init` 有意不创建的中文对侧的切换行——于是新项目的合同在自己的第一次运行中就挂了链接门禁。

## 决策

一份交付的技能文件——以及技能集合安装的每一份模板——与它来源文本的偏离只有两个原因；两者都不占的改动，要么是应修的缺陷，要么是应记在别处的决定。

1. **交付布局要求带来的引用变化。** 检查改为按名称经分发器寻址，而不是包脚本；约定移入技能的 `references/`；路径指向笔记树或引擎目录。
2. **去掉某个项目专属内容的通用化。** 它的产品名、包布局、linter、文档树和私有门禁，都换成任何采用本技能集合的项目都成立的说法。

其余内容都在本次改动中删除或修复。属于整个技能集合的规则迁到了它归属者所在之处——管理器、某份参考文档、或项目自己的指令——而不是留在一项会交付给每个项目的能力里。术语表规则迁入 `docs/AGENTS.md`，与它所约束的那张表同处一处。`dsh-translate-docs` 取回了使它只能由用户调用的一对 frontmatter 键，那正是它新增散文用文字描述过的机制。两个无缘无故改名的引用文件回到了来源名称，于是目录 diff 能同类相比。

缺陷是修复而不是回退。被改写毁掉的散文复原了，每条引用现在都指向本技能集合确实交付的东西、或项目自己拥有的路径，而对外发布的命令里不再夹带本仓库环境的变通办法。

## 抽象方法

泛化有两种形态，取哪一种由「去掉具体之后还剩什么」决定。

规则自己能站住的地方，就在原地泛化。去掉某个产品的名字、包布局、linter 或私有检查之后，剩下的是任何项目都能照做的指导，因为那些名字只是规则的例证，规则从来不是关于它们的；别的什么都不需要，也不必保留任何例子。

材料是某个项目的判断的地方，抽象在上、案例重述在下。抽象必须触及判断本身的性质：权衡了哪些因素——实现成本、维护重量、增量可采纳性与迁移成本、可逆性、持久性、安全性——以及什么会推翻这个决定。给主体起一个名词不是对它的抽象：「删掉死代码」是重述案例，而「一个没有生产者也没有消费者的声明，是每个实现都必须考虑的合同表面，它会在有东西发出它的那天回来」才是读者能拿去套在没人写过的案例上的判断。重述的案例跟在下面作为支撑例证，每一条都保留足够的背景、语境与选择，好让它能被拿去和上面的抽象对照，并且每一条都读得出是这个项目自己的材料，而不是规则的一部分。

来源与许可这类表面完全不抽象。一个文件来自哪里、来自哪个版本、这个项目改了什么，是关于一份副本的事实而不是判断；把它们泛化掉，就毁掉了它们唯一的作用。

## 曾考虑的替代方案

**保留新增内容并把它们记录下来。** 新增的规则本身是对的，每一条都是因为某位读者需要才写下的。它落选，是因为技能正文就是 agent 加载的东西，而某个项目的操作规则不属于一项交付给每个项目的能力：同样的材料本来就在技能集合自己的文档里，那才是读者接触本套件的地方。

**把这些技能当作本技能集合自己的文档，自由重写。** 每个技能按自身的标准都会更清楚。它落选，是因为它会毁掉「这次抽取改了什么」的廉价答案：`submodules/dsh/` 里 pin 的基线，正是让重新抽取及其评审只需几分钟、而不是通读一遍的原因。

**删掉每一处对未交付机制的引用，不做替代。** 对悬空路径来说，删掉那个从句是最短的修法。它在从句承载规则的地方落选——证据选择器、引用判据——那些规则改为通用地重述，只有完全无所指的指针才被丢弃。

## 后果

- 任何技能目录与 `submodules/dsh/` 的 diff 只显示引用变化与通用化，别的都没有，因此评审者能把余下的每一行归入两种允许原因之一。
- 删掉的材料并没有丢失：项目 README 介绍了整套技能，管理器保留了记录与引擎，术语表规则则住在 `docs/AGENTS.md`。
- 交付的技能不再点名本仓库自己的门禁、它的沙箱变通办法或它的 vendored 基线；采用者读到的路径都是它确实拥有的，而模板在写入时就解析出引擎路径，不再把占位符留给某个人去填。
- 代价是另一种意义上的来源保真：凡是一句话必须逐从句通用化的地方，技能的散文都比自由重写离来源措辞更远。
- 材料是判断而不是转述的地方，抽象与它的案例一起交付：`skills/dsh-find-simplifications/references/historical-patterns.md` 为每条模式写明它权衡过哪些因素、什么条件会推翻结论，并把记录下来的案例留在下面，作为项目可以换成自己案例的材料。

## 验证

`dsh-spec.ts check --all --root .` 以 `check notes: ok` 与 `check notes-archived: ok` 结束，`scripts/verify-skill-structure.ts` 对本次改动触及的每个技能目录都通过，而逐文件与 `submodules/dsh/` 的 diff 就是本次改动自身的证据：余下的每一处差异都是引用变化或通用化。
