# Agent Note：整套技能不在每个技能旁放 README

Status: implemented

[English](2026-09-21-the-skill-set-is-introduced-once.md) | 中文

## 问题

每个技能在入口旁边带一套 README——它是做什么的、什么时候加载、不做什么——于是有二十四个文件和八对记录，主题却与仓库自己的 README 相同：介绍这一整套。而读者来到仓库时反而看不到总览：README 只指向其中一个技能的 README，另外七个得逐个目录打开才发现。两处文档在讲同一件事，配对门禁又让“保持两边一致”变成一项长期成本。

## 决策

各技能旁的 README 继续缺席。根 README 承担采用总览：列出通用起始组、映射五个按需分组、概括来源，并链接到唯一的详细选择指南。[选择 dsh-spec 技能](../../../../docs/choosing-skills.zh.md)维护各组职责、推荐配套技能及其作用、常用组合和能力要求。入口（`SKILL.md`）仍然是 agent 加载的东西，它旁边的参考材料仍然属于该工作流本身；一个技能目录装入口、参考材料，以及它的交付物所需的脚本或 notices，不装 README。

## 曾考虑的替代方案

**保留它们，接受重复。** 它们曾是供人阅读的入口：打开一个技能目录就能判断，不必读整个仓库。它落选，是因为总览的归属地是这一整套，而不是单个技能——要比较技能的人需要把它们并排看，而这份比较一旦有八份副本就会各自漂移。

**只保留 manager 的 README。** 那是源项目的形状，而且 manager 是技能集合的入口。它落选，是因为 manager 介绍的是这个*包*，不是八个工作流：读者问“哪一个是管评审证据的？”，从这里得不到答案；而它自己的内容，大半是把根 README 的材料又写了一遍。

**把各技能的介绍搬进各自的 `SKILL.md`。** 一个技能一个文件，不新增文档。它落选，是因为 `SKILL.md` 是写给“判断要不要加载这个技能”的 agent 的，而“判断这套东西值不值得采用”的人读的是另一种文档；入口本来也已有职责——路由与触发。

## 后果

- 一份总览和一个负责选择细节的归属地：根 README 的配对概括采用方式，指南的配对维护选择细节。
- 少记录八对配对，技能目录里只剩下交付物需要的东西：入口、参考材料，以及所需的脚本或 notices。
- 安装副本会失去这些 README：它镜像的是已落地的技能，因此修订不再交付的文件不会在经过一次刷新后保留下来。
- 代价是多一组需要维护的配对：详细指南在 README 的分组行之外承担选择深度，技能的入口和参考材料仍然用于查看具体实现。
- 验证：`pnpm test` 与 `node scripts/verify-corpus.ts --base-ref=HEAD` 通过；spec 门禁对每个没有 README 的技能目录均通过；入口旁不再留有技能 README。
