# Agent Note: Forging dsh-spec-code-review from the upstream code-review skill

Status: implemented

English | [中文](2026-10-28-forging-dsh-spec-code-review.zh.md)

## Problem

The package's skill set includes the forge, the agent-experience, agent-notes, prose-standard, find-simplifications, pre-push-checks and error-handling skills. It has no code-review skill, so an adopting project gets no agent-facing procedure for reviewing a pull request against that project's own declared standards. Upstream `dsh-code-review` is that procedure for one repository: a reviewer-oriented skill that makes the reviewer establish the review's base and scope, read the owning requirements before judging a diff, check a set of blocking requirements, walk the review-specific checks that code alone cannot show, and report findings in a fixed shape. Its sections name one repository's paths and mechanisms — `pnpm change-scope`, `packages/AGENTS.md`, the defensive-patterns pages, Cordis, the client-UI localization gate, the Agent Notes tree, the bilingual rules. Carrying the text verbatim would import another project's policy and make the skill useless outside that project; leaving it out would drop a review mechanism the package exists to extract. The forging must keep the mechanism and re-bind every repository-specific referent to the adopting project's own declaration. The target audience and domain are software engineering.

## Decision

The package ships `dsh-spec-code-review` as an adaptation of the upstream `dsh-code-review` skill for software engineering. The skill directory holds `SKILL.md` and a skill-root `THIRD_PARTY_NOTICES`; the skill is mirrored into `.agents/skills/`, and the upstream-named installed copy is gone. `AGENTS.md` and the root `THIRD_PARTY_NOTICES.md` name the skill.

`SKILL.md` keeps the upstream section names and order — Sources of truth, Blocking requirements, Manual checks, Reporting findings — and the mechanism each section carries: establish the review basis and the changed scope; read the owning requirements before judging the diff; apply the blocking requirements; walk the review-specific checks; report findings in the fixed shape. The adaptations are the disposition table's: the adopting project's declaration replaces one repository's document list; the scope requirement is stated in natural language, names the `dsh-spec-pre-push-checks` example and falls back to version control; the title names the proposed change; M0 preserves required rendered evidence while rejecting gaps for optional reporting and repeated checks; M9 applies the adopting project's ownership, state-size, historical-read and migration rules; M4a checks workspace responsibilities and runtime dependency edges; the core review duties stay unconditional while mechanism-specific requirements carry their own condition; the siblings the package ships appear as parenthetical examples; the section headings stay upstream. The description is generalized with the Chinese trigger language appended, and the frontmatter `license` field names the skill-root notices. The delivered skill ships no script, reference or local test; the development eval corpus remains in `tests/skill-evals/`. The alpha.2 delta from the previous rc.5 extraction baseline adds the numbered-rule ID citation, the module-responsibility/dependency-edge review, the UI evidence boundary and the projection source category; the earlier required-behavior, producer-extension-point and configuration-precedence checks remain carried; the projection categories are re-bound to adopting-project design rules rather than to the source repository's unshipped sibling.

- Delivery and language: English delivery with Chinese trigger keywords; the Chinese review draft (`SKILL.zh.md` with its `SKILL.i18n.yaml` record) is produced at the stop and `publish` removes it, while the record's own Chinese pair is written at landing (R5, R6, R9).
- No script or package source ships; the development corpus stays outside the delivered skill. The reviewed project's scope tooling or version control supplies the changed scope (R2, R4).

## Review integrations

The shipped skill requires the project's existing stable machine-readable failure identity to survive a machine-consumable boundary, preserves the original cause or equivalent structured detail, and rejects routing on message text. It applies the project's UI evidence rules to the cumulative visible change: missing required inspection is a gap, omitted optional reporting is not, an ordinary change needs no full-audit record, and only new interactions or invalidated evidence need rechecking; a named project waiver or equivalent evidence form is authoritative. Source inspection and passing tests do not establish visual acceptance. For retained or projected state, the skill applies the project's ownership, size or retention, historical-read and migration rules, and records a gap when the project declares none. The error-handling, UI and state requirements remain complete without another skill, and their concrete mechanisms appear only in availability-qualified examples. PR119 retains historical model evidence that is not answer-blind; PR122 records dependency-edge and numbered-rule scenarios; PR141 reruns the UI scenarios and adds the ordinary-UI and projection controls under `tests/skill-evals/evidence/2026-11-25-pr141/`. Scenario inputs, modes, capability profiles, traces, skill hashes and artifacts are bound by the repository test.

## Target shape

The skill is one file with the upstream section skeleton:

- Frontmatter: `name: dsh-spec-code-review`; the description triggers on reviewing a proposed change against the project's declared standards and names the review-specific checks code alone cannot show; Chinese trigger language appended; the `license` field names the skill-root notices.
- `# Reviewing a proposed change`: the guidance framing, the verified base/head, the changed scope, the priority order, and the "read the requirements before judging the diff" paragraph.
- `## Sources of truth`: the declaration and the categories it fills — standing instructions at the root and in each changed subtree; the design or architecture rules it cites, one owning page per artifact; the documentation and prose standard; the standards it names for the changed area, for example prose, test reliability, error handling, UI/UX, or state persistence, projection and recovery; the testing policy and quality gates; the decision records; the language and terminology policy for paired changes. The core review duties are unconditional; the mechanism-specific requirements carry their own condition.
- `## Blocking requirements`: six numbered requirements, each keeping its upstream property; the mechanism-specific ones carry their own condition while the core duties stand unconditionally.
- `## Manual checks`: the review-specific checks, including the UI evidence boundary and retained or projected state rules, each keeping its concrete content.
- `## Reporting findings`: defect, location, impact and evidence; inline versus change-level; blockers versus suggestions; green-gate exclusions; reply and receiving-review conduct.

## Constraint dispositions

Dispositions use the forge skill's values: **Keep** carries the original wording and sense with language and layout adjustments; **Adapt** instantiates a target value; **Re-bind** abstracts a vanished referent to its purpose and finds the target's equivalent; **Dissolve** records that the referent is gone and what check takes over. The constraint column states the source requirement, including the source's own names; the basis states the target fact. Target homes: `SK` = the skill's single `SKILL.md`; section names follow the target shape above.

## Target rulings

| # | Ruling | Why | Reversible by |
|---|---|---|---|
| R1 | The review's requirements come from the adopting project's declaration — `AGENTS.md` or the file it cites — and from the artifacts that declaration names. The target states the categories to find and the mapping procedure, not fixed paths. ## Alternatives considered

**Carry the upstream text verbatim.** It lost because the request's audience and domain are software engineering, not the source repository: the verbatim text imports another project's commands, paths, framework rules and policy, and every one of them is false for an adopter.

**Reuse the deployed `.agents/skills/dsh-code-review` adaptation.** It lost because the deployed copies are not a design source; the request names the upstream skill, and every carried constraint must trace to that source. Reusing an earlier adaptation would leave the record unable to show the disposition of each source unit.

**Ship a change-scope script.** It lost because the upstream command is the source repository's tooling; the requirement is domain-neutral once its result is stated instead of its tool, and a bundled scope script would invent a mechanism the target does not own.

**Split the manual checks into a reference file.** It lost because the adapted text is expected to fit the gate's budget and every review needs the whole checklist; progressive disclosure would add a retrieval step without reducing the context a review uses.

**Replace the sources of truth with a generic best-practices checklist.** It lost because the mechanism is review against the project's own declared standards — generic advice cannot tell a reviewer what this project decided — and the reviews would no longer be able to cite an owning page.

**Keep the dsh-specific checks as conditional sections.** It lost because a condition written in one project's vocabulary still carries that vocabulary into a general skill; their general properties are re-bound instead, and the framework names are dissolved (R8). The reverse error — conditioning the core duties as if every project's declaration were thin — is what R11 rules out.

**Keep the upstream bilingual rules as mandatory.** It lost because whether a project pairs languages is its own declaration; the target keeps the paired-content check conditional on the project's policy.

**Leave the candidate unpublished at the stop.** It lost because the work directory and branch are the reversible state until review acceptance, and that acceptance is the landing authorization that turns the candidate into the shipped skill.

**Keep the blanket category conditionality.** It lost because the core review duties are unconditional and only mechanism-specific requirements are conditional: conditioning every category would let a thin declaration read as permission to skip the review itself.

**Rename the section headings for clarity.** It lost because the section headings follow upstream, so `## Sources of truth`, `## Blocking requirements`, `## Manual checks` and `## Reporting findings` keep their names.

**Publish without removing the superseded installed copy.** It lost because the new skill replaces `.agents/skills/dsh-code-review/`: the installed copy and its manifest entry are removed, and the pinned upstream baseline stays untouched.

**Land the record without its Chinese pair.** It lost because the notes tree's implemented records carry their pairs, and the final review is where the pair is written (R5); the pair record proves currency, not quality.

**Keep the rc.5 wording and record the alpha.2 diff as a deviation.** It lost because the package is an extraction that tracks upstream: numbered-rule citation and dependency-edge review are generic procedures that sharpen the check without naming the source repository, and no reason supplies a deviation.

**Carry the added `dsh-session-projection` sibling name as an availability-qualified example.** It lost because the package ships no such sibling; naming a skill that never ships creates an unavailable dependency. The generic mechanism is the adopting project's own state-persistence, projection or recovery rules, which S12 and M9 re-bind without importing the source's defaults (R14).

## Consequences

- The set ships `dsh-spec-code-review` at `skills/dsh-spec-code-review/` and its installed copy at `.agents/skills/dsh-spec-code-review/`; the superseded upstream-named installed copy and its manifest entry are gone, and `AGENTS.md` and the root `THIRD_PARTY_NOTICES.md` name the skill.
- The skill is prose-only: the upstream mechanism and its concrete checks are carried as the disposition table records, with the declaration-based re-binding, the natural-language scope requirement, the UI evidence boundary and the conditional asymmetry as the deliberate adaptations; the alpha.2 numbered-rule, dependency-edge and projection categories are adopted, with projection re-bound to project rules rather than a sibling dependency.
- The skill is maintained against the repository baseline `dsh-v0.2.3-alpha.2` (`4b399c39a6d1479cd84ca591b4d7c88e24d38a96`): the earlier required-behavior, producer-extension and configuration tests remain carried, numbered rules are cited by ID, module responsibilities are checked against dependency and reverse edges, required UI evidence remains blocking without optional-report overreach, and projection ownership, size, historical reads and migrations follow the adopting project's rules.
