# Agent Note: 从上游 code-review 技能锻造 dsh-spec-code-review

Status: implemented

[English](2026-10-28-forging-dsh-spec-code-review.md) | 中文

## 问题

包的技能集合包含锻造技能、agent-experience、agent-notes、prose-standard、find-simplifications、pre-push-checks 与 error-handling 技能。包里没有 code-review 技能，所以采用项目得不到一套 agent 可执行的流程，来对照项目自己声明的标准评审一个 PR（Pull Request）。上游 `dsh-code-review` 正是某个仓库的这套流程：一份面向评审者的技能，让评审者先确定评审基线与范围，在判断 diff 之前读管辖该变更的要求，检查一组阻断性要求，逐项走过只看代码无法覆盖的评审检查，并以统一格式报告发现。它的各小节列出了那个仓库的路径与机制——`pnpm change-scope`、`packages/AGENTS.md`、defensive-patterns 页面、Cordis、客户端 UI 本地化门禁、Agent Notes 树、双语规则。原样搬运会引入另一个项目的策略，使技能在项目之外不可用；略去则丢掉这套包要抽取的一项评审机制。锻造必须保留机制，并把每个仓库专用指涉重绑定到采用项目自己的声明。目标受众与领域是软件工程。

## 决策

包交付 `dsh-spec-code-review`，它面向软件工程改编自上游 `dsh-code-review` 技能。技能目录包含 `SKILL.md` 与技能根的 `THIRD_PARTY_NOTICES`；技能镜像到 `.agents/skills/`，上游同名的安装副本已不存在。`AGENTS.md` 与根 `THIRD_PARTY_NOTICES.md` 点名该技能。

`SKILL.md` 保留上游的小节名称与顺序——Sources of truth、Blocking requirements、Manual checks、Reporting findings——以及每一节承载的机制：确定评审基线与变更范围；在判断 diff 之前读管辖它的要求；执行阻断性要求；逐项走过评审专用检查；以统一格式报告发现。改编内容即处置表所记：采用项目的声明取代某个仓库的文档列表；范围要求以自然语言陈述，点名 `dsh-spec-pre-push-checks` 示例并以版本控制兜底；标题命名拟议变更；M0 保留必需的渲染证据，同时拒绝把可选报告或重复检查的缺失判为缺口；M9 应用采用项目的归属、状态大小、历史读取与迁移规则；M4a 对照 manifest 和调用点检查模块职责与运行时依赖边；核心评审职责保持无条件，机制型要求各自携带条件；包已交付的兄弟技能以括号示例出现；小节标题保持上游原词。description 已泛化并追加中文触发语言，frontmatter 的 `license` 字段指向技能根通知。交付技能不附带脚本、reference 或技能内测试；开发评估语料仍位于 `tests/skill-evals/`。alpha.2 相对上一版 rc.5 抽取基线增加编号规则 ID 引用、模块职责/依赖边评审、UI 证据边界与投影的来源类目；既有的必需行为、生产方扩展点与配置优先级检查继续承载；投影类目被重绑定到采用项目的设计规则，而不是来源仓库未交付的兄弟技能。

- 交付与语言：英文交付并附中文触发关键词；中文评审草稿（`SKILL.zh.md` 与其 `SKILL.i18n.yaml` 记录）在停止时产出并由 `publish` 移除，记录自身的中文对侧在落地时写入（R5、R6、R9）。
- 不附带脚本或包源码；开发语料留在交付技能之外。被评审项目的范围工具或版本控制提供变更范围（R2、R4）。

## 评审集成

交付技能要求项目现有的稳定、机器可读失败身份穿过机器可消费边界后保持不变，同时保留原始 cause 或等价的结构化细节，并禁止依据 message 文本进行路由。它对累计可见变更应用项目的 UI 证据规则：缺少必需的检查会记为缺口，省略可选报告则不会；普通变更无需完整审计记录，只有新增交互或证据失效时才需复核；具名项目豁免或等价证据形式拥有权威。源码检查和通过的测试都不能确立视觉验收。对于保留或投影的状态，技能应用项目的归属、大小或保留期限、历史读取与迁移规则；项目未声明时记下缺口。错误处理、UI 与状态要求无需另一个技能即可完整成立，其具体机制只以带可用性限定的示例出现。PR119 保留非答案盲的历史模型证据；PR122 记录依赖边与编号规则场景；PR141 重跑 UI 场景，并在 `tests/skill-evals/evidence/2026-11-25-pr141/` 下新增普通 UI 与投影对照项。仓库测试绑定场景输入、模式、能力档位、trace、技能 hash 与产物。

## 目标形态

技能是一个文件，沿用上游小节骨架：

- Frontmatter：`name: dsh-spec-code-review`；description 在评审对照项目声明标准的拟议变更时触发，并点名仅看代码无法覆盖的评审检查；追加中文触发语言；`license` 字段指向技能根通知。
- `# Reviewing a proposed change`：指导式框架、已核实的 base/head、变更范围、优先级顺序，以及“先读要求再判 diff”那一段。
- `## Sources of truth`：声明及其填充的类目——根与每个改动子树的常驻指令（standing instructions）；它引用的设计或架构规则，每个产物一个归属页面；文档与行文标准；它为改动领域点名的标准，例如行文、测试可靠性、错误处理、UI/UX，或状态持久化、投影与恢复；测试策略与质量门禁；决策记录；成对变更的语言与术语策略。核心评审职责无条件；机制型要求各自携带条件。
- `## Blocking requirements`：六条编号要求，各自保留上游属性；机制型要求携带自己的条件，核心职责保持无条件。
- `## Manual checks`：评审专用检查，包括 UI 证据边界以及保留或投影状态的规则，各自保留具体内容。
- `## Reporting findings`：缺陷、位置、影响与证据；内联与变更级；阻断与建议；已由绿色门禁强制的问题排除；回复与接收评审的规则。

## 约束处置

处置使用锻造技能的取值：**保留**（Keep）承载原始措辞与语义，仅调整语言与布局；**适配**（Adapt）实例化目标值；**重绑定**（Re-bind）把消失的指涉抽象到目的，再找到目标等价物；**消解**（Dissolve）记录指涉已消失，以及接管它的检查。约束列陈述来源要求，包含来源自身的名称；依据列陈述目标事实。目标落点：`SK` = 技能唯一的 `SKILL.md`；小节名沿用上面的目标形态。

## 目标裁定

| R1 | 评审的要求来自采用项目的声明——`AGENTS.md` 或它指向的文件——以及该声明点名的产物。目标陈述要寻找的类目与映射流程，不是固定路径。核心评审职责适用于任何软件项目并无条件陈述；只有管理项目可能没有的外部机制的要求才以该机制为条件；自带回退的要求把未声明的标准记为缺口，而不是用来源仓库替换。 | 通用项目的标准是它自己的；固定列表只是换名的某个仓库策略，而无条件核心职责让薄声明不至于削弱评审本身。 | 改 sources 小节与各要求的条件。 |

## 备选方案

**原样搬运上游文本。** 它失败是因为请求的受众与领域是软件工程，不是来源仓库：原样文本引入另一个项目的命令、路径、框架规则与策略，每一条对采用者都不成立。

**复用已部署的 `.agents/skills/dsh-code-review` 改编。** 它失败是因为部署副本不是设计来源；请求点名上游技能，每条搬用的约束都必须追溯到那个来源。复用更早的改编会让记录无法展示每个来源单元的处置。

**交付 change-scope 脚本。** 它失败是因为上游命令是来源仓库的工具；一旦陈述结果而不是工具，要求就与领域无关，打包范围脚本会发明目标不拥有的机制。

**把 manual checks 拆到 reference 文件。** 它失败是因为改编文本预期落在门禁预算内，且每次评审都需要整份检查项；渐进式披露只会增加检索步骤而不减少评审使用的上下文。

**用通用最佳实践清单替换事实来源。** 它失败是因为该机制是拿项目自己声明的标准来评审——通用建议无法告诉评审者这个项目决定了什么——而且评审将不再能引用负责该产物的页面。

**把 dsh 专用检查保留为条件小节。** 它失败是因为用一个项目词汇写成的条件仍会把那套词汇带进通用技能；它们的通用属性被重绑定，框架名被消解（R8）。反向错误——条件化核心职责，仿佛每个项目的声明都很薄——由 R11 排除。

**把上游双语规则保持为强制。** 它失败是因为项目是否成对语言由它自己声明；目标让成对内容检查以项目策略为条件。

**在停止时保持候选不发布。** 它失败是因为工作目录与分支在评审验收前是可逆状态，而该验收正是把候选变成已交付技能的落地授权。

**保留全类目条件化。** 它失败是因为核心评审职责无条件、只有机制型要求条件化：条件化每个类目会让薄声明被读成可以跳过评审本身的许可。

**为清晰重命名小节标题。** 它失败是因为小节标题遵循上游，因此 `## Sources of truth`、`## Blocking requirements`、`## Manual checks` 与 `## Reporting findings` 保留原名。

**发布但不移除被取代的安装副本。** 它失败是因为新技能取代 `.agents/skills/dsh-code-review/`：安装副本与清单条目被移除，固定的上游基线保持不变。

**不带中文对侧地落地记录。** 它失败是因为 notes 树中 implemented 记录携带对侧，而最终评审正是写出对侧的时点（R5）；配对记录证明当前性，不是质量。

**保留 rc.5 措辞，把 alpha.2 差异记为偏离。** 它失败是因为本包是跟随上游的抽取：编号规则引用与依赖边评审是通用流程，在不点名来源仓库的情况下让检查更锐利，而没有任何理由支持一个偏离。

**把新增的 `dsh-session-projection` 兄弟技能名称作为“可用时”示例搬用。** 它失败是因为包不交付这样的兄弟技能；点名一个永不交付的技能会制造不可用的依赖。通用机制是采用项目自己的状态持久化、投影或恢复规则，S12 与 M9 重绑定这些规则且不搬用来源的默认值（R14）。

## 后果

- 包交付 `dsh-spec-code-review`，路径为 `skills/dsh-spec-code-review/`，安装副本位于 `.agents/skills/dsh-spec-code-review/`；被取代的上游同名安装副本与清单条目已消失，`AGENTS.md` 与根 `THIRD_PARTY_NOTICES.md` 点名该技能。
- 技能是纯散文：上游机制与其具体检查按处置表所记保留，其中基于声明的重绑定、自然语言范围要求、UI 证据边界与条件非对称是刻意的适配；alpha.2 的编号规则、依赖边与投影类目被采纳，投影被重绑定到项目规则，而不是兄弟依赖。
- 技能按仓库基线 `dsh-v0.2.3-alpha.2`（`4b399c39a6d1479cd84ca591b4d7c88e24d38a96`）维护：既有的必需行为、生产方扩展与配置测试继续承载，编号规则按 ID 引用，模块职责对照依赖与反向边检查，必需的 UI 证据仍会阻断评审，同时不会把可选报告纳入过度要求，投影归属、大小、历史读取与迁移遵循采用项目的规则。
- 落地是 `refactor/dsh-skills` 上的一个提交；它之前的锻造分支是本地备份。
- **代价与限制。** 声明标准更少的项目得到核心职责与记下的缺口，而不是来源仓库策略；关联技能示例是指导而非依赖；改编文本按设计贴近来源，因此来源可追溯性取决于与来源的对照；中文对侧的保真是一项评审判断；没有状态持久化、投影或恢复规则的项目会得到记下的缺口，而不是来源仓库固定的大小、版本或检查点默认值。
- **回退。** 回退落地提交；它之前的锻造分支与仓库历史保留被移除的安装副本与更早的候选。
