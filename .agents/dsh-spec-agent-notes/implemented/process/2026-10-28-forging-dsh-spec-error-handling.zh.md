# Agent Note: 从上游 error-handling 技能锻造 dsh-spec-error-handling

Status: implemented

[English](2026-10-28-forging-dsh-spec-error-handling.md) | 中文

## 问题

本技能集合把 DeepSeek Harness 的开发模式抽取为技能，而该模式中有一部分背后没有技能：系统如何声明失败、赋予稳定的机器身份、决定谁拥有恢复，以及如何让结果对受影响的人可见。上游 `dsh` 把这一部分放在 `.agents/skills/dsh-error-handling/SKILL.md` 及其错误码参考中。它的标题点名 harness；它的示例引用该仓库的错误基类、registry 字段、errno 映射与 `assertNever` 辅助函数；它的约定规则说复用「包错误约定」；它的汇报规则假定该产品的运行时。本技能集合需要这套机制，而不需要该产品的类型、字段、路径或汇报假设。

## 决策

`dsh-spec-error-handling` 从 `skills/dsh-spec-error-handling/` 交付，其在 `.agents/skills/dsh-spec-error-handling/` 的安装副本与之逐字节一致。该技能是一份 `SKILL.md` 与 `references/error-contracts.md`，面向任何类型的软件工程项目：应用、库、命令行工具、服务、嵌入式系统与批处理系统。正文承载六个单元：类型化、结构化的失败；处理、恢复或停止；静默失败处理器；本地化、可见的报告；兼容性与验证；以及基础。参考文档拥有字段职责、错误族与错误码选择、标准条件、外部错误转换、兼容性和测试清单。

该技能不交付脚本。失败是否拥有一个错误族、遏制规则、静默处理的真实理由和可操作报告，都是设计判断。它没有环境要求，因此没有 `compatibility` 字段。

- 交付语言是英文；评审语言是中文，由于评审语言与交付语言不同，description 追加中文触发语言。

### 描述

该技能的 frontmatter description，逐字如下（484 个字符，低于仓库 500 字符的 catalog 预算）：

> Apply error-handling principles when designing, implementing, or reviewing failures in applications, libraries, command-line tools, and services: exceptions, result variants, status or exit codes, recovery, retries, background tasks, silent handlers, and user-visible error reports. Not for general code review, test design, performance tuning, or debugging unrelated to failure handling. 用于应用、库、命令行工具和服务中的错误处理：异常、结果变体、状态码或退出码、恢复、重试、后台任务、静默捕获与用户可见错误报告；不用于一般代码评审、测试设计、性能调优，或与失败处理无关的调试。

英文句子是交付语言。它点名采用该技能的系统形态、失败表示方式和技能覆盖的相邻任务，然后排除一般代码评审、测试设计、性能调优，以及与失败处理无关的调试。中文句子是附加触发语言。

### 要求锚点

每个处置行都是其承载要求的锚点。N1 是机械的：技能门禁检查名称与目录一致。N2-N30、N11a 与 E1-E10 是判断项，需对照上游句子。N30 保留外部文献链接。技能门禁机械检查格式、规模、参考文件和链接完整性。开发评估语料记录 message-only failure、边界丢失失败、静默多步骤处理，以及对项目现有判别值的保留。

`tests/skill-evals/evidence/2026-11-20-pr113/` 下的干净上下文模型评估针对 candidate、previous-skill 与 no-skill 三个 profile 运行了 `codex exec --ephemeral`。五个候选场景都加载了该技能，并通过了全部 20 项断言。previous-skill 基线通过了 20 项中的 18 项，因为它在静默处理器场景中丢弃了意外的清理失败；no-skill profile 通过了 20 项中的 19 项。每个场景一次候选运行是所测试行为的证据，并不宣称每种措辞或宿主 profile 都有相同效果。

十项查询的触发语料把候选版本安装在一个原本为空的项目中，并记录每次运行是否读取了 `SKILL.md`。五个正例提示词触发了该技能。五个近失提示词初次产生四条不触发和一条 performance-tuning 误触发；把 performance tuning 加入 description 的排除项后，重跑后五条全部不触发。该条查询的首跑不作为最终证据。

## 考虑过的替代方案

**原样承载上游文件，只改名字。** 它落败，因为它的三个指涉在一般项目中不存在——标题里的产品、`assertNever` 辅助函数与包约定——而它的五个句子与一个小节标题假定来源产品的运行时。来源仓库之外的读者无法据此行动，而该技能集合的采用者声明要求改动可追溯至来源或被记录为刻意偏离；保留产品词汇的复制两者都没做到。

**从机制出发用全新措辞重写规则。** 它落败，因为上游文本已经是软件工程指引，其精确性——拥有者、遏制、影响与可见性的区分——正是目标需要保留的；整篇重写会丢弃它，并要求为每个句子重新论证保真度。只有带假设的单元被改编。

**保留承载文本并增加范围段落。** 它落败，因为对目标范围的大部分而言规则将不再是规则，而边界将不得不重新定义机制所依赖的汇报呈现面；在使用点改编呈现面能让规则对每个项目保持完整。

**改编每个提到渠道或机制的句子。** 它落败，因为目标范围共享其中一些：后台任务、重试、回滚与声明的失败种类在缺失时是条件性或空真的，而不是错的；改编它们会增加词语而不改变规则。

**将扩大后的错误契约全部留在入口。** 它落败，因为错误族选择、code 命名、标准条件、转换与兼容性已经形成只在错误契约工作中使用的详细参考；入口仍保留较短的设计流程。

**随附一个检查设计是否有错误处理小节的脚本。** 它落败，因为来源中没有一条规则是机械可判定的：命令可以 grep 标题，但无法判定拥有者、遏制规则、保证或恢复路径是否正确。这样的脚本会发明来源没有的机制。

**保留 `assertNever` 作为示例。** 它落败，因为它点名一个生态的辅助函数；规则关乎缺陷的种类以及遏制不得做什么，目标可以在没有辅助函数名字的情况下陈述两者。

**把小节命名为「Intercept, recover, or stop」。** 它落败，因为 `handle` 是覆盖各失败模型中拦截与失败后行动的伞概念，而来源的拦截含义在 N15 中明确陈述；`intercept` 会点名一个步骤，而不是该小节的选择。

**增加实现步骤或评审清单。** 它落败，因为来源是原则的陈述，不是流程；步骤清单会把机制扩展到来源所述之外，并给读者第二份可违反的契约。

**给技能增加按文件的出处头。** 它落败，因为要求头部的通知句被限定到带 SPDX 标识符的引擎文件；交付的声明是由 `license` 字段点名的技能根 `THIRD_PARTY_NOTICES`，它随安装副本移动，而不进入加载文本（R7）。

## 后果

- 技能集从 `skills/dsh-spec-error-handling/` 交付 `dsh-spec-error-handling`，并带有逐字节一致的安装副本；交付物是入口、一个契约参考和技能根 notice。
- 入口不假定 UI、默认开启日志、API 文档实践、应用运行时、错误基类或单一失败模型。项目没有约定时，参考提供只约束结果、不规定实现或表示形式的新失败兜底要求。
- 详细契约只有一个参考拥有者；入口在错误族和 code 决策需要细节时链接到它。
- 代价：参考为约定相关工作增加一个按需加载文件；概括措辞不如产品示例具体；每个场景一次干净上下文运行覆盖了已改变的决策，但不能确立所有提示词下的触发精确度。
- 风险：过度泛化可能丢掉来源的力量；审计之外的句子仍可能携带未记录的假设；改编可能漂移；description 可能与 code-review 技能竞争。
- **执行者遵循是判断，不是测量。** agent 是否应用这些规则是判断；没有命令能判定它，因此技能的效果依赖评审。
- **预设分类是判断。** 一个句子的运行时假设是共享、空泛还是不共享，是逐句判定的，记录在 § 预设审计 中，评审对照目标范围检查该分类。
- **机制一致是判断，无法机械证明。** 与上游机制的一致由评审对照来源文本检查。
- 被放弃的东西：改编单元上的逐字忠实、产品专属错误基类契约和按文件的出处头。
- 回滚：回退本技能修订、安装副本、评估语料与本记录；基线 pin 仍由 #104 拥有。
