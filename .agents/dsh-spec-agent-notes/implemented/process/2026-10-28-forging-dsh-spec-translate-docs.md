# Agent Note: Forging dsh-spec-translate-docs as a self-contained translation mechanism

Status: implemented

English | [中文](2026-10-28-forging-dsh-spec-translate-docs.zh.md)

## Problem

The first design of this forging, superseded on this branch, extracted only the workflow map of upstream `dsh-translate-docs` and left the pairing record, the switcher lines, the consistency check and the terminology discipline to an "adopter's pairing mechanism" that this package does not ship. A fresh adopter installing the skill would receive guidance that stops at a mechanism it does not have; routine maintenance of already-paired documents would not be owned by the skill; and the deliverable would be the only skill in this package that is not self-contained.

The misreading was to treat upstream's project-internal layout as a design boundary. Upstream keeps `gen-translation-brief` and `verify-translation-pairing` in its repository's `scripts/` and its pairing contract, translation rules and terminology discipline in `docs/i18n/`, but those scripts, contracts and the SKILL.md are one cohesive mechanism; the files sit outside SKILL.md only because the mechanism serves that repository alone. The target of this forging is the whole mechanism, extracted and generalised.

The direct user rulings that replace the earlier adjudication for this branch:

- the mechanism is self-contained: the skill ships scripts that mechanically check a pair and generate its record;
- the scripts reference upstream only — this repository's manager port is historical residue that this forging will replace, not a source;
- the invocation boundary is stated in the body only; the description carries no user-naming rule;
- one skill; the adopter-declared and already-paired files are maintained automatically; other new pairings need the user's consent;
- source language defaults to English, the counterpart language is the adopter's and is declared or named in conversation; multiple languages are declared or instructed;
- the terminology table lives at `.agents/dsh-spec-translate-docs/terminology.md`, and a missing table is initialised from a template;
- one constraint replaces a two-path body: do not pair an unpaired file unless the adopter's declaration covers it or the user explicitly asks;
- no separate adopter declaration file: the adopter declares in its own declaration, the agent passes the facts to the scripts, and the scripts never read a project config.

## Decision

Forge `dsh-spec-translate-docs` as a self-contained extraction of the upstream bilingual-document mechanism: one skill whose SKILL.md is the workflow map, whose `references/` carry the pairing contract, the translation rules and the style-sample convention, and whose bundled `scripts/translate-pair.mjs` is the mechanical half — pair listing, checking, recording, region comparison, minimal-update briefing, mechanical splice, and terminology-template initialisation. The range-wide check and review reporting name `dsh-spec-pre-push-checks` and `dsh-spec-code-review` only as availability-qualified examples; the project's own checks and review convention remain the binding rules.

### v2 redesign

The user approved a second redesign that supersedes the v1 corpus-completeness model and the fixed English source language; R51–R64 own the decisions and V29–V36 their evidence. The mechanism is now an **existing-pair consistency gate**: the check verifies the pairs that exist, while creation and update are driven by the project's declaration or the user's instruction.

- **Gate.** Only existing pairs are checked: aggregate-record structure, recorded hashes, switchers, structural signature, generated-region equality and section anchors, and link locale. Completeness, the excluded-artifact rule and the required-pair error are removed. --select and --skip choose existing pairs; they do not demand or forbid pairing. An empty check exits 2; list on an empty repository reports zero rows and exits 0.
- **Languages.** Source and target languages are properties of a pair. A source file is unsuffixed; its source language is the code on the source hash line of every record section and is supplied with --source-lang when the first record is written (default en only when omitted). Targets are declared and may differ per source; the default target stays zh=中文.
- **Record.** One foo.i18n.yaml per source is flat: each section has one source hash and one target signature per target. A target signature is H(sourceHash || targetContentHash), so a source edit invalidates every target confirmation; write --target updates the source hash and that signature only, while write --all refreshes every existing target and drops targets whose counterpart is gone. There is no per-target or nested record file.
- **Update paths.** The SKILL carries three: a lightweight direct update for one or two units in one section; the briefing path for other existing-pair changes (including code-fence-only --apply); and delegated whole-document translation for new pairs. The orchestrator does not translate whole documents.
- **Generated regions.** Marker shell A follows the upstream shape (BEGIN with an optional trailing note, END exact, slug one token), while the skill keeps fence awareness, own-block, duplicate-slug and marker-shape strictness. Region lines are masked for the record, section keys and structure signature; positions are compared through the authored section anchor. The script exposes region render and region splice as a correctness-enforcing generator CLI; it carries no JavaScript generator API.
- **Data and voice.** Terminology keeps its defaults and table format; only the path is adopter-declarable. Style is one replaceable references/style-examples.md carrying default guidance and selected upstream English-to-Chinese samples; a project's declared style file replaces it wholesale, and the non-negotiable priority lives in translation-rules.md. Provenance lives only in notices.
- **Removed.** The automatic-pipeline translation-prompt.md stays uncarried: it is a machine-consumed prompt asset for fixed English-Chinese whole-document generation, explicitly not rendered by agents using the upstream skill. Delegation is carried by the SKILL and the briefing.
- **Migration.** Existing pairs are re-recorded once into the aggregate format; archived, frozen and vendored trees are simply not selected. There is no v1-record compatibility layer because nothing landed.

### The pairing model

- **A pair is three sibling files.** A source document `foo.md` (the source language is English in v1); its counterpart `foo.zh.md` for the default target language or `foo.<lang>.md` for another declared target; a consistency record `foo.i18n.yaml` for the default target or `foo.<lang>.i18n.yaml` for another target. A pair merges whole: both sides and the record.
- **The record is section-keyed.** One entry per heading-section path that still carries language-specific content. The key is the section's source-heading slug path (`/` for text before the first heading; a repeated path gets `~2`, `~3`, …); the entry holds a hash of the source and of the counterpart blocks in that section, excluding fenced code blocks and generated regions (R28/R28a), which the contract already requires byte-identical. Content that merely happens to be identical is still hashed, so a code-only or region-only change leaves the record untouched and independent edits to different sections change separate lines. Paired-document link destinations are normalized to their semantic target before hashing, so a locale-only rewrite of a link does not invalidate the record; the normalization predicate is defined below. The canonical record comment names `references/pairing-contract.md` and the skill's own `write` command; comment lines are provenance the check ignores (R30/R45), while a record migrated from another mechanism re-records once because its link-bearing hashes were computed with a different sentinel (R13/R34), not because of the comment.
- **Language switchers.** The switcher is the unique top-level paragraph between the H1 and the next heading whose label/link structure matches the canonical line; metadata paragraphs such as `Status:` may precede it, and only that paragraph's links are exempt from the structure signature and the locale check. The source side reads `English | [中文](foo.zh.md) | [日本語](foo.ja.md)`, listing every existing counterpart in language-code order; a counterpart side reads `[English](foo.md) | 中文`. A link destination is the relative counterpart path or an absolute URL whose pathname ends with it, and a generated source declared with `--generated` waives only its own side's switcher while the counterpart still links back.
- **Language model.** The source language is English in v1 (no source-language option; a non-English source waits for a declared model). Targets are declared as `--target <lang>=<display>`, repeatable; `zh=中文` is the documented default for this package's own bilingual corpus, and the adopter's declaration supplies the real list. A document may carry several counterparts; each counterpart is its own pair, and every pair is recorded separately. Declared target suffixes identify counterparts, and an existing pair is additionally recognized from its artifacts — a counterpart with its record — so a file whose pair already exists is maintained even when the declaration does not name its target, with the language code standing in as the display name until the declaration names it. A `.md` that matches no declared or existing-pair suffix is a source document; a source file must not be named with target-suffix syntax — if it is, the file is a counterpart, so rename the source (declaring a target is how a document becomes paired, not how it stays a source). `zh=中文` is the package default only when no `--target` is passed; passing targets replaces it.
- **Scope and exclusions.** The adopter's declaration says which documents must be paired and in which targets; the agent passes that scope as repeatable `--scope <glob>` and `--exclude <glob>` flags. A *recognized target* is a declared target, the default target, or the target of an existing pair. With a scope, completeness means every in-scope source has a pair for every declared target; an in-scope unpaired source is a missing pair, and the fix is to pair it or add it to the declaration's `--exclude` list; the exclusion is dropped when its pair is created. Without a scope the verbs touch existing pairs only. An excluded source must have neither a counterpart nor a record; a pair artifact found on an excluded path is a violation. A check over an empty corpus fails rather than passing silently. There is no persisted manifest and no project config file.
- **The link predicate.** A document belongs to the pair corpus when the supplied scope and exclusions say so; with no scope, a document belongs when it already has a counterpart or a record for at least one recognized target. Record normalization and locale checking use the same predicate. A pair's sources and counterparts must pass the same scope flags whenever a project declares one, so the predicate — and therefore the record normalization — is the same at write time and at check time. Adding or removing a pair can change the predicate for documents that link to it; the contract says to re-record the affected pairs in that change, and the check reports them out-of-sync until it is done.
- **Expected locales.** A relative document link to a target that belongs to the pair corpus keeps its semantic target: the source side links to the base document, and the counterpart side of language L links to that document's L counterpart. A target outside the corpus keeps the authored path. The switcher links are exempt.
- **Terminology.** The table is project data, one file per target language: `.agents/dsh-spec-translate-docs/terminology.md` for the default target (`zh`) and `.agents/dsh-spec-translate-docs/terminology.<lang>.md` for another target, overridable with `--terminology <lang>=<path>`. One or more Markdown tables; by column position: 1 the source term (English), 2 the target rendering, 3 the first-occurrence form, 4 forbidden renderings, 5 a note. `init` writes the template for one target when the file is missing and never overwrites one. The briefing quotes the rows the change touches; the translator applies them; the contract owns the pending-term protocol.
- **Git and runtime.** The `brief` verb needs Git because it recovers the last-confirmed text from commits whose contents produce the recorded state; `list`, `check`, `write` and `init` read the worktree only. Node 22.19+ or 24+ is the runtime; nothing installs and nothing reaches the network.
- **What the check decides vs what review owns.** The check decides completeness, the recorded state, switcher presence and canonical structure, the structural signature, generated-region equality, the excluded-file rule, generated-source exemption and link locale. Review owns translation quality, terminology decisions, list and table order, noncanonical numbering, inline code, emphasis, meaning and tone.

### Pair selection and the multi-target workflow

| Argument form | Pair selected |
|---|---|
| `foo.zh.md` or `foo.i18n.yaml` | the `zh` pair |
| `foo.<lang>.md` or `foo.<lang>.i18n.yaml` | the pair for that recognized target |
| `foo.md` or `foo` | every recognized target's pair for that source; several `--target` values select several pairs |
| no pair arguments (`brief`) | every existing pair for every recognized target |

A named pair needs no `--scope`: this is what lets the skill's own stop-time review draft, and work on a single pair outside a declared corpus, be recorded and checked.

- The authored side of the change is its pair's update source (both sides carry equal authority): a source edit runs the source-to-target path for that pair, and a counterpart edit first runs the target-to-source path and updates the source.
- Once the source changes, every other declared target's pair of that source is maintained in the same change: an existing pair is updated and re-recorded, and a declared-in-scope source whose pair does not exist yet is translated through the whole-document path and recorded — that is routine maintenance under the declaration.
- A translation-only correction that leaves the source untouched is pair-local: it may update a counterpart and re-record that pair without touching the other targets. The contract states this as the one exception; a correction that changes meaning in the source is not one.
- A corpus check with `--scope` requires every in-scope source × every declared target.

### Script interface

`node <skill-dir>/scripts/translate-pair.mjs <verb> [options] [pairs...]`; run from the project root, `--root <dir>` overrides it.

| Verb | Behaviour and exit |
|---|---|
| `list [--scope …]… [--exclude …]… [--generated …]…` | report existing pairs, or every in-scope source × declared target with a scope, as `ok`, `out-of-sync`, `missing` or `unrecognized`; a region mismatch or a failing pair state is what `out-of-sync` means; never fails on state, exit 0 |
| `check [pairs…] [--scope …]… [--exclude …]… [--generated …]…` | verify complete pairs: three files, record body matching the entries, switchers, structure signature, generated-region comparison, excluded-file rule, link locale. Named pairs only by default; a scope adds completeness over every in-scope source × declared target. `0` clean, `1` violations or an empty corpus, `2` usage or a named argument that names no pair on disk |
| `write <pairs…> \| --all [--scope …]… [--exclude …]… [--generated …]…` | recompute and write the record for the pairs the caller confirmed. `--all` records every complete pair in scope, or every complete existing pair without a scope; it is the only way to record without naming pairs. `0` written (at least one), `1` nothing to record, `2` a named pair is incomplete or a usage error |
| `brief [pairs…] [--apply] [--scope …]… [--exclude …]… [--generated …]…` | print the minimal-update briefing for drifted pairs; with no pair arguments it discovers every drifted existing pair across the declared targets. `0` nothing to brief, `1` `--apply` refused because the computed splice would violate the structure, `2` a named pair is consistent, incomplete, a pair whose current regions disagree, or has no recoverable last-confirmed commit; a pair-less run aborts with exit 2 naming the pairs whose current regions disagree (a half-generated pair is a corpus-wide regeneration error, not a per-pair precondition the discovery run can skip) |
| `init [--target <lang>=<display>]` | create the target's terminology file from the template when missing; exactly one target per invocation (omitted = the default; more than one is a usage error); `--generated`, `--scope`, `--exclude`, `--apply` and `--all` are rejected with exit 2; `0` created or already exists (prints which), `2` usage |

Shared options: `--target <lang>=<display>` (repeatable; default `zh=中文`), `--scope <glob>`, `--exclude <glob>`, `--terminology <lang>=<path>` (repeatable; defaults as above), `--generated <glob>` (corpus verbs only), `--root <dir>`, `--apply` (brief only), `--all` (write only). `init` accepts only `--target`, `--root` and `--terminology`; the corpus verbs accept `--generated`.

`--apply` computes the code-fence-only counterpart, validates the structure signature before writing anything, and writes only on success; on a change that is not code-fence-only it exits 2 and writes nothing. A target's terminology file must exist before a translation runs: the update path and the whole-document path run `init` for the target when it is missing, and `brief` refuses with exit 2 and the init hint until it does.

The terminology template `init` writes: a heading, one short paragraph naming the target language and the column semantics, and an empty five-column table `| English | <display> | First occurrence | Forbidden renderings | Note |` followed by its delimiter row `|---|---|---|---|---|`. It is written only when absent.

### Generalisation and simplification decisions

| Aspect | Upstream | This skill | Basis |
|---|---|---|---|
| Source language | English, hardcoded | English in v1; no source-language option | the request's default; a non-English source needs a declared model, recorded as out of v1 scope |
| Target languages | Simplified Chinese, hardcoded | declared `--target <lang>=<display>`, repeatable; `zh=中文` default | the adopter's language(s); the default preserves the extracted corpus |
| Pair naming | `.zh.md` + `.i18n.yaml` | `.zh.md`/`.i18n.yaml` for `zh`; `.<lang>.md`/`.<lang>.i18n.yaml` for another target | upstream compatibility plus multilingual pairs |
| Pair selection | one pair per source | a target-suffixed path selects one pair, longest record suffix first; a source path or bare stem selects the pairs that exist for it, with `--target` selecting a declared target that has no artifacts yet; named pairs need no scope | the record must not demand pairs a repository never had, a non-default record must not be shadowed by the default suffix, and the stop draft and single-pair maintenance stay addressable |

### Auto-maintenance and invocation rule

One constraint replaces the earlier two-path layering:

- an existing pair is maintained as part of any edit that touches either side — bring the counterpart along, re-record it, and check the pair in the same change;
- a document the adopter's declaration puts in scope is paired for every declared target as routine maintenance, through whichever path the pair needs (the update path when it exists, the whole-document path when it does not);
- do not pair an unpaired document outside the declaration, and do not add a target the declaration does not name, unless the user explicitly asks; that is where the user's request governs;
- the heavier one-off work — translating a document the declaration does not cover, or a corpus the declaration does not name — runs only when the user explicitly invokes the skill or asks for it.

This is the declaration-authorises reading: the declaration, not a separate invocation, authorises routine pairing and maintenance of its scope; explicit invocation governs work outside it.

## Alternatives considered

**Keep the first design (adopter-owned pairing mechanism).** It loses on the user's ruling: a fresh adopter has no mechanism to supply, so the skill would stop at a missing record and check, and it would not own the routine maintenance the request now requires.

**Reuse this repository's `scripts/dsh-spec-manager` port as the script source.** It loses on the user's ruling: that engine is the historical residue this forging replaces, and taking it as the source would keep the port's dsh-spec-specific shape in a skill that must trace to upstream.

**Reuse the schema format only and write a new engine.** It loses because the mechanical half — structure signature, section record, briefing granularity, link locale — is exactly the part upstream already implements; writing it from scratch would be a second implementation with no provenance.

**Two skills: one automatic maintainer, one explicitly invoked extended workflow.** It loses on the user's ruling that the structure is one skill; the boundary is the declaration plus one constraint in the body, not a second package.

**Control invocation through the frontmatter fields or a `metadata` key.** It loses because the Agent Skills frontmatter is a closed set, the fields are Claude-Code extensions, dsh and Codex read no invocation control from `metadata`, and disabling model invocation would remove the skill from the catalog, which contradicts automatic maintenance.

**A persisted scope/config file beside the terminology table.** It loses on the user's ruling: the adopter declares in its own declaration, the agent passes the facts, and a file no script reads would be a second source of truth.

**One terminology file with per-language columns.** It loses because a table's rendering column belongs to one target language, a source with several counterparts needs several tables per term, and the file would have to grow columns for every declared language; one file per target keeps the column shape the extracted table has and selects the file by target.

**Ship the dsh style samples and the pipeline prompt verbatim.** They lose because sample texts are the project's and the pipeline prompt is a pipeline asset. The skill ships the style-sample convention and the distilled language-neutral principles (R35), and the translation rules name the project's declarations for the rest.

**Support arbitrary plain-text formats in v1.** It loses because the shipped record, structure signature and briefing unit model are document-class concepts; v1 ships the Markdown class, and another class waits for a declared model.

**Build the stop without the review draft.** It loses because the request pairs review drafts before stopping and the human reviews the Chinese draft; the pair is the mechanism's own proof.

## Consequences

- **The gate no longer proves corpus completeness.** A declared document without a counterpart is simply not a pair; the declaration, the lightweight path and review own creation. This is the explicit trade for per-file target sets and a stable gate.
- **The aggregate record has one target signature line per target.** A source edit recorded for only one target leaves the other signatures bound to the old source and out of sync by design; the check catches this, but the workflow must update every existing target in the same change. Concurrent edits to the same source should serialize.
- **Retirement is a bulk operation.** Removing a counterpart requires removing its switcher link and then write --all; a named write never drops a target. An entry whose counterpart is gone is reported incomplete until the bulk write.
- **Per-file source language relies on the record and the counterpart label.** A first record without --source-lang falls back to en; a French source must supply the flag once. Mixed source languages are created per-source, not by one bulk write.
- **The lightweight path depends on agent discipline.** Its conditions are prose; a working agent that oversteps gets a red check but may produce a worse minimal edit than the briefing path. The triage tells it to switch when uncertain.
- **Region anchors are section-level.** A region moved within the same authored section is not caught; both sides agreeing on a wrong position is treated as a coordinated change. A region before the first heading has anchor 0.
- **Shell A is looser than the old slug grammar.** A marker line is accepted when it matches the upstream-shaped shell, including punctuation in the slug and an optional BEGIN note; the stricter fence, own-block and duplicate rules still apply.
- **The existence-based link predicate can flip when a pair is added.** Adding a counterpart can change normalization for links that point at it; affected existing pairs must be re-recorded in the same change.
- **Migration is a one-time aggregate re-record.** The selected live corpus is re-recorded once; there is no v1-record compatibility layer and no per-target record reader. Archived, frozen and vendored trees are not selected.
- **The project declaration is the only source of creation intent.** The script never reads it; the agent passes --select/--skip, targets, terminology and generated globs. A CI run that forgets the declaration's flags checks fewer pairs, not a wrong corpus.
- **Hidden and vendored trees are adopter layout.** The walk enters hidden directories and prunes only the default trees; a broad declaration must use --skip for frozen or vendored trees.
- **Translation quality is unverified by the mechanism.** The stop's review draft is the first run of the workflow; the check proves pair completeness and consistency, not that the prose reads well.
- **Landing replaces the repository's current pairing mechanism.** The declaration and the selected re-record are follow-ups after the human review; this branch does not modify the manager, the installed copies, the pinned submodule or any shared file.
