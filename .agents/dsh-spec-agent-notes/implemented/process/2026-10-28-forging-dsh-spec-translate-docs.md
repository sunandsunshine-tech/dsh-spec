# Agent Note: Forging dsh-spec-translate-docs as a self-contained translation mechanism

Status: implemented

English | [中文](2026-10-28-forging-dsh-spec-translate-docs.zh.md)

## Problem

An extraction of only the workflow map of upstream `dsh-translate-docs` would leave the pairing record, the switcher lines, the consistency check and the terminology discipline to an "adopter's pairing mechanism" that this package does not ship. A fresh adopter installing the skill would receive guidance that stops at a mechanism it does not have; routine maintenance of already-paired documents would not be owned by the skill; and the deliverable would be the only skill in this package that is not self-contained.

Treating upstream's project-internal layout as a design boundary is the misreading. Upstream keeps `gen-translation-brief` and `verify-translation-pairing` in its repository's `scripts/` and its pairing contract, translation rules and terminology discipline in `docs/i18n/`, but those scripts, contracts and the SKILL.md are one cohesive mechanism; the files sit outside SKILL.md only because the mechanism serves that repository alone. The target of this forging is the whole mechanism, extracted and generalised.

Design rulings for this skill:

- the mechanism is self-contained: the skill ships scripts that mechanically check a pair and generate its record;
- the scripts reference upstream only — this repository's manager port is historical residue that this forging will replace, not a source;
- the invocation boundary is stated in the body only; the description carries no user-naming rule;
- one skill; the adopter-declared and already-paired files are maintained automatically; other new pairings need the user's consent;
- source language defaults to English, the counterpart language is the adopter's and is declared or named in conversation; multiple languages are declared or instructed;
- the terminology table lives at `.agents/dsh-spec-translate-docs/terminology.md`, and a missing table is initialised from a template;
- one constraint replaces a two-path body: do not pair an unpaired file unless the adopter's declaration covers it or the user explicitly asks;
- no separate adopter declaration file: the adopter declares in its own declaration, the agent passes the facts to the scripts, and the scripts never read a project config.

## Decision

`dsh-spec-translate-docs` is a self-contained extraction of the upstream bilingual-document mechanism: one skill whose SKILL.md is the workflow map, whose `references/` carry the pairing contract, the translation rules and the style-sample convention, and whose bundled `scripts/translate-pair.mjs` is the mechanical half — pair listing, checking, recording, region comparison, minimal-update briefing, mechanical splice, and terminology-template initialisation. The range-wide check and review reporting name `dsh-spec-pre-push-checks` and `dsh-spec-code-review` only as availability-qualified examples; the project's own checks and review convention remain the binding rules.

- Delivery language is English; the review language is Chinese, and additional Chinese trigger language is appended to the description because the review language differs from delivery.
- The skill ships from `skills/dsh-spec-translate-docs/` and the installed mirror under `.agents/skills/`; the terminology table lives at `.agents/dsh-spec-translate-docs/terminology.md`; the old installed `dsh-translate-docs` copy and the `scripts/dsh-spec-manager/` engine are gone (R70, R71).

### Auto-maintenance and invocation rule

The auto-maintenance rule rests on one constraint:

- an existing pair is maintained as part of any edit that touches either side — bring the counterpart along, re-record it, and check the pair in the same change;
- a document the adopter's declaration puts in scope is paired for every declared target as routine maintenance, through whichever path the pair needs (the update path when it exists, the whole-document path when it does not);
- do not pair an unpaired document outside the declaration, and do not add a target the declaration does not name, unless the user explicitly asks; that is where the user's request governs;
- the heavier one-off work — translating a document the declaration does not cover, or a corpus the declaration does not name — runs only when the user explicitly invokes the skill or asks for it.

This is the declaration-authorises reading: the declaration, not a separate invocation, authorises routine pairing and maintenance of its scope; explicit invocation governs work outside it.

## Alternatives considered

**Keep the adopter-owned pairing mechanism.** It loses because a fresh adopter has no mechanism to supply, so the skill would stop at a missing record and check, and it would not own the routine maintenance the request requires.

**Reuse this repository's `scripts/dsh-spec-manager` port as the script source.** It loses because that engine is historical residue, not a source, and taking it would keep the port's dsh-spec-specific shape in a skill that must trace to upstream.

**Reuse the schema format only and write a new engine.** It loses because the mechanical half — structure signature, section record, briefing granularity, link locale — is exactly the part upstream already implements; writing it from scratch would be a second implementation with no provenance.

**Two skills: one automatic maintainer, one explicitly invoked extended workflow.** It loses because the structure is one skill; the boundary is the declaration plus one constraint in the body, not a second package.

**Control invocation through the frontmatter fields or a `metadata` key.** It loses because the Agent Skills frontmatter is a closed set, the fields are Claude-Code extensions, dsh and Codex read no invocation control from `metadata`, and disabling model invocation would remove the skill from the catalog, which contradicts automatic maintenance.

**A persisted scope/config file beside the terminology table.** It loses because the adopter declares in its own declaration, the agent passes the facts, and a file no script reads would be a second source of truth.

**One terminology file with per-language columns.** It loses because a table's rendering column belongs to one target language, a source with several counterparts needs several tables per term, and the file would have to grow columns for every declared language; one file per target keeps the column shape the extracted table has and selects the file by target.

**Ship the dsh style samples and the pipeline prompt verbatim.** They lose because sample texts are the project's and the pipeline prompt is a pipeline asset. The skill ships the style-sample convention and the distilled language-neutral principles (R35), and the translation rules name the project's declarations for the rest.

**Support arbitrary plain-text formats in v1.** It loses because the shipped record, structure signature and briefing unit model are document-class concepts; v1 ships the Markdown class, and another class waits for a declared model.

**Build the handoff without the review draft.** It loses because the Chinese review draft is the mechanism's own proof and the pair is checked before the handoff.

## Consequences

- **The gate does not prove corpus completeness.** A declared document without a counterpart is simply not a pair; the declaration, the lightweight path and review own creation. This is the explicit trade for per-file target sets and a stable gate.
- **The aggregate record has one target signature line per target.** A source edit recorded for only one target leaves the other signatures bound to the old source and out of sync by design; the check catches this, but the workflow must update every existing target in the same change. Concurrent edits to the same source should serialize.
- **Retirement is a bulk operation.** Removing a counterpart requires removing its switcher link and then write --all; a named write never drops a target. An entry whose counterpart is gone is reported incomplete until the bulk write.
- **Per-file source language relies on the record and the counterpart label.** A first record without --source-lang falls back to en; a French source must supply the flag once. Mixed source languages are created per-source, not by one bulk write.
- **The lightweight path depends on agent discipline.** Its conditions are prose; a working agent that oversteps gets a red check but may produce a worse minimal edit than the briefing path. The triage tells it to switch when uncertain.
- **Region anchors are section-level.** A region moved within the same authored section is not caught; both sides agreeing on a wrong position is treated as a coordinated change. A region before the first heading has anchor 0.
- **Shell A is looser than the earlier slug grammar.** A marker line is accepted when it matches the upstream-shaped shell, including punctuation in the slug and an optional BEGIN note; the stricter fence, own-block and duplicate rules still apply.
- **The existence-based link predicate can flip when a pair is added.** Adding a counterpart can change normalization for links that point at it; affected existing pairs must be re-recorded in the same change.
- **Migration is a one-time aggregate re-record.** The selected live corpus is re-recorded once; there is no v1-record compatibility layer and no per-target record reader. Archived, frozen and vendored trees are not selected.
- **The project declaration is the only source of creation intent.** The script never reads it; the agent passes --select/--skip, targets, terminology and generated globs. A CI run that forgets the declaration's flags checks fewer pairs, not a wrong corpus.
- **Hidden and vendored trees are adopter layout.** The walk enters hidden directories and prunes only the default trees; a broad declaration must use --skip for frozen or vendored trees.
- **Translation quality is unverified by the mechanism.** The check proves pair consistency, not that the prose reads well; translation quality is not measured.
- **The repository's previous pairing mechanism is gone.** The legacy manager engine and the old installed copy are gone (R71).
