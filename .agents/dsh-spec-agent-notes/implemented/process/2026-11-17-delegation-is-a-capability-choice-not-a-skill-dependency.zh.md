# Agent Note: 委派是能力选择，不是技能依赖

Status: implemented

[English](2026-11-17-delegation-is-a-capability-choice-not-a-skill-dependency.md) | 中文

## 问题

两个交付技能把 subagent 写成整篇文档翻译和宽泛简化调查的唯一路径。harness 并不保证每个采用者都提供 subagent、并行执行或隔离上下文。把其中任一机制写成必需，就会把一个可选的执行能力变成安装前提，并阻止合法任务完成。反过来完全删除隔离要求也是错误：独立生成或审查可以是质量边界，静默丢掉它会得到自信但无效的结果。

## 决策

技能陈述所需结果以及需要保留的隔离或覆盖性质。subagent、并行执行和隔离上下文是可选机制，不是安装要求。宿主提供适用机制时，技能可以使用；没有时，使用仍能保留该性质的等价路径：有界顺序处理、干净上下文交接、分阶段独立审查或其他可验证方式。如果没有任何等价路径能保留必需的质量边界，就停止并交接，明确缺少的能力、已完成工作和剩余工作；不得把静默降质的结果当作完成。

本笔记拥有技能必需结果的可移植性。[委派交给 harness 与提示词](2026-09-23-delegation-follows-the-harness-and-the-prompt.zh.md) 继续拥有仓库级规则：技能不规定载体阶梯。带明确回退的能力偏好不是载体选择协议。

## 备选方案

- **保留强制 subagent 路径。** 这会破坏独立安装，并把宿主能力缺口变成任务内容失败。
- **删除所有 subagent 提及。** 这会丢掉可用的隔离上下文路径，并在宿主提供隔离能力时削弱独立审查。
- **新增中央“何时使用 subagent”阶梯。** 这会复活既有委派决定撤销的、依赖部署形态的协议。
- **把所有当前上下文内的执行视为等价。** 这会允许静默降质和虚假完成。
- **要求项目声明可用能力。** 这会增加配置负担，并违背“缺少项目声明是有效状态”的规则。
- **要求用兄弟技能作为回退。** 这会把安装依赖换一个名字重新建立。

## 后果

- 没有 subagent 的宿主可以通过可验证路径完成局部任务，或对需要隔离的任务得到明确交接。
- 有能力的宿主保留隔离上下文偏好，但不规定 subagent 数量、深度或工具名。
- 两个受影响技能各自在本地 eval 语料中携带能力缺失和能力可用的场景。
- 锻造流程要求依赖能力的技能记录能力可用与能力缺失两类结论。
