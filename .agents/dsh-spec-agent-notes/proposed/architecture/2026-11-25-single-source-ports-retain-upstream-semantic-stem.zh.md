# Agent Note: 单来源移植保留上游语义词干

Status: proposed

[English](2026-11-25-single-source-ports-retain-upstream-semantic-stem.md) | 中文

## Problem

技能集合同时包含单来源直接移植、单来源通用化移植，以及由多个上游工作流组成的复合技能。如果每个移植都获得一个按意图命名的新名称，采用者就无法从目录识别它的上游来源，历史证据也难以映射到如今承载同一任务族（task family）的技能。#135 之前的性能技能是一个具体例子：它的行为源自 `dsh-speed-up-perf`，但名称没有保留这个语义词干。

## Proposal

单来源直接移植或通用化移植会在 `dsh-spec-` 命名空间下保留其上游工作流的语义词干。只有复合技能或确实合并后的范围可以采用新名称，并且其锻造记录必须点名每一个上游输入，并说明为什么合并后的名称更准确。

### 已发布的命名选择

#126 中的直接移植重命名交付了本提案的两个应用：`dsh-ci-test-reliability` 安装为 `dsh-spec-ci-test-reliability`，`record-browser-gif` 安装为 `dsh-spec-record-browser-gif`。

#144 已为单来源通用化移植落实本提案。`dsh-ci-test-reliability` 以 `dsh-spec-ci-test-reliability` 保留语义词干，技能把通用化后的行为限定在 CI 或等效测试执行通道；生产性能仍不属于该技能。

#135 将这条规则应用于通用化的性能移植：`dsh-speed-up-perf` 安装为 `dsh-spec-speed-up-perf`。

`dsh-spec-agent-notes`、`dsh-spec-client-ui-ux` 和 `dsh-spec-prose-standard` 继续使用复合名称。它们的锻造记录点名各自纳入的上游工作流。[README.md](../../../../README.zh.md) 在面向采用者的目录中列出这些合并后的输入。

### 未决事项

#135 与 #144 均未留下尚未解决的映射。本提案继续保持开放，只用于让未来的单来源移植依据这条规则接受评审。

### 迁移边界

重命名会更新当前的技能目录、frontmatter、安装副本、package 与 bundle banner、测试、notices、文档及当前 Agent Note 引用。历史模型运行保留其实际运行的名称和 hash；它们不会成为重命名后技能的证据。description 或触发语料发生变化时，包括不重命名而只校正范围，都需要新的触发证据。

## Alternatives considered

**使用不带包前缀的上游原名。** 这能最大化字面识别度，但会与上游安装冲突，并使来源成为识别当前加载了哪个技能集合的唯一途径。

**为每个通用化移植选择新的意图型名称。** 这能描述目标包的表述框架，但会破坏可辨识的来源，并使新旧证据更难关联。

**保留当前名称，只在 README 记录映射。** 这避免迁移工作，但在加载技能前，可发现性取决于目录名称；放在别处的来源表无法修复语义词干。

## Acceptance criteria

- 每个单来源直接移植或通用化移植都命名为 `dsh-spec-<upstream-semantic-stem>`。
- 每个复合或合并范围的名称都有记录的上游集合和明确的命名原因。
- 当前引用一致采用提案名称；历史证据保留其记录时的名称和 hash。
- #135 与 #144 的重命名在不使用只改名称的别名的情况下，确定了已知的单来源映射。
- 实现本提案时，双语配对记录与语料门禁通过。

## Risks

- 当两个来源覆盖同一工作流的不同部分时，相似的上游词干仍可能产生有歧义的名称。
- 重命名会使旧触发证据失效，并可能要求为安装过旧名称的采用者安排分阶段迁移。
- 过于字面的命名规则可能保留对通用采用者没有意义的上游品牌；语义词干判断只允许确实合并的范围记录例外。
- 可辨认的语义词干仍须通过标题、description 和指令表明其受限范围。
