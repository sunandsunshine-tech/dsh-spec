# Agent Note: 规范的 source 指向能读到它理由的地方

Status: proposed

[English](2026-10-09-a-norm-source-names-where-its-rationale-can-be-read.md) | 中文

## Problem

`norms.json` 为每条规范记录一个 `source`，而集合把它当**本仓库内的路径**读取：`skills/dsh-spec-manager/scripts/norms.ts` 里的 `recordUrlOf` 把它拼到 `https://github.com/<repo>/blob/<ref>/` 之后，而它接受的校验只有"非空字符串"这一条。今天每一条的值都是仓库相对路径，所以这个字段从没被迫表达别的东西。它的读者只需要一个事实——这条规范的理由能在哪里读到——而那个地方并不总在本仓库里：一条采纳自别的项目做法、某个 issue 或某篇文章的规范，无处可记。把这样的 URL 填进字段，得到的是一个把 URL 粘进路径的 blob 链接；单独把 URL 挑出来放行，又占掉了本地承载者的位置，于是记录再也指不到"采纳它的那条笔记"。而且没有任何检查确认仓库内的路径存在，写错的链接就是一个没人会发现的 404。

## Proposal

一个字段，两种拼写。仓库相对路径按**管理器自己安装时的那个仓库与 ref**（也就是项目持有的那版修订）渲染；绝对的 `https://` URL 原样使用。路径形态必须存在，URL 形态必须是合法的 `https`。门禁只读这个字段、绝不去抓取，因为一个会联网的套件不是本仓库会跑的套件。外部来源是证据而不是权威：它连同阅读日期一起被引用在采纳这条规范的笔记里，这正是 `evidence.external-is-data` 对任何带了来源的主张已经提出的要求。

## Alternatives considered

**拆成两个字段：`owner` 记本地承载者，`origin` 记外部出处。** 它落败，因为这个字段本来只表达一件事——理由能在哪里读到——而两种拼写就是这一件事在它可能所在的两处。第二个字段会容许一条两个都填不上的记录，也会诱导读者把"谁拥有这条规则"和"这条规则从哪来"当成两件事，而一条规范的采纳让它们成为同一件。

**一律用 URL，让目录为每条规范带一个完整链接。** 它落败，因为本地那一类会把某个修订固化进目录：要么链接指向的 ref 不是项目安装的那版，要么每次发布都得重写全部链接，于是目录成了 ref 的第二个家，而 `owner.ssot` 要求 ref 只有一个家。

**维持现状、不加校验。** 它落败，因为它放行的失败是静默的：不存在的路径会渲染成一个看起来合理的链接，跟过去的人什么也学不到。这项检查的代价是一次仓库遍历，且不引入任何网络访问。

## Acceptance criteria

- source 是仓库相对路径的记录，按管理器安装时的仓库与 ref 渲染。
- source 是 `https` URL 的记录，原样渲染成该 URL。
- 路径形态指向不存在的目标时被具名拒绝；URL 形态不是合法 `https` 时被具名拒绝。
- 目录今天携带的记录保持有效，无需重写。
- 没有任何门禁因此获得网络访问。

## Risks

外部链接不是本仓库能控制的文本：页面会移动、改写、消失，所以记录记的是"位置 + 阅读日期"，而不把它当成稳定的东西。校验读的是工作树，因而按构造保持离线，但它确实多了一次遍历，不能被误当成抓取。项目里已渲染的规范文件不受影响——它旁边那份记录哈希的是每条规范的正文，不是 source——所以这次改动只到目录与它的列举输出，不到项目状态；这也正是它不需要迁移的原因。
