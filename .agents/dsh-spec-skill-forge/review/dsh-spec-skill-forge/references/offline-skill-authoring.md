# 离线回退：Agent Skills 创作义务

仅在在线 Agent Skills 指南无法访问时阅读本文。它是一份提炼过的回退，不是第二权威：在线页面只要可读，就以在线页面为准。于 2026-10-26 从以下来源提炼：

- `https://agentskills.io/specification`
- `https://agentskills.io/skill-creation/best-practices`
- `https://agentskills.io/skill-creation/optimizing-descriptions`
- `https://agentskills.io/skill-creation/using-scripts`
- `https://agentskills.io/skill-creation/evaluating-skills`

规范中的 `must` 规则是强制的；其余页面给出的是建议。一条规则保留其来源的效力。

## 1. 规范——格式规则

- 技能是一个至少包含 `SKILL.md` 的目录；`scripts/`、`references/`、`assets/` 可选，其他任何文件或目录都允许存在。
- `SKILL.md` 由 YAML frontmatter 后接 Markdown 组成。必填字段：`name`（1–64 个字符，只含小写字母、数字和连字符，首尾不得有连字符，不得出现连续连字符，并与目录名一致）和 `description`（1–1024 个字符，非空，说明技能做什么、何时使用）。
- 可选字段：`license`（许可证名称或随附的许可证文件）；`compatibility`（1–500 个字符，仅当技能有特定环境要求时使用）；`metadata`（字符串键到字符串值的映射）；`allowed-tools`（以空格分隔的字符串，实验性）。
- Markdown 正文没有格式限制；推荐的章节是分步说明、输入/输出示例和常见边界情形。把细节内容移入被引用的文件。
- 引用其他文件时，使用从技能根目录出发的相对路径，深度一层。不要构建深层引用链。
- 渐进式披露：metadata（约 100 tokens）始终加载；`SKILL.md` 正文在技能激活时加载（建议 `<5000 tokens`、`<500 lines`）；资源按需加载。
- 规范点名 `skills-ref validate` 来检查 frontmatter 与命名。

## 2. 最佳实践——内容义务

- 从真实专业经验出发：从实操任务、内部文档、API 规范、评审意见、版本历史和真实失败案例中提炼或综合。不要只凭模型的通用知识生成技能。
- 用真实执行来打磨：在真实任务上运行技能，阅读执行轨迹而不只看最终输出，并把结果反馈回去。浪费的步骤通常意味着指令含糊、指令不适用，或者选项太多而没有默认值。
- 明智地使用上下文：补上 agent 不知道的内容（项目约定、领域流程、不显眼的边界情形、具体的工具与 API），省略它已经知道的。对每一段自问：没有它，agent 会做错吗？答案为否就删掉。
- 设计内聚的单元：不要窄到一个任务需要加载多个技能，也不要宽到激活变得不精确。
- 细节保持适度：带一个可运行示例的简明分步指导，胜过面面俱到的文档。除非任务脆弱，把大多数边界情形留给 agent 判断。
- 用渐进式披露组织大型技能：核心指令留在 `SKILL.md`；细节移入 `references/`，并明确告诉 agent 何时读哪个文件（“API 返回非 200 状态码时读 references/api-errors.md”，而不是“详见 references/”）。
- 按脆弱程度校准控制力度：多种做法都可行时给出自由并解释原因；脆弱操作、一致性要求和固定顺序则明确规定。
- 给默认值，不给菜单：选一个默认值，简要提及备选。
- 重流程，轻声明：教如何着手一类问题；输出模板和约束这类具体细节仍然有价值。
- 模式：为环境特定的修正写 gotchas 章节；输出格式模板；多步工作流的检查清单；核验循环（执行、核验、修复、重复）；批量或破坏性操作采用先计划、再核验、后执行；当 agent 反复重造同一逻辑时，打包可复用的脚本。

## 3. Description——触发义务

- description 承担全部触发责任：它说明技能做什么、何时使用。
- 用祈使句、面向意图、略带推动性的写法：“Use this skill when…”，列出适用语境，包括用户没有直接点明领域的情形，并保持简洁（硬上限 1024 个字符）。
- 触发评估：约 20 条真实查询，其中 8–10 条应触发、8–10 条不应触发。变化措辞、明确程度、细节和复杂度；包含文件路径、个人语境和口语化表达。最有价值的负例是共享关键词、但实际需要别的东西的近似查询。
- 在安装技能的状态下运行每条查询，观察技能是否被调用；每条查询运行 3 次并计算触发率（0.5 是合理阈值，应触发项要求高于它，不应触发项要求低于它）。
- 按约 60% 训练集、40% 验证集划分。只有训练集的失败指导修改；按验证集通过率挑选最佳迭代，以避免过拟合。选定后，再用 5–10 条全新查询做最后的合理性检查。
- 通过泛化来修改，而不是把失败查询里的关键词加进去；卡住时，改 description 的结构。迭代过程中把字符数保持在 1024 以下。

## 4. 脚本——接口与面向 agent 的设计

- 简单工具调用优先用现成的一次性命令（固定版本、说明前提条件）；命令变复杂或同一逻辑被反复重造时，把测试过的脚本打包进 `scripts/`。
- 在 `SKILL.md` 中列出可用脚本，并用相对于技能根目录的路径运行它们。
- 让打包脚本自包含，或清楚记录依赖；优先内联依赖声明，做到无需单独的安装步骤。
- 面向 agent 的要求：不得有交互式提示（硬性要求——agent 运行在非交互 shell 中）；用 `--help` 提供用法说明；错误信息要可操作（出了什么问题、期望什么、可以试什么）；结构化数据写到 stdout，诊断信息写到 stderr；重复运行要安全（幂等）；含糊的输入要用清晰的错误拒绝，并尽量使用封闭集合；破坏性或带状态的操作支持 `--dry-run`；使用互不相同且有文档说明的退出码；选择安全的默认值；让输出规模可预期（摘要、上限，或显式的 `--output`）。

## 5. 评估产出质量——测试与迭代

- 一条测试用例由真实的提示词、人类可读的期望输出和可选的输入文件组成；把测试用例存放在技能目录下的 `evals/evals.json`。从 2–3 条用例开始，变化措辞和细节，并至少包含一条边界或畸形输入的用例。
- 每条用例运行两次：一次带技能，一次不带（改进现有技能时，对比上一版本的快照），都在干净的上下文中运行。按迭代和用例保存输出。
- 记录每次运行的耗时和 token 用量，让基准能显示技能付出多少、换来多少。
- 看过第一批输出之后才写断言。断言必须客观可核验且具体（“输出文件是合法 JSON”“图表恰好显示 3 个月”），不能含糊（“输出很好”），也不能脆弱（精确到措辞，正确的替代写法也会被判错）。断言必须客观可核验；主观质量交给人工评审。
- 给每条断言判 PASS 或 FAIL，并给出引用或指向输出的具体证据；可机械检查的断言使用核验脚本。
- 汇总成基准：每种配置的通过率、耗时和 token，多次运行时的标准差，以及差值。
- 分析模式：删掉两种配置下都始终通过的断言，调查始终失败的断言，研究带技能通过、不带技能失败的断言，运行不一致时收紧含糊的指令，并阅读执行记录，找出耗时或 token 离群的情况。
- 由人把产出与评分放在一起评审，并按用例记录可操作的反馈。
- 迭代：把失败的断言、人工反馈和执行轨迹交给提出改进的模型；评审并应用；在新一轮迭代中重跑全部用例；再次评分、汇总和评审。满意、反馈持续为空，或结果不再改善时停止。
- 改进时，从反馈中泛化，而不是逐个修补例子；让技能保持精简；解释指令背后的原因；把重复的辅助逻辑打包进 `scripts/`。
