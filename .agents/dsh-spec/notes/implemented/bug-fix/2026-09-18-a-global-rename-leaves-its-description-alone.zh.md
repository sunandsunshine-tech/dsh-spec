# Agent Note: 全局改名不动描述这次改名的那句话

Status: implemented

[English](2026-09-18-a-global-rename-leaves-its-description-alone.md) | 中文

## 问题

一次协同改名在整个仓库里把一个名字替换成另一个，这样就不会落下半改名的状态。替换过程没有「提及」与「使用」之分：记录这次改名的那份文件，其正文本身就在描述这次改名，其中旧名出现两次，两处都被替换了。于是这份文件说某个名字变成了它自己，又说这一步淘汰了它刚刚引入的那个名字。

每道门禁都是绿的。门禁读的是结构——标题、链接、类文件夹、字数、标记配对——而一个各名词彼此不再一致的段落，在上述每一项度量下都形态良好。这份文件之所以被修好，只是因为有人为了无关的编辑读了它，而那不是检查。

## 决策

**协同改名在替换之后写它自己的描述，而不是之前；或者豁免那份描述改名的文件。** 在替换必须全局进行的地方，记录这次变更的文件最后编辑，并在之后通读一遍。

**描述一次改名的文件靠阅读来验证。** 这里没有门禁判断一句话是否表达了它所说的意思，因此阅读就是那道检查；而一次改名类改动要在评审说明里点名那份描述改名的文件。

## 考虑过的替代方案

**只对代码运行替换，散文手工编辑。** 代码里没有「提及」，因此在那里的替换按构造就是安全的。它输掉是因为关于某个名字的散文大多是正确的「使用」，手工编辑每一处所费的注意力超过通读一份文件。

**对一切运行替换，再用 grep 找矛盾。** 自动化且完整。它输掉是因为矛盾是语义上的：没有任何模式能表达「这句话和它后面那句不再一致」，而 grep 需要具备的正是替换过程所缺的那种理解。

**加一道通读散文、检查自洽的门禁。** 这是唯一可能抓到它的检查。它输掉是因为这样的门禁需要一个关于主题的模型，而这正是本集合拒绝用脚本来解决的推理记录问题；它要替代的那次通读比这道门禁更便宜。

## 后果

一次协同改名多花一遍通读描述它的文件的时间，而最容易被机械编辑破坏的文件，恰恰是这次变更为了让评审可行而写下的那份。

残余风险没有变化，并且属于评审：一次破坏散文的替换仍然会让每道门禁保持绿色，这里没有任何东西会指出这一点。
