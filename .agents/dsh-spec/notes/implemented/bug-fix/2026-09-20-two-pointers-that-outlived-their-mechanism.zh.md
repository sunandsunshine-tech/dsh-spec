# Agent Note: 两个指针活得比它们的机制更久

Status: implemented

[English](2026-09-20-two-pointers-that-outlived-their-mechanism.md) | 中文

## 问题

这套机制自己的文档指向了本仓库已经不再拥有的东西。`.agents/dsh-spec/notes/README.md` 告诉读者 slop 检查清单在「文档标准 `docs/AGENTS.md`」里，`.agents/dsh-spec/notes/archived/AGENTS.md` 则告诉读者 `{gate-dir}` 是「账本中 `notes-gates` 的值」。文档标准和账本都在本次会话中被删除，因此这两句话都把读者送进死路——而且是在治理决策记录的约定内部，那是最不该留下失效指针的地方。

另有一处：归档门禁的封条其实从未被读到。它把仓库根目录算成笔记根目录之上两级，这在笔记位于 `.agents/notes/` 时是对的，而在笔记迁到 `.agents/dsh-spec/notes/` 之后少了一级。git 是通过向上逐级查找来找到仓库的，因此以 `<repo>/.agents` 为工作目录时仍然位于仓库之内；缺陷在于 pathspec（路径规格）是相对于该工作目录的——`git ls-tree <ref> -- .agents/dsh-spec/notes/archived/manifest.json`——于是从 `<repo>/.agents` 出发，它索要的路径是 `<repo>/.agents/.agents/dsh-spec/notes/archived/manifest.json`，而这个路径并不存在。

`<repo>/.agents` + pathspec `.agents/dsh-spec/notes/archived/manifest.json` → `.agents/.agents/…`

git 回答的是「该树中没有这个路径」；读取结果为空，代码又把空结果当成「还没有封条」。门禁随后拿工作区清单与它自己比较：抹掉封条并改写清单——而这正是已提交的封条所要禁止的做法——会报告归档干净。单独丢掉一个产物仍会触发三文件组和逐清单检查，因此盲区比看上去更窄，但仅追加的保证已经没了。

## 决策

**这两个指针改为指向确实存在的东西。** slop 检查清单被描述为本集合不再以页面形式提供的内容，归档说明则点名集合固定的引擎目录 `.agents/skills/dsh-spec-manager/scripts` 作为门禁所在之处。**安装这两句话的模板在同一变更中被同样修正**，因此新项目不会再收到坏掉的形式。

**归档门禁向上三级到达仓库根目录，并读取封条。** 笔记根目录位于仓库根目录之下三级，即 `.agents/dsh-spec/notes`，这段上溯正是按这个深度写的；现在读取已提交的清单会返回内容，因此已提交的封条点名、而工作区不再记录的产物会被报告为缺失的已封存条目，而不是被报告为归档干净。

## 考虑过的替代方案

**保留这两个指针，让读者自己去撞死路。** 不必改动，而且跟随那句话的读者会得知该文档已不存在。它输掉是因为这份约定*就是*这套机制：跟不下去的读者会不再信任它，而代价落在下一个会话，不落在这一次。

**保留指针，但标注为历史。** 对现状是诚实的，也保住了原句的形态。它输掉是因为被删掉的那些文档不是本项目可以引用的历史，它们已经没了；一句「这里以前有文档」是更慢的死路。

**干脆去掉 git 读取，改为信任工作区清单，以此修好封条。** 少一个活动部件，而且清单就在磁盘上。它输掉是因为已提交的封条才是让归档仅追加的东西，而读工作区会让一次编辑蒙混过关。

## 本次变更所需的验证

本次变更需要聚合检查通过：`run.ts --all --root .`，其中也包括在 `.agents/skills/` 下的**安装副本**上运行，那才是调度器实际执行的副本。

还需要在一个临时仓库中做探针，分两部分：一个被封存后又被删除的产物必须让门禁失败；而真正把这处修复单独隔离出来的是另一种情形——已提交的封条点名的清单条目，工作区不再记录它，此时必须报告为缺失的已封存条目，而在修复之前，被改写的清单会报告归档干净。

## 后果

归档门禁的判定现在依赖一份它真正读取的已提交清单，因此封条的含义就是它字面所说的。笔记根目录是一条同时被两套机制读取的路径——门禁运行 git 时所在的工作目录，以及相对于它解析的 pathspec——而迁到 `.agents/dsh-spec/notes/` 时只在其中一套里改了这条路径，另一套仍按旧深度假设，这与本仓库自己那条「路径必须从它的所有者推导」的规则属于同一类。这次读取花了一次探针才确定下来：三文件组检查和逐清单检查仍然能抓到单独被丢掉的产物，因此只有被抹掉或被改写的封条才能把这处损失单独隔离出来。

被修正的那两句话陈述的是事实而不是引用，因此再删掉一个页面时不会有东西腐烂。

这次找出两处的审计本身才是值得带走的教训：删掉一套机制之后，去 grep 提到它的机制文档——不留下悬空引用的删除是例外，而不是常规。
