# Agent Note: 四个机制，而非十二个

Status: implemented

[English](2026-09-18-four-mechanisms-instead-of-twelve.md) | 中文

## 问题

本集合的机制已经增殖到一个人无法整体把握：一套带目标值、上限和棘轮的文档分层系统；十五道门禁；一个调度器、一份 manifest 和一份逐文件哈希的发布记录；一份十三键的台账；每条笔记的三文件配对；事后复盘；一套图。维护者报告说他再也看不到设计的整体，而这妨碍他决策。这件事本身就是缺陷，而不只是关于缺陷的报告：没人能在脑中装下的机制会被绕过，而被绕过的机制仍然被算作覆盖。

有两个原因需要分开陈述。大部分重量是本仓库自己发明的机器，而不是它借来的纪律：dsh 把门禁放在项目里并由 CI 运行，而本集合把通用门禁投递到别的项目，因此需要调度器和 manifest 来完成投递。另外，本仓库一直处在自举过程中——在同一段时间里既设计机制又在自己的源码上使用它——这是判断重量最差的样本，因为看得见的很大一部分是脚手架而不是结构。

## 决策

**本集合保留四个机制，其余全部砍掉。**

1. **笔记是唯一的决策记录。** 笔记树、分类、生命周期、文件内格式，以及守护这三者的三道门禁保留。事后复盘并入笔记的 `bug-fix` 类，不再作为第二个叙事层级存在。
2. **代码架构界定认知边界。** 一个模块目录就是一个限界上下文：它的 README 陈述契约，它的测试陈述行为，改动它不需要读别的任何东西。
3. **根目录只放一个索引。** `AGENTS.md` 承载命令与**路由**——哪类改动该读哪个目录。根 `README.md` 就是架构文档：有什么、什么拥有什么，以及检查它的那条命令。
4. **一条聚合检查。** 它的退出码就是全部检查。门禁清单**记录**在 `references/manifest.json` 中，调度器在运行任何东西之前，先把这份记录与它旁边的 `verify-*.ts` 文件对账——记录里有名称却没有对应文件，或存在记录未点名的文件，都会被报告并拒绝运行。它运行记录中的每一道门禁，并在某道门禁失败**或记录与引擎目录不一致**时失败，而正是这一点让任何门禁都不可选。[门禁是一个被记录的名称](2026-09-20-a-gate-is-a-recorded-name.zh.md)。

### 八个技能

| 技能 | 它拥有什么 |
|---|---|
| [`dsh-spec-manager`](../../../../../skills/dsh-spec-manager/SKILL.md) | 项目初始化、manifest、在单一钉定修订上的 install/update/uninstall、集合唯一的代码归属——每一道门禁与按记录的名称对照旁边引擎目录解析它的分发器——以及运行记录中每一道门禁的聚合检查 |
| [`dsh-archive-agent-notes`](../../../../../skills/dsh-archive-agent-notes/SKILL.md) | 笔记契约及其三道门禁：分类、文件内格式，以及冻结的归档区 |
| [`dsh-translate-docs`](../../../../../skills/dsh-translate-docs/SKILL.md) | 双语配对契约及其门禁，采用自声明配对规则 |
| [`dsh-pre-push-checks`](../../../../../skills/dsh-pre-push-checks/SKILL.md) | 一次外发 diff 必须携带哪些证据，从记录的门禁中选取 |
| [`dsh-prose-standard`](../../../../../skills/dsh-prose-standard/SKILL.md) | 哪些地方必须有散文，以及它要满足的写作标准 |
| [`dsh-trim-cot-leakage`](../../../../../skills/dsh-trim-cot-leakage/SKILL.md) | 读起来像泄漏的推理记录的散文 |
| [`dsh-code-review`](../../../../../skills/dsh-code-review/SKILL.md) | 一次改动接受的评审，对照根 `AGENTS.md` |
| [`dsh-find-simplifications`](../../../../../skills/dsh-find-simplifications/SKILL.md) | 死代码、重复、投机性和过度建造的表面 |

**四个技能离开**，各自因为其参数化的机制已消失，或因为该能力属于别处：

| 被移除的技能 | 原因 |
|---|---|
| `dsh-doc` | 它的主题**就是**本次决策要删除的文档机制；分层表、预算策略以及 `verify-doc-*`、`verify-readme-shape` 门禁随它一起离开，而 `verify-md-links`、`verify-md-link-syntax` 存留在 `dsh-prose-standard`。**维护者基于这一理由确认了删除：一个主题就是被删机制本身的技能，已无物可拥有。** |
| `dsh-ci-test-reliability` | 它的参数来自 `test-lanes` 键，而该键记录的是 `none`：本仓库没有 CI、没有构建步骤、也没有测试运行器，因此这个技能在这里不描述任何工作 |
| `dsh-speed-up-perf` | `perf-baseline` 键记录这里没有任何被测量的东西：交付物是按需运行的 Markdown 和无依赖 TypeScript |
| `dsh-merging-stacked-prs` | 堆叠拉取请求是宿主平台的能力，不是仓库纪律，该能力已由 `gh` 技能承接 |

**「八个」是一项决定，不是剩下的部分。** 每个留下的技能都保留其名称与触发描述，因为每一个仍然拥有一个独立的主题；上面四个各自拥有的机制正是本次决策移除的。

### 集合只有一个代码归属

**每一道门禁都住在 `dsh-spec-manager/scripts/`，其余技能不带任何代码。** 过去各自携带门禁的三个技能——`dsh-archive-agent-notes`、`dsh-prose-standard` 和 `dsh-translate-docs`——只保留 `SKILL.md` 与 `references/`，它们的脚本移进了 manager，除这次移动本身要求的 import 说明符之外没有任何改动。如今一个目录持有每一道门禁、按记录的名称解析门禁的分发器，以及它们共同导入的模块；`references/manifest.json` 也相应缩小：它只决定要安装哪些技能、钉定哪个修订，以及被记录的门禁名称清单，别的什么都不决定。它不再把门禁映射到归属者，因为只有一个代码归属时，一道门禁只有一种可能的归属。

**这是用每个技能的自包含，换取一处可改动的地方。** 这笔交换是有意的。对 manager 的依赖早已很强——每道门禁都导入它的仓库遍历器、笔记根、i18n 范围与 Markdown 解析器，运行它们的分发器也一直在它的目录里——因此自包含只是表面现象：一个技能无法被单独阅读、运行或修复，而目录布局仍暗示它可以，于是每新增一道门禁，都要为这份表象多维护一条需要推理的路径。让出去的是「技能目录可以从集合中单独拎出」这一主张。**前提是整个集合一起安装：单独安装某一个技能不受支持。** 项目通过 manager 在同一个钉定修订上取走整份 manifest，而一个脱离集合的技能失去的是它的检查，而不是保留它们。

**门禁的缺陷就是集合的缺陷。** 引擎目录不是 manager 自己的工作流，门禁的缺陷属于该门禁的主题，而不属于项目初始化；manager 的 `SKILL.md` 与 README 在读者遇到这个目录的地方就这样写明。

**少了三个机制，而它们持有的事实都有已存在的归属。** 台账连同创建它的模板、每道门禁导入的读取模块，以及报告其未决问题的门禁一并删除；与文件系统并存的第二个键值存储，就是同一事实的第二个存放处。下表点名台账回答过的每一个问题，以及它现在在哪里被回答：

| 台账问题 | 它现在在哪里被回答 |
|---|---|
| `notes` | 固定路径 `.agents/dsh-spec/notes`，来自 `notes-root.ts` 拥有的那一个字面量 |
| `notes-gates` | 固定路径本身：上面的笔记树，以及集合唯一的代码归属 `.agents/skills/dsh-spec-manager/scripts/`——每一道门禁都待在按名称寻址它的分发器旁边 |
| `i18n-scope` | **自声明**：一个 `.md` 只要有 `.zh.md` 兄弟文件就是一个配对，且它的 `.i18n.yaml` sidecar 必须匹配。文件的存在即是声明，因此配对门禁不读任何键 |
| `quality-gates` | manifest 记录门禁清单、与引擎目录对账，即 `references/manifest.json`，加上聚合检查 `dsh-spec.ts check --all` |
| `skill-refresh` | manager 的 [`manager-lifecycle.md`](../../../../../skills/dsh-spec-manager/references/manager-lifecycle.md)，命令原样写出 |
| `code-review` | 根 [`AGENTS.md`](../../../../../AGENTS.md) 中的常驻条目 |
| `_mode`、`_proposals` | 随「有人值守/无人值守」一起删除：初始化永远是先扫描再询问，这两个文件都不再写入 |
| `test-lanes`、`perf-baseline`、`doc-tiers`、`stacked-prs` | 随各自参数化的技能或机制一起删除 |

### 发布记录被删除

`references/release.json` 已消失，manager 的 `release` 子命令随之而去。它记录一个修订、每个层文件的 SHA-256 和每道门禁的 SHA-256，而这些事实各自都已有归属：`gh skill install` 把它解析出的 ref 作为 `metadata.github-ref` 写进每个已安装的 `SKILL.md`，因此已安装的修订可以从将要运行的那个文件里读到；而 `references/manifest.json` 记录门禁清单，供分发器与引擎目录对账。除此之外不再记录任何东西，因此也不会有别的东西变陈旧。

两次假绿是删除它的原因，而它们是同一个缺陷的两次出现。一次从源分发器调用的释放，把记录写在了 `skills/` 旁边，而已安装的分发器读的是自己那份；更早的一次记录了四道门禁，而已安装的集合持有七道。两者打印的绿，都是根据该命令所寻址文件之外的文件算出来的。这次改动留下的规则就是验收标准：**任何命令都不得在它运行的东西与工作树持有的东西不一致时报绿。**

### 文档机制被删除

分层表及其目标值、上限和棘轮；放置、分层、组合、生成区域、预算和 README 形态检查；组合图；作为受维护产物的图集；以及 `docs/AGENTS.md` 标准，全部删除，`dsh-doc` 技能随之离开。文档门禁确实抓到过真实缺陷，对此诚实的解读是：它们抓到的是本仓库刚刚发明、并一直在改动的机制里的缺陷，而不是「一个项目的文档需要分层系统才正确」。

**`docs/` 作为一个不受管理的目录存活下来。** 留在那里的是人写给人读的东西：没有分层、没有预算、没有门禁，也没有属于它自己的指令文件。那里不要求存在任何东西，那里的任何东西也不被检查。

**`docs/terminology.md` 保留其消费者，而它的路径只有一个归属。** 翻译简报仍然把改动过的片段与它的行做匹配，而正是这种匹配让简报值得生成。这个路径是 `i18n-scope.ts` 里的一个字面量，由简报生成器导入，因此术语表只在它已定的归属被读取，而本集合不再以模板形式附带它的一份副本。

**初始化器写 agent 指令与笔记树，不写文档树。** 它过去创建的层级目录、它过去安装的 `docs-AGENTS.md` 模板，以及 `AGENTS.md.template` 里那句话，都随机制一起删除。造成差别的那条规则记录在[初始化器不覆盖不是它写入的文件](../bug-fix/2026-09-18-never-overwrite-a-file-the-initializer-did-not-create.zh.md)里：初始化器不覆盖任何不是它写入的内容，而新增在一组既有写入旁边的写入从它们那里继承这条规则。

**没有机械支撑的规则不会成立。** 本次决策移除的分层表本身就是证据：源项目的表与它的目录树脱节——有页面无人认领，两个预算数字与执行它们的 manifest 相互矛盾——而它有着与本仓库相同的散文标准和评审注意力。因此，删除散文门禁是有意把它们抓到的东西交给评审，下面「后果」一节说明评审如今承担什么。

### 被归并的笔记

**十三篇已实现笔记被归并进本篇并删除。** 每一篇都连同它贡献的理据一并列出，以确保没有独有内容丢失：

| 被归并的笔记 | 本篇从它保留了什么 |
|---|---|
| `两个预算数字与棘轮` | 同一事实的两个数字必须同处一个归属，否则就会漂移；上限是一个独立的已记录数字，绝不跟随它所约束的文档；对 dsh 尚未交付的提案的有意偏离 |
| `选取一次 diff 需要的证据` | 证据由 diff 选择；门禁按名称而非按路径寻址；被遗忘的门禁与不适用的门禁看起来完全一样；这张映射表随 manifest 一起老化 |
| `检查文档所处的位置` | 语料必须对检查而言是完备的：没有规则认领的文档，正是局部检查看不见的失败，因此存留的门禁在空语料上失败，并报告它们排除了什么 |
| `复制文档机制，而不是它的模板` | 机制与模板可以分离，而只有机制可迁移；被描述却未被执行的树会腐化，源项目的分层表已经证明了这一点 |
| `初始化 docs 树，以及上限的唯一归属` | 在某个文件里记录、却在另一个文件里执行的数字，正是台账本要防止的漂移；用抽象键来命名文档，会给同一事实增加第三个归属 |
| `检查地图，以及生成器拥有的区域` | 一条没有任何东西与目录树比对的记录会无声地不再为真，因此根 `README.md` 保持短到可以靠阅读它来维持真实；一道检查用它自己的话陈述覆盖缺口，而不是暗示已有覆盖 |
| `每个工作流一个技能，外加一个 manager` | 每个工作流一个目录条目，让每一段触发描述都保持有效，而不是藏在可能永不加载的条目后面路由；安装按 manifest 中的显式名称在单一钉定修订上进行，因为发现是仓库范围的；由 manager 拥有安装、更新与移除 |
| `从台账配置门禁` | 门禁的范围是一项决定：文档不会失败，因此一条带理由的固定路径胜过没人复读的可配置字面量；门禁报告它跳过了什么，并按跳过它的规则分组 |
| `人类文档不是 agent 材料` | 写给人读的散文与写给 agent 读的散文遵循不同规则；把一套规则强加给另一种读者，会把有意为之的设计变成永久违规，而一个文件的读者是一项决定，不是 glob 猜出来的 |
| `读取 frontmatter 块` | 元数据对解析器是数据，对文本处理是散文；全语料编辑必须把围栏区域当作不透明单元，而它自身的教训记录在[批量编辑把 frontmatter 当作一个块，而不是一个段落](../bug-fix/2026-09-18-frontmatter-is-a-block-not-a-paragraph.zh.md)里 |
| `抽取其余工作流技能` | 一个技能在其主题具有一般性时被抽取，而不是在其代码具有一般性时；本集合自己的工作流技能存在，是因为没有归属者的工作流会变成没人负责的事 |
| `安装术语表` | 模板的行是示例，术语表的行是决定；一张满是另一个项目术语的表，会教译者去够本项从不书写的术语；每个主题一张查阅表，就是一份有单一归属的文档 |
| `恢复模块契约的类型系统` | 模块 README 是读者无需被指引就会读到的唯一文档，因此存留的架构机制要求每个模块目录都有一个；摘要上限与整体上限回答的是不同问题，而类型推导与承载它的模板可以分离 |

**另有四篇已实现笔记保留其结论但失去其中一个条款**，因此它们保持活跃并被交叉链接，而不是被归并：`放弃工作记录`（台账不再是决策所在的三个地方之一）、`在门禁出厂处引用它们`（引用模型保留，`notes-gates` 键不保留）、`在本仓库上运行初始化器` 和 `扫描范围、内联理据与包 README`（两篇都描述了一个会创建台账的初始化器）。

### 边界条件，而不只是原则

「代码就是事实」在契约存在于代码与测试中的地方成立——库、应用、命令行工具。有三类事实不在那里：**为什么**是现在这样，那是笔记；**公开接口承诺了什么**，那是对导出符号的检查，本仓库不需要而编译型项目需要；以及**如何操作它**，那是项目自己拥有的运维手册。采纳本模式的项目要显式决定这三类，而不是假定该原则已经覆盖它们。

## 考虑过的替代方案

**保持现状。** 最小的改动是不改动，而清单里的每个机制都能工作。它输给催生本决策的证据：现状正是维护者无法决策的状态，因此它的代价是实测出来的，而不是预测出来的。

**只砍自造的机器，保留文档机制。** 这保住了读者最可能想要的那部分，只移除本仓库为自己建造的东西。它输掉是因为文档机制是代码已经拥有的事实中最大的一份第二副本：分层表、放置检查和预算行都只是在重述文件树与散文已经说过的内容。

**回到 dsh 的确切形态：门禁放在项目里、由 CI 运行。** 这是模式被抽取出来的形态，不需要调度器、manifest 和发布记录。它输掉是因为本集合要把通用门禁投递到其他项目，只要这一点不变就无法采纳——不过如果本集合有朝一日变成某一个项目自己的工具，那就是终点。

**保留台账，只删掉没人读的键。** 这是移除死重的最小切割，并且为项目事实保留一个归属。它输掉是因为存留的键都已经有归属——一条路径、manifest、一份参考文档、常驻命令——台账会变成别处已陈述事实的副本，而这正是分层表所展示的失败。

**保留记录，但写在分发器读取的位置。** 记录确实抓到过被人编辑过的层，而从已安装副本运行的释放写的正是已安装分发器所读的那个文件。它输掉是因为安装器已经把解析出的 ref 写进每个已安装的 `SKILL.md`：同一事实的第二个文件只可能与将要运行的那个文件不一致，而一份记录正是这样为分发器从未执行的目录树报出了绿。

**每份文档只留一个预算数字，如同 dsh 出厂那样。** 这是对分层系统最小的改动，而且它保留的数字正是门禁执行的那个。它输掉是因为它重新制造了这个机制本要检测的漂移：同一事实的两个数字，记录在不同文件里，彼此不一致却没有信号。

**把源项目的分层作为分类法整份出厂。** 一张表，整份采纳，无需协商。它输掉是因为一个项目有哪些文档取决于它自己的布局与技术栈，而一张点名另一个项目目录的表，教采纳者去删行，而不是去决定自己的仓库需要什么。

**修好工具，保留分层词汇。** 放置、分层集合、组合与生成区域检查各自都抓到过真实缺陷，因此这套词汇本可以在门禁更少的情况下留下。它输掉是因为这套词汇本身就是那份第二副本：它用一张表重述文件树已经展示的内容，而为它存在的每一道检查，都只是在维持这份重述为真。

**保留组合图，只删图集。** 组合图是读者会坐下来通读一遍的那一页，而图集是另一项维护成本。它输掉是因为组合图与分层表把同一个问题回答了两次，而根 `README.md` 已经在读者本来就会打开的地方回答了它。

**只报告没有规则认领的文档，不让检查失败。** 一份警告清单更容易采纳，也从不阻塞改动。它输掉是因为没人必须据以行动的報告正是被替换掉的现状：源项目有散文说明页面该放在哪里，页面照样漂移。

**把术语表作为出厂模板保留。** 少一个文件，而模板已经带着规则和五行示例。它输掉是因为模板的行是示例：照它做的译者遵循的是本仓库的示例，而不是一项决定，而简报生成器需要一张位于它所读路径上的真实术语表。

**把模块契约类型放回模板。** 这些类型泛化得很干净，每个类型一份模板是具体的起点。它输掉的原因与这些类型随 `dsh-doc` 离开的原因相同：一个类型就是换个名字的文档分层，它要求的章节是对散文的形态检查，而存留的架构机制只要求模块 README 必须有的那一件事——它存在。

**为仍未解决的问题保留台账。** 初始化本可以记录它无法确定的事情，而不是报告它们。它输掉是因为一份未决问题清单是没有读者的第二份清单：初始化器在运行的那一刻报告它无法确定的事情，而一个必须长期存在的未答问题就是一篇笔记。

## 后果

**一份文档回答「有什么」。** 根 `README.md` 陈述各个表面、每个表面的归属、一次改动如何流动，以及如何刷新已安装集合；根 `AGENTS.md` 承载常驻命令并负责路由；manager 的 README 仍是本集合面向安装者本人的介绍。一个新人读这三份，加上被改动目录的 README。

**检查是一条命令，而记录决定它运行什么。** `dsh-spec.ts check --all --root .` 运行以整棵树为断言的那些检查——笔记分类、格式与归档门禁——而 `references/manifest.json` 一共记录六道门禁：这三道、配对门禁，以及检查链接目标与链接语法的两道 Markdown 门禁。调度器在启动时把这份记录与它旁边的 `verify-*.ts` 文件对账，两者不一致就拒绝运行，因此新增一道门禁意味着在同一次改动中既记录它的名称、又加入它的脚本，而记录在案的门禁一旦文件丢失，就会让这次运行失败，而不是从记录中消失。[动作是子命令](2026-09-21-actions-are-subcommands.zh.md)拥有这条命令本身的形状。

**已安装的修订从已安装文件里读取。** `status` 把 `gh` 注入已安装 `SKILL.md` 的 ref 与 manifest 的钉定值比较，而没有该块的 `SKILL.md` 会被点名报告为不是一次安装，而不是被当作一致。没有任何东西拿已安装目录树与一份「复制了什么」的清单比对，因此后续修订删掉的文件对 `status` 不可见——同时也是惰性的，因为门禁是通过已安装分发器与它自己的引擎目录对账的那些记录名称来寻址的。

**被删除门禁持有的覆盖，除存留的三道检查之外，如今由评审承担。** 文档长度、模块契约类型，以及被删除的 `.zh.md` 是否有意取消配对：评审承担这些，下面的风险逐一列举。链接目标、链接语法与 frontmatter 形态仍是机械检查，由 `dsh-prose-standard` 承担。

**清理已经完成，归档区保持为空。** 删除一篇被完全取代的已实现笔记属于归并，不属于归档：它的理据活在拥有该决策的笔记里，它的三文件被删除，而 `.agents/dsh-spec/notes/archived/` 下的冻结归档区仍然空无一物。

**根 `README.md` 只要没短到能靠读它来保持真实，就会腐烂。** 已经没有任何东西检查它；与目录树比对组合图的那道门禁随机制一起删除，而组合图自己的笔记记录了一条背后没有任何东西的记录为何会无声地不再为真。

**删掉某个 `.zh.md` 就能丢掉一个配对。** 自声明配对意味着纯英文文档是正当的，因此没有任何东西能区分「有意取消配对」与「丢失译文」；配对门禁报告什么没有声明配对，而由评审决定那是否出于本意。

**抓到 glob 塌缩的那道检查存留在 `dsh-prose-standard`。** `verify-md-links` 拒绝因 glob 塌缩而不再指向任何文件的链接目标，因此这类缺陷不依赖评审是否注意到。frontmatter 这一类后来退出了随包集合，因为[执行它的那道门禁在采用者项目中并无归属者](2026-09-21-frontmatter-has-no-owner-in-an-adopted-project.zh.md)；本仓库把自己的检查留在 `scripts/verify-skill-structure.ts` 里。记录这两起事件的 bug-fix 笔记仍是长存的记述。
