# Agent Note: 引用门禁所在地，而不是把它们释放出去

Status: implemented

[English](2026-09-18-reference-gates-instead-of-releasing-them.md) | 中文

## 问题

`init` 会把 Agent Note 门禁复制到 `.agents/dsh-spec/notes/scripts/`，于是每个采纳它的项目都持有一份自己的副本。由此产生两个失败，而本仓库两个都撞上了。

被释放出去的门禁没有更新通道。`init` 从不覆盖不是它创建的文件，而集合自身的更新器只作用于集合，因此在 `skills/` 里修好的门禁，在所有已经采纳它的项目里依然是坏的。记录它们位置的那条规则正是这么写的——"靠复制来刷新"——而这是一道没有任何门禁检查、也没有哪位协作者会记得的工序。

被释放出去的门禁还有两个归属者。没有任何东西说明集合那份和项目那份谁是权威，两者之间的漂移也是不可见的：已部署的笔记契约相对其模板已经陈旧，带着一条失效的门禁路径和被弄坏的链接，而没有任何检查覆盖它，因为每道门禁都以 `--root skills/dsh-doc` 运行。

## 决策

门禁**在它们发布的地方被引用**，绝不释放。`init` 不复制任何门禁；它记录自己运行所在的分发器路径，而初始化后的项目在其文档化的命令里点名该路径：

```sh
node .agents/skills/dsh-spec-manager/scripts/dsh-spec.ts verify-agent-note-format --root .
```

`.agents/dsh-spec/notes/` 保留项目自己拥有的东西——契约文档、生命周期与类别文件夹、笔记——并且不含任何代码。

### 一条路径，只记录一处

只有初始化器知道集合落在了哪里：安装目录是一个选择（`--dir`、项目级、用户级），所以模板无法陈述它，门禁也无法推导它。分发器路径在 init 时记录一次，每条命令都点名它，这就让路径只有一个归属者，而不必在每个模板里各猜一遍。

### 契约文档仍然释放

分界是**代码引用，文档释放**。`README.md`、`AGENTS.md`、`implemented/AGENTS.md` 和 `archived/AGENTS.md` 是项目自己的文本——它要填写其中的占位符、要指向自己的生命周期与类别集合——所以保留一份副本是正确的，覆盖它反而是破坏性的。门禁是代码：它们接受配置而不是编辑，所以副本只会变成一次分叉。

### 迁移是被描述的变更，而不是自动化的变更

未来某个会破坏笔记布局的版本——结构、长度、标题集合——要依照更新后的集合自身对新形态的描述来迁移。没有任何机制能升级已释放的契约文档，本决策也不新增这样一个机制。

## 曾考虑的替代方案

**继续释放门禁，另加一条刷新命令。** 一个 `--refresh` 覆盖已释放的门禁，用一个标志就能恢复更新通道。它落选是因为它重建了本仓库刚刚为已安装技能副本解决的问题：同一个文件的两份拷贝、用文档化的工序代替结构性的保证，以及为发现"刷新本应防止的漂移"而需要的第三道门禁。引用让第二份拷贝不可能存在，而不是被盯着。

**在模板里硬编码 `.agents/skills/scripts`。** 这是集合在本仓库中的位置，而且它不需要任何记录、也不需要替换。它落选是因为它只在这里成立：以用户级安装、或用了别的 `--dir`、或把集合 vendored 到别处的项目，读到的会是一个不存在的路径，而文件里没有任何东西说明真实路径从何而来。

**把门禁作为项目依赖的已安装包发布。** 一份 manifest、一个 lockfile 和一段版本范围会给门禁一个真正的依赖图。它落选是因为本集合的既定属性就是不需要 `package.json`、不需要 `node_modules`；引入依赖等于用一条引用换取采纳项目可能并不具备的工具链。

## 后果

在集合里修好的门禁，现在会到达每一个更新它的项目——这正是被释放的副本无法提供的属性。

门禁不再能在集合缺席的情况下运行。在本仓库中已安装的副本是纳入跟踪的，所以一次普通检出就带有它们；以用户级安装的项目则必须先安装集合，其检查才能运行，而失败模式是文件缺失而非文件陈旧——更响，所以这是更划算的取舍。

记录下来的路径是采纳项目唯一可能弄错的东西，而只有运行一条命令才会暴露它：没有任何东西校验一条模板无法知道的路径。初始化器打印的命令里路径已经解析好，因此项目复制到的是一条能跑的命令，而不是往令牌里做替换。

已释放的契约文档仍然没有升级通道，这与本决策之前一样。这个缺口现在是被明确写出的，而不是藏在一份被释放的门禁副本背后——那份副本让整棵树看起来是被维护着的。

[四个机制，而非十二个](2026-09-18-four-mechanisms-instead-of-twelve.zh.md)保留了本决策，并删掉了把该路径记录为配置键的那个条款：引用模型保留，持有该键的台账不保留。
