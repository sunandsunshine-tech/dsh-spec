# Agent Note: 在本仓库上运行初始化器

Status: implemented

[English](2026-09-18-run-the-initializer-on-this-repository.md) | 中文

## 问题

本仓库是手写出来的，而不是初始化出来的：`AGENTS.md` 用自己的措辞承载了关于决策记录的规则，却从未带有 `dsh-spec:agent-notes` 标记，因此重跑初始化器会把一条该文件已经陈述过的规则再追加一遍。

初始化器还报告了十二个子树指令文件，全部位于 `submodules/dsh/` 内。它们属于那份固定的基线，本仓库不得修改其内容；把它们当作本项目的子树指令报告，会把维护者引向不属于他们的文件。

## 决策

初始化器现在**在嵌套仓库处停止**：含有 `.git` 的目录属于另一个归属者，因此其指令文件既不被报告也不被计数。

在这里运行它只写了一样东西——追加到 `AGENTS.md` 的带标记 Agent Note 章节——而 `## Conventions` 中因此重复的那条项目符号在同一次变更中被删除，于是这条规则只有一个归属。重跑是无操作：标记会抑制追加。

被注入的章节本身也已修正。它此前告诉项目从 `.agents/dsh-spec/notes/scripts/` 运行门禁——那是一个不再接收门禁的目录；现在它指向 `.agents/skills/` 下的分发器，而安装好的集合正是把按名称解析门禁的那条命令放在那里。

`dsh-spec-init.md` 与 `SKILL.md` 带有同样的陈旧模型——门禁创建在笔记树下，以及三个并不存在的模板名。两者均已修正。

## 曾考虑的替代方案

**手工加上标记而不运行初始化器。** 手加一行就能让将来的重跑成为无操作，也能完全避免这次追加。它落选是因为标记正是初始化器为这种状态准备的机制，手工使用它会让章节文本无从与维护它的工具核对——而漂移正是本仓库一再发现的东西。

**保留重复的规则，让追加的文本一并存在。** 删掉手写的那条项目符号、只保留注入的章节，这是实际发生的做法；同时保留两者是被否决的替代方案，因为同一条规则的两处陈述会漂移，而手写的那份会是没人更新的副本。

**把十二个子模块指令文件写进报告，让读者自行忽略。** 诚实但无用：报告的存在是为了告诉维护者该读什么，而一份必须被忽略才能被正确阅读的清单，比没有清单更糟。

## 后果

初始化器在本仓库上的报告只有一行关于根文件和笔记树的内容——这就是本仓库实际拥有之事的全部真相。

它的扫描不再伸入任何嵌套仓库，这也意味着 vendored 了第二份检出的项目不会看到那份检出的指令。这正是意图：那些文件由拥有那个仓库的人在那个仓库里阅读。

初始化器工作流的第 5 步——调整已部署的 Agent Note 契约，它仍指向三份只存在于上游的决策记录——**未完成**。它需要维护者在"在这里写出等效记录"与"指向集合"之间做决定，而发明其中任何一个都会把没人写过的理由放进契约。它同时点名的那棵文档树已完全不属于初始化器的职责：[四个机制，而非十二个](2026-09-18-four-mechanisms-instead-of-twelve.zh.md)删除了该机制，因此 `docs/` 是一个不受管理的目录。
