# Agent Note: 门禁是一个被记录的名称

Status: implemented

[English](2026-09-20-a-gate-is-a-recorded-name.md) | 中文

## 问题

门禁清单曾同时存在于两个地方，而两者都没有说明对方做了什么。分发到每一个已初始化项目的 manifest 带有一个 `gates` 数组；分发器忽略它，转而拿名称到紧邻自己的 `verify-*.ts` 文件中解析，于是这个数组与引擎脱节，两边都没有任何信号。把该数组从 manifest 中移除，被理解为删除一份重复，而分发器的扫描成了「存在哪些门禁」的唯一陈述。

扫描回答的是与聚合检查所需不同的问题。它报告哪些文件存在，而不是哪些检查必须运行，因此一道已记录、却从引擎中删除的门禁仍会留在项目保有的任何清单里，而一个新脚本只要落进该目录就成了一道检查。此时一次绿色的 `--all` 意味着聚合检查运行了恰好在那里的那些文件。扫描还出过一次机械性失败，这正是如今需要对账的原因：它在运行途中把引擎目录的辅助模块当作门禁来执行，其中包括 `archived-agent-notes.ts` 和 `translation-pairing.ts`，因为扫描剥去了 `verify-` 前缀，而不是要求它。这些模块什么也不打印并以 0 退出，于是聚合检查把它们每一个都算作一道通过的门禁。为一个并非门禁的文件打印的绿色一行，正是本集合存在所要防止的失败。

## 决策

**门禁清单记录在 `references/manifest.json` 中，分发器拿记录与引擎目录对账。** `dsh-spec.ts` 读取它所在技能 `references/` 中的记录，并在解析或运行任何东西之前先比对两侧：一个已记录的名称在分发器旁边没有对应的 `verify-*.ts` 文件，以及一个记录没有点名的 `verify-*.ts` 文件。两侧都会按名称被报告，命令以非零退出。不匹配会被拒绝，而不是被跳过。

记录是唯一可运行的清单。`--all` 只运行被记录的名称，点名一道记录没有列出的门禁会被拒绝，而不是被运行。manifest 陈述仓库、钉定修订、要安装的技能，以及存在的门禁；引擎目录持有这些名称解析到的脚本，而这次对账是两者一致的唯一陈述。

记录与引擎目录这一对，正是让这种隐患无从发生的原因。当记录是聚合检查唯一会运行的清单时，引擎目录里的辅助模块就是惰性的：没有任何东西运行它，它的存在被报告为记录没有点名的文件，而不是被算作一道检查。当不匹配被拒绝时，一道失去自己文件的已记录门禁会在任何门禁执行之前中止整次运行。**扫描让假绿变得不太可能；记录让它变得不可能。**

## 曾考虑的替代方案

**扫描引擎目录里的 `verify-*.ts`，运行找到的东西。** 引擎目录本来就持有门禁，因此一份清单在构造上即为真，不需要第二个文件来保持同步；这正是分发器曾经的样子。它落选的原因不是真实性，而是稳定性。一份清单的稳定性只取决于该目录的文件名，因此一次重命名、一次不完整的安装，或一个被丢在分发器旁边的辅助模块，都会在不改变任何人所做决定的情况下改变运行的内容，而上面那次运行途中的扫描展示了后果：两个静默加载并以 0 退出的模块被算作门禁，并被打印为门禁。记录可以在 diff 中评审——维护者在运行之前就能看到聚合检查将要运行的名称与数量——而一份清单不过是那个目录在那一刻恰好持有的内容，顺序也不是任何人选的。

**对两者做对账，但把分歧报告为警告。** 分发器将运行扫描到的脚本，并打印它与记录的差异而不失败。它落选，是因为警告不是检查：一道文件已消失的已记录门禁，和一个没人记录过的辅助模块，都会通过一次聚合检查，而它的退出码——也就是全部检查——保持在零。

**记录门禁，让分发器只信任记录。** 记录就是清单，因此分发器可以把每个名称解析为 `<name>.ts`，并在文件缺失时失败，而完全不读该目录。它落选，是因为它只抓住一半的分歧。一个被留在分发器旁边的辅助模块或被重命名的脚本仍会不可见，而维护者读到的那组文件将不再是记录所描述的那一组。

## 后果

- `references/manifest.json` 除仓库、修订和技能之外还带有 `gates` 数组，而 `dsh-spec.ts` 在启动时拿它与引擎目录中的 `verify-*.ts` 文件对账。一个没有对应文件的已记录名称，或一个记录没有点名的文件，都会连同两侧一起被报告，并在任何门禁运行之前以非零退出。
- 正因为这次对账是致命而非提示性的，`install` 与 `update` 会把每个已安装技能目录削减到其修订真正交付的内容——安装器记在 `github-tree-sha` 里的那棵树，通过 API 列出——因为 `gh skill install --force` 只覆盖修订中含有的文件，从不删除它撤下的文件。否则从集合中移除的一道门禁，会让每个刷新过的项目里的聚合检查都拒绝运行。
- `check --all` 运行以整棵树为断言的那些检查，它的每一行都说明哪个主语运行了、结果如何。一道门禁只有在其名称被记录、且其脚本位于分发器旁边之后，才加入这次运行，而这两处编辑必须在同一个变更中完成。
- 验证：`dsh-spec.ts check --all --root .` 以 `check notes: ok` 与 `check notes-archived: ok` 结束，而这次改动运行的门禁，各自都在它留下的目录树上以零退出。
- 这一决定换来的是一个聚合检查，其清单是读者可评审的一项决定：一个什么都不检查的模块再也不能打印绿色，因为记录没有点名的文件会被报告并拒绝，而不是被运行。它的代价则是：每当增删一道门禁，就要有第二处编辑；以及一个可能出错的 manifest——分发器在每次调用时都必须对它做对账，而不能信任那个目录。
