# Agent Note: 一次改动只跑它该跑的门禁

Status: implemented

[English](2026-09-21-a-diff-selects-the-gates-it-owes.md) | 中文

## 问题

本集合的每道检查都只能按名称调用,于是一个只改了一条笔记的人,得先知道存在三道笔记门禁、知道配对门禁也会读这条笔记、还知道三道 Markdown 门禁同样会读它——否则就跑聚合检查,然后等着那些根本看不见这次改动的门禁跑完。pre-push 技能把这份对应关系写成了散文,而那是"每道门禁读什么"的第二份陈述,门禁范围一变它就开始漂移。

## 决策

manifest 里每道已记录的门禁现在都要声明一个**范围键**——`notes`、`markdown`、`pairs` 或 `tracked`——由分发器通过本来拥有这些路径的模块去解析:`notes-root.ts` 管笔记树,`md-scope.ts` 管散文门禁所读的 Markdown,`i18n-scope.ts` 管配对范围,凭据扫描则看 git 报告的全部文件,因为任何文件都可能夹带凭据。随后 `run.ts --changed --base <ref>` 只跑这次改动触及的门禁,并把每一道被跳过的门禁连同原因打印出来。

用键而不是路径字面量,是为了让每条路径只有一个归属者:manifest 说明一道门禁对哪块*面*负责,引擎说明那块面在哪里。集合外的键一律拒绝——无法解析的范围会被读成"这里没有属于该门禁的东西",从而悄悄丢掉检查;已记录的门禁若完全没有条目也拒绝,这样记录不会只写一半。

`--all` 不变,仍是整套检查;`--changed` 是一个子集,并在自己的输出里说明这一点,永远不能替代推送前的聚合检查。

## 曾考虑的替代方案

**继续把对应关系写成 pre-push 里的散文。** 今天能用,也不需要写代码。它落选,是因为散文无法被执行:门禁范围变了而那句话没变时,没有任何东西会失败,而那句话恰恰是贡献者会去读、而不去跑检查的东西。

**让每道门禁自己报告它读哪些路径。** 这是最忠实的版本——门禁自己回答。它落选,是因为这意味着每道门禁都要长出一个范围上报模式,分发器还要解释四种不同的回答;而由拥有路径的模块解析一个键,说的是同一件事,且只有一个归属者。

**在 manifest 里为每道门禁记录字面 glob。** 评审时最直观,没有间接层。它落选,是因为它把每条路径的第二份副本放进第二个地方,而这个包已经为"一条路径两处字面量"付过两次代价。

**不打印被跳过的门禁。** 输出会更短。它落选,是因为一次不说明自己漏了什么的限定运行,与一次通过的聚合检查无法区分——而这正是整份记录要防的失败。

## 后果

- 改引擎只会跑凭据扫描;改一条笔记会跑读笔记树、配对与 Markdown 的那四道门禁;每次运行都会打印它跳过了哪些。
- manifest 现在承载四条事实;新增一道门禁意味着在同一次改动里记录它的名称、范围与脚本。
- 代价是多了一份要与门禁清单保持同步的记录。只写一半的情况由拒绝覆盖,而封闭的键集合让一个拼写错误无法悄悄缩小运行范围。
- 验证:`run.ts --all --root .` 以 `run: 7 gate(s), 0 failed` 结束;`run.ts --changed --base HEAD --root .` 会打印改动路径数、它拥有的门禁、每一处跳过及其范围,以及属于它自己的 `n of 7 gate(s) run` 一行。
