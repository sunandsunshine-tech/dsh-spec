# Agent Note: 整套技能只在项目 README 里介绍一次

Status: implemented

[English](2026-09-21-the-skill-set-is-introduced-once.md) | 中文

## 问题

每个技能在入口旁边带一套 README——它是做什么的、什么时候加载、不做什么——于是有二十四个文件和八对记录,主题却与仓库自己的 README 相同:介绍这一整套。而读者来到仓库时反而看不到总览:README 只指向其中一个技能的 README,另外七个得逐个目录打开才发现。两处文档在讲同一件事,配对门禁又让"保持两边一致"变成一项长期成本。

## 决策

把各技能的 README 移除,由根 README 用一张表列出八个技能以及各自管什么。入口(`SKILL.md`)仍然是 agent 加载的东西,它旁边的 `references/` 仍然是该工作流自己的材料;一个技能目录现在只装这两样。引擎自己的 `scripts/README.md` 保留,因为它记录了门禁解析 Markdown 所用的那个 vendored bundle,`manager-lifecycle.md` 负责把人引到那里。

## 曾考虑的替代方案

**保留它们,接受重复。** 它们是人读的门:打开一个技能目录就能判断,不必读整个仓库。它落选,是因为总览的归属地是这一整套、而不是单个技能——要比较技能的人需要把它们并排看,而这份比较一旦有八份副本就会各自漂移。

**只保留 manager 的 README。** 那是源项目的形状,而且 manager 是集合的入口。它落选,是因为 manager 介绍的是这个*包*,不是八个工作流:读者问"哪一个是管评审证据的?",从这里得不到答案;而它自己的内容,大半是把根 README 的材料又写了一遍。

**把各技能的介绍搬进各自的 `SKILL.md`。** 一个技能一个文件,不新增文档。它落选,是因为 `SKILL.md` 是写给"判断要不要加载这个技能"的 agent 的,而"判断这套东西值不值得采用"的人读的是另一种文档;入口本来也已有职责——路由与触发。

## 后果

- 一份总览、一个归属地:根 README 的那张表,中英各一份。
- 少了八对需要记录的配对,技能目录里只剩下 agent 加载的东西和它的参考材料。
- 安装副本会在下次安装时失去这些 README:清理步骤会删掉修订不再交付的文件,这正是它被造出来要做的事。
- 代价是深度:想弄清 `dsh-pre-push-checks` 到底做什么的读者,拿到的是表里的一行,而不是一整页。要深入仍然去入口和它的参考材料,而那一行本来就是这张表的用途。
- 验证:`dsh-spec.ts all --check --root .` 以 `run: 7 gate(s), 0 failed` 结束;在没有 README 的情况下,`verify-skill-structure.ts` 对八个技能目录全部通过;`dsh-spec.ts upgrade` 会把这二十四个文件从 `.agents/skills/` 中移除。
