# Agent Note: 项目应用它自己挑的规范

Status: implemented

[English](2026-09-22-a-project-applies-the-norms-it-chooses.md) | 中文

## Problem

这套做法被抽取出来的时候，一路积累下一批对任何项目都成立的规范：一个改动怎么从 WIP 走到 merge，散文该对读者负什么责任，一个事实归谁，什么才算证据，测试套件怎么保持诚实。它们只住在三个地方，而且只有本仓库会去读：`AGENTS.md` 里的常驻指令、每篇决策记录的结论、以及各个工作流技能。采用这套技能集合的项目拿到的是工作流和机制文本，拿不到规范本身；想要其中一条，就得为它去读一整篇决策记录。

## Decision

规范作为一份目录发布，项目按分组、或按 id 挑出自己要应用的那些。

**目录是数据。** `skills/dsh-spec-manager/references/norms.json` 把每条规范都记下来：稳定的 id（`<group>.<name>`）、项目挑它时用的分组、会写进那个项目的英文标题与正文、给选择界面用的中文标题，以及拥有这条规范理由的决策记录。每条正文都长一个样：先用祈使句写规范本身，接着 `- Why:` —— 说明它为什么是规范而不是偏好 —— 最后 `- Self-check:` —— 读者怎么察觉自己正在违反它。渲染不出来的目录，在写任何东西之前就被点名拒绝：id 没法用来匹配、同一个 id 记了两次、规范落在没声明的分组里、分组下面一条规范都没有、正文缺了理由。规范那一行要写读者一眼认得出的症状——「同一个命令跑两次，不能吃掉它没写的内容」，而不是「创建和更新是两种授权」——因为第一遍读不懂的规范，等于没人会去用。

**选择界面是 `norms list`。** 每个分组一个标题，每条规范一行；用哪种语言打印，由 `--help zh|en` 或 locale 决定。正文用英文：读它的是 agent，而整套技能集合本身就是英文；中文标题是为了让中文读者不必读英文正文，也能挑、也能认。`--json` 会把两个标题、正文和记录一起带出来，这正是 agent 拿来渲染选择的形态——CLI 没法到处都渲染出选择器，但它可以把渲染需要的数据交给 agent。记录以 URL 给出，因为仓库相对路径只存在于本仓库；路径留在旁边供对照。列表本身保持干净：它是用来挑的，一条规范要到「有人问起它」的地方去解释。规范**刻意不做成门禁**：项目有权个性化某条规范，所以漂移由 install 和 update 报告，绝不让检查因此失败。

**文件放在项目的 agent 记录旁边，不在 `docs/` 下。** `.agents/dsh-spec/norms/norms.md` 和它旁边的记录，跟 agent 要读的文本放在一起 —— 笔记树里的那份契约就是同一类文件 —— 而 `docs/` 放的是给人读的文档。做成目录而不是单个文件，是因为目录早晚会一页装不下：日后按分组拆分，就是要在它们旁边多出 `pr.md`、`prose.md` 这些文件，入口和记录都不用动 —— 这正是[迁移成本是一项设计约束](2026-09-22-migration-cost-is-a-design-constraint.zh.md)管的事，只不过隔了一层目录。入口按内容叫 `norms.md`，不叫 `README.md` —— 打开 README 的人期待的是目录说明，不是要遵守的规则。

**写进项目的正文是一个受管文件，每个分组一节。** 每条规则是一个列表项，外面包着 `<!-- dsh-norm: <id> -->` … `<!-- /dsh-norm -->`，这样单条规则能被定位、被哈希、被单独个性化；这些标记是 HTML 注释，Claude Code 在把文件注入上下文之前会把它们剥掉。文件旁边另有一份记录，记下这个项目应用了哪些 id，以及每条规则上次由技能集合写入时的哈希 —— 和记录双语配对确认状态的 `.i18n.yaml` 是同一个思路。

**`AGENTS.md` 只在项目应用规范期间指向这个文件。** 这个钩子又是一个带标记的区域：应用第一条规范时由动词加上，移除最后一条时去掉；初始化器的 sync 会按记录把它补回来；它只从一处渲染，所以项目和技能集合对它的说法只有一份。一条规范都没应用的项目，不会带着一行指向它并不拥有的文件。

**安装和更新按 id 比较三种状态。** 项目那份的哈希仍等于记录的 base、而修订改了这条规则：静默用修订的正文覆盖，因为没人动过它。项目那份动过、修订没动：保留，并报为已个性化。两边都动过：保留项目那份，把两份都打印出来 —— 修订那份和项目那份，因为记录里存的是 base 的哈希、不是正文。报告提出的决定要显式执行：`norms update --take <id...>` 取修订的正文，`norms update --keep <id...>` 把项目那份记为有意为之，此后任何更新都不会再覆盖它。`--dry-run` 就是预览与落盘之间的全部差别，预览渲染的是同一套比较。**manager 自己永不写它们。** `install` 和 `upgrade` 报告已应用的规范，就像 `apt update` 报告可升级的包：这次修订会移动其中几条，或者一条都没应用、该去哪里看这套技能集合提供了什么；唯一会写的是 `norms update`。

**`norms explain <id>` 负责读回。** 它打印正文全文、指向 manager 自己被安装时所用 ref 的记录 URL、以及这个项目应用了没有；读不出已安装 ref 的树里，只打印记录路径。

**本仓库不应用自己的目录。** 这些规范就是从本仓库提炼出来的，本来就住在它的 `AGENTS.md` 和决策记录里；再装回来就是把同一份指导写两遍，而两份说法早晚会分叉。测试守着这条线：本仓库没有 `.agents/dsh-spec/norms/norms.md`，`AGENTS.md` 里也没有钩子；机制则在夹具里演练。

**部分取代：[本仓库采用这份规范目录](2026-10-02-the-repository-applies-the-catalog.zh.md)。** 目录已经通用化，钩子由每条规范的红线渲染出来，所以本仓库应用其中一批；本篇拥有的东西——机制、记录，以及"选择归项目"——没有变。

## Alternatives considered

**每个分组一个文件、在 `AGENTS.md` 里按分组埋钩子 —— 最初提出的设计。** 目前落选，依据是这个领域怎么组织 agent 指令。Claude Code 自己的指引要求「始终加载」的文件控制在 200 行以内，而且只拆那些**能按条件加载**的东西：它的 `.claude/rules/` 文件在 `paths` glob 命中时按需加载，而没有 scope 的每次会话都加载 —— 那和不拆是一回事。Codex 记录的是一个 `AGENTS.md`，按全局和仓库两个作用域合并，并要求写具体规则、把关键规则放最前面。dsh 用一个 179 行的根 `AGENTS.md` 按主题分节，另外按子树放 `AGENTS.md`，由目录触发。这些规范是横切的、没有路径范围，拆出去的文件也就没有自己的触发条件；而一条永远不会被读到的规范，比一条占一行的规范更糟。实测这份目录是 20 条、5 个分组、正文 60 行 —— 在那个预算之内。拆分这条路仍然留着，而且便宜：分组和 id 都在数据模型里，日后改成每分组一个文件不动任何 id、不动任何哈希，`AGENTS.md` 里那些分组钩子正好变成触发行。

**在 `install`/`upgrade` 里顺手应用选中的规范。** 落选：这两件事的授权不一样。刷新做的是把技能集合自己的文本带到某个修订，而项目应用的规范是它自己挑的、也可能被它改过；一条命令里同时做这两件事，就意味着 upgrade 会覆盖项目写下的文本。初始化器的受管文件表里不加 `rules` merge 模式，也是同一个理由。报告给出与 `apt update` 同等的发现能力，而不做这次写。

**给漂移做一道门禁。** 落选：个性化一条规范本来就是允许的，漂移不是缺陷；一道因此失败的检查，恰好会禁掉这份记录存在的意义所在的那种定制。功能的稳定性交给它自己的测试。

**把 33 条候选规范全部发布。** 落选：关于这个包自己的门禁和决策记录机制的那些规则，是这套技能集合自己解决的问题，不是项目要应用的规范。通用的那些进目录：候选里 19 条，再加上本仓库接下来需要的那条规则。

**每条规范一个文件，正文和它的哈希并排。** 落选：一份目录加一份记录，才能让每个事实只有一个归属者；而逐条标记已经给出了哈希需要的粒度。

## Consequences

- 规范跟着技能集合一起走，项目手里握着它挑中的那些：可以改，而记录负责分辨「项目改的」与「修订改的」。目录是数据，所以按分组拆分一直很便宜，为此不需要动任何 id 或哈希。
- 目录会长到超过一个「始终加载」的文件该承载的量。缓解手段是那条已经记下来的拆分路径，而不是承诺它一直很小；大小是量出来的，不是感觉出来的。
- 哈希只能说明文本动过，说明不了动得有意图。一个把某条规则重新排版的项目的确会被问到那条规则；好在报告是逐条的，代价是一个问题，不是一个文件。
- 这些是一个仓库的意见。当作好实践发布，主张的超出了一个项目的经验；所以每条规范都带着它来自的那篇记录，读者可以权衡理由，而不必相信规则。
