# Agent Note: 迁移成本是一项设计约束

Status: implemented

[English](2026-09-22-migration-cost-is-a-design-constraint.md) | 中文

## Problem

一个会往别人项目里写文件的包,其实同时在决定两件事:这个功能怎么做,以及它会在一个长期保留它的项目里留下什么样的设计。第一件事在这里判断:看代码、看测试、看本仓库自己的需要。第二件事得拿到那边判断:那个项目可能已经改了自己那份副本好几个月——在我们的小节旁边添了自己的小节,在块里换了自己的措辞,把自己的路径写进了 `AGENTS.md`,又从自己的笔记里链过来。改个名字,在这里不过是一次 diff,在那边却可能把别人已经写下的东西弄坏;而这个不对称只会越来越大:一个项目时只是几句话,一百个项目时就是一次迁移。

这种不对称,本仓库是碰上了才学会的。某个功能的文件先放在 `docs/`,同一次会话里又挪到 `.agents/dsh-spec/`;而讨论往哪儿挪的时候,还顺带问了一句:当初要是选了单个文件呢?——日后再按分组拆分,就得把这个文件变成目录,而那时项目已经攥着这条路径了。这次挪动之所以没有代价,只是因为还没有人采用过。当初那个选择的理由——「只有一个文档,用不着目录」——放在结构上说得通,放到迁移上却是瞎的。

## Decision

**两个设计如果在架构和规划上不分高下,就选那个采用者已经积累的内容还站得住的设计。** 能继续往里加文件的目录,胜过日后不得不变成目录的文件;能继续加字段的格式,胜过日后不得不重写的格式;能一直用下去的名字,胜过日后必须改的名字;放在文档旁边的记录,胜过日后要被改名的记录。这条规则关心的是能不能演进,不是路径本身:要回答的问题是,当这个设计变了,采用者手里正攥着什么。

有两个条件,免得它变成给投机开绿灯。第一,这个变化得是**大概率**会发生的,而且理由要写在改动里,不能靠假定。第二,能扛住它的那个设计现在几乎不花成本,也不动架构与规划。要保护的如果只是一个谁也没料到会发生的改变,那就选更简单的设计——在这个仓库里,投机的结构本身就是缺陷。概率或成本要是只能靠猜,这个决定就归维护者:去问一声。

## Alternatives considered

**现在挑最简单的设计,以后再说迁移。** 落选:迁移才是花钱的那一头。简单由我们付一次;迁移要由每一个已经积累内容的项目来付,这本账本仓库没资格替它们算。

**到处为可选性买单。** 落选:这是同一枚硬币的另一面。需要还没出现就把通用设计造出来,正是[四个机制,而非十二个](2026-09-18-four-mechanisms-instead-of-twelve.zh.md)删掉的东西;而一个没人需要的抽象,比一个目录更难删。

**每个改动自己临场决定。** 落选:第一个设计就是这么选出来的——本地说得通,对采用者是瞎的;而这个答案本该在一次会话里就拿得到,不必每次重推一遍。

**每个这类决定都拿去和维护者讨论。** 作为默认落选,作为退路保留:概率或成本没法用证据说清时,这是对的做法;能说清时,它太慢。

## Consequences

- 有些改动会带上一个目录、一层间接,或者比眼下需要更多的命名。这就是代价,而且要在改动里说出来,不要留给人去发现。
- 「大概率」也可能是错的。办法是把这个判断连同理由写下来,后来的读者能看见当初假设了什么,然后纠正它。
- 这条规则不凌驾于其他边界之上:一个会让这个包假定某一种生态的设计,或者一道会在空语料上通过的门禁,仍然要拒绝。
