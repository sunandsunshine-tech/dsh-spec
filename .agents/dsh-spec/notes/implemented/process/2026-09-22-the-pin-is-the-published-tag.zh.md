# Agent Note: pin 是发布出去的那个 tag

Status: implemented

[English](2026-09-22-the-pin-is-the-published-tag.md) | 中文

## Problem

0.1.0 之前还没有发布,所以 pin 只能指向主干:安装跟着 `main` 走,tag 只是给别人看的标记、用来指认某一个提交。[发布的修订是 main 分支](../../archived/process/2026-09-21-the-released-revision-is-main.md)当初是有意这么定的,并且把自己放弃的那条退路写在了明处——钉 tag,以后要移过去,是一次改动加一次刷新。现在发布出来了,就是那个时刻。

## Decision

**安装跟着发布走。** 不带 `--revision` 的 `install` 与 `upgrade` 解析的是最新已发布的 release,所以一个项目钉住的是它采用时发布出去的那个 tag;主干仍然够得着,用 `--revision main`;某条分支用 `--revision <branch>`。tag 不会移动,所以两次发布之间,项目脚下的东西不会变;发布说明与草稿 release 描述的正是到达的那个修订。

**本仓库自己那份副本,每次发布后重新钉到那个 tag 上。** 这次刷新跑的是 `upgrade --revision v<version> --root .`,于是本仓库运行的那一份与安装者拿到的逐字节相同;开发期间的副本用 `--revision <branch>` 刷新,发布负责把它放回一个已发布的修订。`main` 仍是发布落地的那条开发线,tag 指向它上面的某个提交,但它不再是被部署跟随的那个东西。

## Alternatives considered

**继续留在 `main`。** 有了发布之后落选:本仓库自己的部署会跟着未发布的工作走,副本于是与安装者拿到的不同,而且任何一次落地都会悄悄换掉本仓库自己正在运行的东西。归档的那篇决定把这个代价摆在明处——「pin 会移动」——并且只在还没有东西可钉的时候接受它。

**钉发布所指向的那个提交。** 落选:那是没有名字的 tag。读副本里 `SKILL.md` 的人看不出一个裸 sha 是什么,而 `v0.1.0` 说明到达的是哪次发布;真想要提交号的人,一次 `gh api` 就能拿到 tag 背后的提交。

**副本就留在最后一次分支刷新的位置。** 落选:分支一旦合并删除,那个 ref 谁也没法再取;副本会指着一个解析不到的修订,而从它跑裸的 `upgrade --only-skill-set` 会失败。发布把它重新钉到一个不会移动的东西上。

## Consequences

- 发布从此多一步重钉:先打 tag,再 `upgrade --revision v<version>`。在这步跑之前,副本钉的是它最后一次刷新所用的那条分支。
- 想要未发布工作的项目必须自己说出来:`--revision main`。这正是归档那篇决定用「可移动的 pin」换来的取舍,现在它按项目显式表达,而不是替所有人默认。
- `status` 比的仍只是注入的 ref:ref 对、内容落后的副本,它离线查不出来。让两者同步的是刷新这条纪律。
