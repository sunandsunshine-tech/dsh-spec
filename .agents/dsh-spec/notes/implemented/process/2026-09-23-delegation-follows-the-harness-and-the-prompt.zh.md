# Agent Note: 委派交给 harness 与提示词

Status: implemented

[English](2026-09-23-delegation-follows-the-harness-and-the-prompt.md) | 中文

## Problem

这个仓库曾经把「agent 该怎么委派」写成规则:谁算主线、没有谈成规划就不派、从主线程到后台任务、到一个 `subagent`、到一个持有 fan-out 的 `subagent` 的成本阶梯、持有者欠回什么、以及一个路径一个写者。那套规则是从「产品在运行时怎么架构多代理」借来的,到这里却变成压在 agent 头上的常驻令。

它压不住。一次委派究竟会发生什么,取决于部署与当时的状态:subagent 调用是等结果还是返回一个 id、委派能有多深、同时能活几个子代理、fork 的快照能新鲜多久、一批活的回报是不是一个一个落进对话。这些是设置与状态,不是规则,所以同一条指令在不同会话里给出不同行为。一条没法同样地执行两次的规定不是规则,是穿着规则外衣的习惯。

## Decision

**委派作为规则撤销。** 目录里去掉 `agent.roles`,常驻令删掉,当初引入它的那篇决定归档。

**激活委派的是 harness 与提示词。** harness 原生判断:一次调用做什么、等不等、能多深、能几个。维护者的提示词说清要什么、怎么做。一件事值得拆的时候,harness 自己会给出拆法,人也可以直接要求;两边都不需要一份文档去预测哪个单元该用哪个载体。

**不再补别的东西。** 不写软化的阶梯,不写收窄的工作区规则,不写「什么时候该用 subagent」的清单。仓库保留那些从来与委派无关的规则:验收的主张归跑它的那个人,需要隔离的工作用独立的检出。

## Alternatives considered

**留着规则、把话说软。** 落选:不稳定的地方在机制,不在措辞。一份点名了部署未必提供的载体的成本阶梯,写得多温和都是错的。

**只留成本阶梯。** 落选:挑载体正是 harness 与提示词已经在做的判断;写死的阶梯只会继续预测一个随设置而变的答案。

**只留工作区那条。** 落选,但留作手段:一个路径上两个写者仍然会丢改动,所以并行写的时候该想到隔离;它是手段,不是要遵守的协议。

**只在本仓库保留这套规则。** 落选:这里与一个采用它的项目并没有区别,除了 agent 的个数;同一些机制在两边都做主。

## Consequences

- 目录少一组两条,它自己的记录重新数过。
- 想要拆的人自己说,能拆的 harness 自己拆;代价是每次现场判断,而不是翻一条写好的答案。
- 归档那篇留住了被否掉的理由,包括那份成本阶梯;后来的提议得先跟它辩,而不是重新发现它。
- 留下的是证据:无论活是怎么做出来的,提交的人自己跑验收。
