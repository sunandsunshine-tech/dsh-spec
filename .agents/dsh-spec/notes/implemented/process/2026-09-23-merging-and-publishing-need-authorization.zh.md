# Agent Note: 合并与发布需要授权

Status: implemented

[English](2026-09-23-merging-and-publishing-need-authorization.md) | 中文

## Problem

「谁的判断才让改动落地」这件事,[PR 生命周期](2026-09-21-the-pull-request-lifecycle.zh.md)已经定了:检查跑绿只证明跑过,不证明该落地;本仓库依靠的关卡是维护者的评审;发布这个决定留给同一个人。它没有写下这份判断对在这里干活的 agent 的操作形态,而缺口是有形状的。曾有 agent 从任务描述里拿到一次性常备许可——这个目标的 PR,你自己确认无误后合并即可——它覆盖的是当时还不存在的改动,读起来跟"agent 自认为这个改动做完了"没有分别。

这样到达的规则,下一个读仓库的人找不到,也无法收窄到它当时说的那件事,还把它前面的评审变成走过场。发布更严重:它是唯一会触达每一个装了这套技能的人的动作,而从一句讲别的事的指令里继承来的许可,不是关于它的决定。

## Decision

合并一个改动、发布一个 release、把草稿标为待评审,都只在获得对那次行为的授权之后进行。[PR 生命周期](2026-09-21-the-pull-request-lifecycle.zh.md)承载那条规则——哪些行为需要授权、其中哪些保留给仓库维护者——而一次授权该有什么形式,归这条笔记:它要指明自己覆盖的那次行为,并带上这个改动的说明;对另一个改动的批准、或对同一个改动在更早阶段的批准,都不构成授权。

这条规则有三个落点,每个面向一个读者:

- `AGENTS.md` 把它作为常备令载着,让在这里干活的 agent 每次会话都碰得到。
- `pr.lifecycle` 把它带进规范目录,让采用这套模式的项目随整套继承。
- `.github/release_template.md` 承载发布说明文档该有的形状,让发布照一个形式写,而不是凭记忆。

两条边界让它不外扩。它不重开生命周期关于"维护者的判断"的论证,只指明那份判断授权的是哪个行为;它也不决定合并方式,那是生命周期的地盘:发布 PR 在被授权之后,与其它 PR 一样用 squash 合并。

## Alternatives considered

- **交给每次的任务描述。** 缺口就是这么来的:对一批活的一次性许可,与一般性的许可分不出来,而且后来读仓库的人两样都找不到。
- **只放进规范目录。** 目录是采用者挑选用哪几条的地方,而本仓库当时一条都没应用,于是这条规则在这里约束不到任何人。
- **整批授权一次,而不是每次行为各授权一次。** 五个 PR 一条堆叠只批一次,就是常备许可升了一层:其中四个落地在一个没人做过的决定上。
- **让批准只活在给出它的那次对话里。** 合并会记进仓库,批准却不会,于是下一个读的人分不出哪次合并是被授权的、哪次是被默认的。

## Consequences

**换来了什么。** 结束评审的那个行为,与评审本身重新分开;而发布——那个触达安装者的行为——有了所有者,而不是继承来的许可。任何人问起某次合并或某次发布背后的授权,都能得到答案,这正是这条规则可核的原因。

**代价是什么。** 必须等授权的 agent 会让维护者本以为会跑完的一批活停住;代价是每次行为一个来回,一条堆叠则每层各付一次。申请里"指明这次行为"很容易被跳过,而不指明行为的批准会退化成这条规则要取消的那种常备许可。

**留给读者什么。** 本篇与生命周期笔记并列而非并入,所以只找到其中一篇的读者只拿到一半规则;交叉链接是应对,也正是本篇不得复述生命周期已拥有内容的原因。这条规则没有门禁在守——维护者的答复就是执行——所以授权留下的痕迹,应当出现在合并发生的地方,而不只是给出它的那次对话里。
