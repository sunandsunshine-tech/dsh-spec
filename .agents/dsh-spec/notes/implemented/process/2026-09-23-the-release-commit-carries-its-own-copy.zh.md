# Agent Note: 发布提交自带它发布的那份副本

Status: implemented

[English](2026-09-23-the-release-commit-carries-its-own-copy.md) | 中文

## 问题

[拉取请求生命周期](2026-09-21-the-pull-request-lifecycle.zh.md)把发布 PR 定成它 squash 规则唯一的例外:它的提交用 `git merge --ff-only` 合入,好让发布 tag 指向发布线上的一个提交,GitHub 那边则被报成一次间接合并。而 [pin 就是发布出去的 tag](2026-09-22-the-pin-is-the-published-tag.zh.md)接着在**打 tag 之后**用第二个提交,把本仓库自己的副本放回一个已发布的修订上。

两条规则加起来,付出的比换来的多。一次发布要在 `main` 上留两个提交,还要多一条只有发布 PR 会走的合并路径;而被发布的那个修订仍然带着一份副本,它的注入 ref 指向刷新它时用的那条分支——一条会被合并删掉的分支——因为重钉它的提交在 tag 之后。那篇笔记当初以「取不到」为由否决的状态,恰恰是每一个发布 tag 实际发出的状态。

## 决策

发布 PR 与其它 PR 一样 squash 合并。它的提交就是发布说明和「从发布分支刷新的安装副本」,tag 在合并之后打在 squash 提交上,于是发布线上一个提交同时载着这两样。合并的其它部分不变:发布 PR 照常被评审,squash 仍是本仓库在 GitHub 侧唯一的合并方式。

那个提交里的副本 pin 的是发布分支,而合并会把它删掉。这个悬空的 ref 是接受的:发布要对得上的是副本的**内容**而不是它的名字——注入的 tree sha 就是发布出去的技能,而本仓库里每一次刷新都显式点名修订(`upgrade --revision <branch|tag>`),所以只有一条裸的 `upgrade --only-skill-set`(在被发布的修订上跑)才会去解析这个名字。安装者自己的副本 pin 的是他安装时用的 ref——一个 tag,或一条会留下来的分支。

两条边界。它不改变「一次发布是什么」、也不改变安装跟随什么,那两件事归 [pin 笔记](2026-09-22-the-pin-is-the-published-tag.zh.md);它也不扩大发布提交携带的东西——发布新增的就是说明与副本,其余需要的东西都在它之前、由做出那个改动的 PR 落地。

## 曾考虑的替代方案

- **在发布提交里把副本 pin 到 tag 上。** 被发布修订的副本会指向一个活着的 ref,这正是 pin 笔记想要的。它落选,是因为 tag 无法在「从它构建副本」之前存在:得先给发布分支打 tag,合并之后再把它移到 squash 提交上;那样一个安装者会解析的名字就被移动了,而且是为了一条正常流程从不解析的 ref 而移动。
- **从 `main` 刷新副本。** 同样的技能内容、一个活着的 ref,而且合并之前不需要 tag,因为发布分支的 `skills/` 树就是 `main` 的。它落选,是因为它把开发线写成副本的来源:后来的读者分不出这份副本来自哪次发布,而且副本从此跟着未发布的工作走。
- **保留本地 `git merge --ff-only`。** 那是生命周期当初的决定,而且它把 tag 放在分支自己的提交上。它落选,是因为发布于是需要一条自己的合并路径,而它需要的那第二个提交让被发布修订的副本仍然陈旧;当初为此引入例外所要的那个保证,用「给 squash 提交打 tag」同样能得到。
- **把副本留到下一个改动开始时再刷新,发布只带自己的说明。** 发布时除了说明没有任何活。它落选,是因为被发布的修订于是会发出没有任何修订安装过的技能,而发布也不再是「把副本带到它所发布的东西上」的那一刻。

## 后果

**换来了什么。** 发布线上一个提交同时载着这次发布和它的副本,发布 PR 用的是其它 PR 都在用的那种合并,发布 tag 指向普通合并产生的提交。生命周期记下的那两笔间接合并代价——不生效的保护、要手工删的分支——随例外一起消失。

**代价是什么。** 被发布修订里的副本 pin 着一条已删分支,而且没有后续提交去修它:在下一次刷新之前,本仓库里一条裸的 `upgrade --only-skill-set` 会以 `could not resolve version: HTTP 422: No commit found for SHA: <branch>` 失败,必须给它 `--revision`——而常驻令每次都带。同时,「本仓库跑的副本就是安装者收到的那一份」这句话从逐字节一致,降级为「同样的技能、不同的注入 ref」。

**留给读者什么。** 发布成了唯一为「发布出去」而刷新副本的地方,所以发布分支必须先推上去,才能从它刷新副本——这也正是发布 PR 至少要有两个提交的原因。而被发布修订携带的那个 ref 是名字而不是承诺:读它旁边注入的 tree sha,那才是这次发布真正作出的断言。
