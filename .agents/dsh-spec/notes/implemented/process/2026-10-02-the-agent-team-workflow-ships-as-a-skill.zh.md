# Agent Note: 团队工作流以一个技能的形式交付

Status: implemented

[English](2026-10-02-the-agent-team-workflow-ships-as-a-skill.md) | 中文

## Problem

本仓库里的委派之所以发生,是因为有人用对了措辞提出要求,也因为当时在调度的人恰好记着那些约束:一个文件只有一个写者、评审者要重跑而不是阅读、文字那一遍要独立于作者。技能集合里没有任何东西承载它们,于是下一个会话只能重新推导——推得差,或者干脆不推。[激活委派的是 harness 与提示词](2026-09-23-delegation-follows-the-harness-and-the-prompt.zh.md)撤销了那条规则、把提示词留下当触发条件;而提示词会要求的那套做法,当时没有东西承载。

## Decision

`dsh-agent-team-workflow` 是第十个技能。它拥有 Agent Teams 面向使用者的那一半:角色——Lead 只有一个,Worker、Reviewer、Texter 各成池——每个角色持有什么契约、一件工作以什么任务卡交接、以及某一步欠本仓库哪些义务。它的入口在被激活的那一轮第一行就声明自己,读者因此能看见当前跑的是哪种模式。

分工是定死的。Lead 规划、拆分、整合,并且是唯一对用户说话的角色;Worker 实现并跑检查;Reviewer 在干净的上下文里重跑验收命令,而不是阅读关于它的说法;Texter 写作与翻译,不动代码。每项义务都留在它原来的所有者那里:技能从规范推导一次改动欠哪些检查,不复述任何一条。

## Alternatives considered

**留在常驻指令里。** 落选:`AGENTS.md` 说的是改动欠什么,不是工作怎么分;而一个从没被要求拆分的会话,会把每一步都留在同一个上下文里。

**并进 manager 技能。** 落选:manager 拥有的是采用——初始化、技能集合、规范、以及采用方跑哪些检查。团队是同一批规则的第二类使用者,不是第二个 manager。

**短任务上不设 Lead。** 落选:激活就是这个机制本身。没有触发条件的技能,是一份 agent 读完就丢开的文档。

## Consequences

- 两份 README、`AGENTS.md` 与清单都记十个技能,安装器的状态报告随之。
- Texter 的改动只涉及文字,所以纯文字 diff 免跑类型检查——写在技能里,而不是每次临场决定。
- 每一步的义务从规范推导,意味着规范改了,技能的说法随之改变,不需要改技能。
