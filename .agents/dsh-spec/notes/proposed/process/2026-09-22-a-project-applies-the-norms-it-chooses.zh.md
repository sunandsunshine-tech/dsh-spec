# Agent Note: 项目应用它自己挑的规范

Status: proposed

[English](2026-09-22-a-project-applies-the-norms-it-chooses.md) | 中文

## Problem

这个仓库抽取的那套做法里,积累了一批对任何项目都成立的规范:一个改动怎么从 WIP 走到 merge、散文欠读者什么、一个事实归谁、什么才算证据、测试套件怎么保持诚实。今天它们住在只有本仓库会读的三个地方——`AGENTS.md` 里的常驻指令、每篇决策记录的结论、以及各个工作流技能。采用这套技能集合的项目拿到的是工作流与机制文本,不是这些规范本身;想要其中一条的人,得为一条规范去读一篇决策记录。

## Proposal

把规范作为一份目录发布,让项目按分组或按 id 挑选要应用的那些。

**目录是数据。** `skills/dsh-spec-manager/references/norms.json` 持有每条规范:稳定的 id(`<group>.<name>`)、项目用来挑选的分组、会写进那个项目的英文标题与正文、供选择界面使用的中文标题,以及拥有其理由的决策记录。正文统一一个形状:祈使句写规范本身,然后 `- Why:` —— 让它成为规范而不是偏好的理由 —— 然后 `- Self-check:` —— 读者怎么发现自己正在违反它。渲染不出来的目录在写任何东西之前就被点名拒绝:id 无法用于匹配、id 记了两次、规范落在未声明的分组里、分组底下没有任何规范、正文缺理由。规范那一行写读者认得出的症状——「同一个命令跑两次,不能吃掉它没写的内容」,而不是「创建与更新是两种授权」——因为一条第一遍读不懂的规范,等于没人应用。

**选择界面是 `norms list`。** 每个分组一个标题、每条规范一行,按 `--help zh|en` 或 locale 选定的语言打印。正文用英文,因为读它的是 agent、而这套技能集合本身是英文的;中文标题的存在,是为了让中文读者不必读英文正文也能挑选和辨认一条规范。`--json` 同时带两个标题、正文与记录,这正是 agent 用来渲染选择的形态——CLI 无法可移植地渲染选择器,但它可以把渲染所需的数据交给 agent。记录以 URL 发布,因为仓库相对路径只存在于本仓库;路径留在旁边供对照。列表本身保持干净:它是用来挑的,而一条规范在「问起它」的地方解释。规范**刻意不做成门禁**:项目被允许个性化一条规范,所以漂移由 install 与 update 报告,而绝不让检查失败。

**文件放在项目的 agent 记录旁,而不是 `docs/` 下。** `.agents/dsh-spec/norms/README.md` 与它旁边的记录,和 agent 要读的文本放在一起 —— 隔壁的笔记契约就是同一类文件 —— 而 `docs/` 放的是给人读的文档。它们是目录而不是单个文件,因为目录会长到一页装不下:日后的按分组拆分会在它们旁边加上 `pr.md`、`prose.md` 等文件,而入口与记录都不用动。**项目已经开始持有的路径,才是改起来昂贵的那样东西** —— 等到很多项目都积累了自己的修改,那次移动就是破坏它们的东西 —— 所以现在就选那个能扛住大概率变化的形状,代价不过是一个更长的名字。入口叫 `README.md`,因为这里一个目录的入口就叫这个:隔壁的笔记契约是同一类文件。

**写进项目的文本是一个受管文件,每个分组一节。** 每条规范是一个列表项,外面包 `<!-- dsh-norm: <id> -->` … `<!-- /dsh-norm -->`,于是单条规范可以被定位、被哈希、被单独个性化;这些标记是 HTML 注释,而 Claude Code 在把文件注入上下文之前会剥掉它们。文件旁边一份旁车记录项目应用了哪些 id,以及每条规范上次由技能集合写入时的哈希——与记录双语配对确认状态的 `.i18n.yaml` 是同一个思路。

**`AGENTS.md` 只在项目应用规范期间指向该文件。** 这个钩子又是一个受标记的区域:动词在应用第一条规范时加入它、在最后一条被移除时去掉它,初始化器的 sync 按记录把它补回,而它只从一处渲染,于是项目与技能集合对它的陈述只有一份。一条都没应用的项目,不会带着一行指向它并不拥有的文件。

**安装与更新按 id 比较三种状态。** 项目那份的哈希仍等于记录的 base、而修订改了这条规范:静默用修订的文本覆盖,因为没人动过它。项目那份动了、修订没动:保留,并作为「已个性化」报一次。两边都动了:保留项目那份,并把两份都打印出来 —— 修订那份与项目那份,因为记录里存的是 base 的哈希而不是正文。报告提出的那个决定由显式的动作执行:`norms update --take <id...>` 取修订的文本,`norms update --keep <id...>` 把项目这份记为有意为之,此后任何更新都不再覆盖它。`--dry-run` 仍是预览与落盘之间唯一的差别,而预览渲染的是同一套比较。**manager 永不写它们。** `install` 与 `upgrade` 报告已应用的规范,就像 `apt update` 报告可升级的包 —— 这次修订会移动其中几条,或者一条都没应用、以及去哪看这套技能集合提供了什么 —— 而唯一会写的是 `norms update`。

## Delivery in two rounds

- **先落地:** 目录、`norms list`(带 `--group` 与 `--json`),以及让目录保持可渲染、让界面保持稳定的测试。
- **再落地:** `.agents/dsh-spec/norms/README.md` 与 `.agents/dsh-spec/norms/applied.yaml`、三种状态、`norms install | update | remove`、`--take`/`--keep` 两个决定,以及 `norms explain <id>` —— 正文全文、指向 manager 自己被安装时所用 ref 的记录 URL,以及这个项目应用了没有。读不出已安装 ref 的树里只打印记录路径。
- **第三批落地:** 条件式的 `AGENTS.md` 钩子,由动词与初始化器的 sync 加入与移除。
- **刻意不做:** 初始化器受管文件表里的 `rules` merge 模式。刷新拥有的是机制文本,而规范是项目自己的选择、也可能被它改过;把两者合成一条命令,就会让 upgrade 重写项目写下的文本 —— 正是「创建与更新」那条规范要防的失败。报告给出发现路径,而不给出这次写。
- **本仓库不应用自己的目录。** 这些规范是从本仓库提炼出来的,本来就住在它的 `AGENTS.md` 与决策记录里;再装回来会把同一份指导写两遍,而同一规则的两种陈述会漂移。测试守住这条线:本仓库没有 `.agents/dsh-spec/norms/README.md`,这个 `AGENTS.md` 里也没有钩子;机制则在夹具里演练。

## Alternatives considered

**每个分组一个文件、在 `AGENTS.md` 里按分组埋钩子 —— 最初提出的形态。** 目前落选,依据来自这个领域如何组织 agent 指令的证据。Claude Code 自己的指引把「始终加载」的文件控制在 200 行以内,并且只拆那些**能被条件加载**的东西:它的 `.claude/rules/` 文件在 `paths` glob 命中时按需加载,而没有 scope 的那些每次会话都加载 —— 那和不拆是一回事。Codex 记录的是一个 `AGENTS.md`,按全局与仓库两个作用域合并,并要求写具体的规则、把关键规则放最前。dsh 用一个 179 行的根 `AGENTS.md` 按主题分节,另外按子树放 `AGENTS.md`,由目录触发。这些规范是横切的,没有路径范围,所以拆出去的文件没有自己的触发条件,而一条永远不会被读到的规范比一条占一行的规范更糟。实测这个目录是 18 条规范、约 60 行正文 —— 在那个预算之内。拆分这条路仍然留着,而且便宜:分组与 id 都在数据模型里,日后改成每分组一个文件不会改任何 id、也不会改任何哈希,而 `AGENTS.md` 里的分组钩子正好成为触发行。

**在 `install`/`upgrade` 里直接应用选中的规范。** 落选:两件事的授权不同。刷新做的是把技能集合自己的文本带到某个修订,而项目应用的规范是它选的、也可能被它改过;一条命令里同时做这两件事,就意味着 upgrade 覆盖项目写下的文本。报告给出与 `apt update` 同等的发现能力,而没有这次写。

**把漂移做成门禁。** 落选:个性化一条规范是被设计允许的,所以漂移不是缺陷;一个会因此失败的检查,恰好会禁止旁车存在的意义所在的那种定制。功能自身的测试承担它的稳定性。

**把 33 条候选规范全部发布。** 落选:关于这个包自己的门禁与决策记录机制的那些规则,是这套技能集合自己解决的问题,不是项目要应用的规范。通用的那些整合后是 18 条。

**每条规范一个文件、文本与哈希并排。** 落选:一份目录加一份旁车让每个事实只有一个归属者,而逐条标记已经给出了哈希所需的粒度。

## Acceptance criteria

- `norms list` 打印每一条随包发布的规范;`--group` 收窄到一个分组,并拒绝目录没有声明的分组;locale 决定中文标题;`--json` 同时带两个标题、正文与记录。渲染不出来的目录 —— 测试种下的九种 —— 被点名拒绝。(由这一轮的测试满足。)
- install 把选中的规范写进 `.agents/dsh-spec/norms/README.md`,每个分组一节、每条规范一个标记块,并把每条的基础哈希记在旁边;update 只覆盖文本哈希仍等于 base 的块,保留并点名已个性化的那块,冲突时把两份版本都打印出来,并且永不写标记块之外的内容;`--take` 与 `--keep` 执行那个决定;`--dry-run` 渲染全部且不写盘。(由写盘路径的测试满足。)
- `install` 与 `upgrade` 点名这次修订会移动的已应用规范,或者说明一条都没应用、以及去哪看它们;两者都不写 `.agents/dsh-spec/norms/README.md` 与 `.agents/dsh-spec/norms/applied.yaml`。(由刷新的测试满足。)
- 项目只在应用规范期间带着 `AGENTS.md` 钩子:动词加入、刷新、移除它,初始化器的 sync 按记录把它补回,而本仓库一个都不带。(由钩子的测试满足。)

## Risks

- 目录会长到超过一个「始终加载」的文件该承载的量。缓解手段是那条记下来的拆分路径,而不是承诺它保持小;大小是量出来的,不是感觉出来的。
- 哈希记录的是文本动过,不是动得有意图。一个把某条规范重新排版的项目会被问到那条规范;由于报告是逐条的,代价是一个问题,不是一个文件。
- 这些是一个仓库的意见。把它们当作好实践发布,主张的超出了一个项目的经验;所以每条规范都带着它来自的那篇记录,读者可以权衡理由,而不是相信规则。
