# Agent Note: 合并与发布需要授权

Status: proposed

[English](2026-09-23-merging-and-publishing-need-authorization.md) | 中文

## Problem

「谁的判断才让改动落地」这件事,[PR 生命周期](2026-09-21-the-pull-request-lifecycle.md)已经定了:检查跑绿只证明跑过,不证明该落地;本仓库依靠的关卡是维护者的评审;发布这个决定留给同一个人。本篇不重开这些。缺的是这份判断对**在这里干活的 agent** 的操作形态——它开完 PR 就停下,而每一次合并、每一次发布,都要有指明那一次行为的授权。

这个缺口不是假想的。在这里干活的 agent 曾拿到过一次性的常备许可:这个目标的 PR,你自己确认无误后合并即可。缺口就是这个形状。许可塞在任务描述里,覆盖的是当时还不存在的改动,读起来跟"agent 自认为这个改动做完了"没有分别。这样到达的规则,下一个读仓库的人找不到,也无法收窄到它当时说的那件事,还把它前面的评审变成走过场。发布更严重:它是唯一会触达每一个装了这套技能的人的动作,而从一句讲别的事的指令里继承来的许可,不是关于它的决定。

## Proposal

把规则写下来,并给它三个落点,每个面向不同的读者。

规则:agent 开完 PR 就停在那里。合并它、以及发布一个 release,都只在维护者对**那一次行为**授权之后进行,而申请要指明这次行为、并带上这个改动的说明。对另一个改动的批准、或对同一个改动在更早阶段的批准,都不构成授权——评审阶段与合并是两个行为,被保留的只是后者。

落点:本仓库 `AGENTS.md` 里的一条常备令,让在这里干活的 agent 每次会话都碰得到;规范目录里的一条,让采用这套模式的项目随整套继承;以及一份发布说明模板,让发布有固定的形状,而不是看当时动手的人记得什么。

## Alternatives considered

- **交给每次的任务描述。** 缺口就是这么来的:对一批活的一次性许可,与一般性的许可分不出来,而且后来读仓库的人两样都找不到。
- **只放进规范目录。** 目录是采用者挑选用哪几条的地方,而本仓库故意不应用自己的目录,于是这条规则在这里不约束任何人。
- **整批授权一次,而不是每次行为各授权一次。** 五个 PR 一条堆叠只批一次,就是常备许可升了一层:其中四个落地在一个没人做过的决定上。
- **让批准只活在给出它的那次对话里。** 合并会记进仓库,批准却不会,于是下一个读的人分不出哪次合并是被授权的、哪次是被默认的。

## Acceptance criteria

- `AGENTS.md` 载有这条常备令,并链接拥有其理由的那篇笔记。
- `norms list` 在 `pr` 组里显示 `pr.authorization`,含规则、理由与自检。
- `.github/release_template.md` 存在,遵循这套模式发布的发布结构,且它自己的相对链接与锚点都能解析。
- 本仓库的每一次合并与每一次发布,都指得出一条许可它的授权。

## Risks

必须等授权的 agent 会让维护者本以为会跑完的一批活停住;代价是每次行为一个来回,一条堆叠则每层各付一次。申请里"指明这次行为"很容易被跳过,而不指明行为的批准会退化成这条规则要取消的那种常备许可。本篇与生命周期笔记并列而非并入,所以只找到其中一篇的读者只拿到一半规则——交叉链接是应对,也正是本篇不得复述生命周期已拥有内容的原因。
