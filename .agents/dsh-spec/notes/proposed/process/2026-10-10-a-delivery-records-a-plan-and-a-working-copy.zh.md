# Agent Note: 交付由计划与工作副本承载

Status: proposed

[English](2026-10-10-a-delivery-records-a-plan-and-a-working-copy.md) | 中文

## Problem

多步交付的拓扑——有哪些工作包、按什么顺序、各自拿什么验收、谁等谁——在一次对话里商定，而对话之后它无处安放。笔记树记录的是能活过一次会话的两种状态：`proposed/` 装想做但还没细化的工作，`implemented/` 装已经交付的决定。一个即将开工的交付两者都不是。以后再接手的那次会话，只能从对话记录里重建计划，或者另起一套；分支上也没有任何东西说明这次交付当初对着哪个 main 想做什么。

## Proposal

交付由 `.agents/dsh-spec/plans/` 下的两个文件承载：`<slug>.md` 是计划，`<slug>-progress.md` 是交付运行期间写下的工作副本。它们的契约——计划的章节、状态规则、依赖写法、计划何时生效、开工与收口——是 [`plans/README.md`](../../../plans/README.zh.md)，子树的 orders 在 [`plans/AGENTS.md`](../../../plans/AGENTS.md)。这里记下的决定是这个载体本身，以及让它可用的几条规则：

- **计划是工作文档，不是决策记录。** 决定了什么、为什么，住在笔记树里，由计划引用。已经定下的决定绝不在计划里复述，于是两者不会漂成两份互相打架的说法。
- **状态是读出来的，不是写上去的。** 只有 `<slug>.md` 是*未开始*，两个文件都在是*进行中*，两个都不在是*已落地*。没有状态行，也没有生命周期目录，于是没有任何产物、任何读者会对交付走到哪一步产生分歧。
- **依赖是 `## Constraints` 里的一行** —— 等的是哪个交付，以及证明它已落地的命令。这条命令读的是 main 上的事实，不读计划代号、笔记或别处保存的状态；也没有任何轮询。
- **计划只在用户自己的信号下生效。** 在那之前，交付不做事：不组队、不建卡、不开工。阅读、探索和不产生副作用的验证属于规划，不算工作。
- **收口是折分支的合并准备。** 它删掉计划与工作副本，在同一次改动里把交付谈定的每个决定记成笔记，把仍未决的一项交给用户。两个文件都不进 main。

## Alternatives considered

**把交付记成 `proposed/` 下的一条笔记，而不是自建一棵树。** 它落败，因为笔记树是耐久决策的清单：一条笔记带生命周期目录、`Status:` 行和必须维护的对侧，状态一变就要换目录。计划是会被删除而不是被移动的临时工作材料；放进 `proposed/` 等于把工作文档混进一份「记下的决定就留在原地」的清单，而且它需要的恰恰是载体本想避开的那些目录搬移。

**写一条状态行，或者用生命周期目录，而不是读工作副本的有无。** 它落败，因为写下来的状态是文件已经携带的事实之外的第二个家。两者会不一致，而不一致时没有任何东西失败；`<slug>-progress.md` 的有无不可能和自己不一致。

**轮询依赖，或者把依赖状态存在计划旁边。** 它落败，因为轮询没有归属者，读的又是存在 main 之外的状态：前置条件失败的交付，看起来会和只是在等待的交付一样。开工时跑一次的那条命令，要么通过，要么具名失败。

**让计划作为耐久设计文档进入 main。** 它落败，因为合并准备已经把每个谈定的决定搬进笔记树。一份永不更新的第二份说法会和拥有这些理由的笔记争位，而保持与已交付事实一致的是笔记。

**现在就给计划加一道格式门禁。** 它输给了等待：计划少而短命，形状由契约承担，门禁会变成比它消除的风险活得更久的表面积。重新开启这个问题的条件是有名字的：等真的出现畸形计划，最省的形状是一道 `keys: ["markdown"]`、`selection: "files"`、只圈计划树的门禁。

## Acceptance criteria

- 本仓库的 `.agents/dsh-spec/plans/` 下有契约、它的中文对侧和子树 orders，且这份契约的配对完整。
- manager 的采用路径建出它落装的两个文件 —— `plans/README.md` 与 `plans/AGENTS.md` —— 并把带标记的计划段注入根 `AGENTS.md`。采用只写每份契约的英文侧，中文侧随包作为模板发布，也不建 sidecar；项目自己补上中文侧之后，它会随之同步并重录配对，而标记之外的内容保持不动。
- 没有任何产物写着交付状态：树里只有计划读作未开始，两个文件都在读作进行中，两个都不在读作已落地。
- 依赖命令读的是 main 上的事实；命令失败时交付具名停住，没有任何循环或 agent 代为轮询。
- 已经商定但尚未生效的计划，在用户开工之前不产生 worktree、卡片或实现。
- 合并准备在一次改动里删掉计划与工作副本，同时把每个谈定的决定记成笔记。
- 这次改动该跑的检查全部通过。

## Risks

- 计划不受任何门禁约束，于是畸形或过期的计划由读者发现，而不是由检查发现 —— 这正是推迟格式门禁留下的风险。
- 工作副本是交付运行期间手写的。停止更新它的交付，会在计划已经完成时仍报作进行中，而状态规则看不出这个差别。
- 丢在分支上的交付，连计划一起丢。计划提交在那条分支上、合并准备时删除，于是 main 既不留它当初想做什么，也不留它放弃了什么。
- 合并时删除，使计划在构造上就是临时的：合并之后的读者在笔记树里找到决定，却永远看不到产生它的顺序。这份损失被接受，工作副本是那个顺序存在过的唯一地方。
