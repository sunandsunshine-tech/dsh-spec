# Agent Note: 从一次应用四产物分析锻造 dsh-spec-workflow

Status: rejected — abstract meta-method prompts do not converge stably; concrete prompts win until the method can be formally checked

[English](2026-10-22-forging-dsh-spec-workflow.md) | 中文

## Problem

本仓库随附 agent team 工作流与技能锻造，却没有一套从目标、预算与环境推导工作流、再随真实结果修订它的方法。设计对话找到了闭环答案，而前两次锻造都偏了：第一次把它摊成框架形状的技能，第二次用的是一份更早、更浅的分析方法。驾驶员的第三次审查要求分析技能覆盖一切可结构化对象、修好格式，并在工作流技能被重新锻造前达到锻造技能的精度。本记录覆盖最终的锻造，其分析由完善后的 `dsh-spec-analysis` 按四产物格式产出。

## Proposal

把 `dsh-spec-workflow` 锻造成单文件、无 script 的 Agent Skill。它的层是全局释义、工作流要素模型、十五条全局准则、机制选择表、失败模式、六个 SOP 步骤与成果断言。每一步都有完成判断、检查方法和失败恢复。

方法的内容：工作流是把当前状态在约束与预算下朝已宣告目标推进的、推导出的可执行工作单元安排，连同让该安排可被判断并依据证据修订的验证与决策规则。技能固定循环——读懂情况、编排、执行、断言、重新决策、收尾——并把安排留给情况。三层断言把工作流可行性、运行进展与目标完成分开；两个决策范围让局部修正不会变成反复推翻，也让沉没成本留不住一条坏掉的计划；执行完整性保持状态、行动与结果可信；机制只在挣得其成本时才被选择。技能只在第 1 步点名 `dsh-spec-analysis`，用于不清楚的目标。

锻造采用采用者默认值：工作草稿用交付语言（英语），description 带中文触发；审查草稿用采用者语言（中文），带英文触发；记录为本 Agent Note；落地目标是 `skills/dsh-spec-workflow/`。技能不带 script：没有通用的状态 schema，固定账本会变成设计所否定的框架。

来源是题为「Agent编排本质与组合」的共享对话；本记录引用它，被锻造的技能不引用。与本文相关的内容已直接内联在这里，因此记录不依赖链接：

- 编排是对任务执行过程的闭环控制，而不是一份计划；闭环读情境、行动、验证进展，再重新决策。
- 工作流是推导出来的工作单元安排，不是固定流程。可以固定的是方法——理解、解构、处置、重组、断言、循环——具体安排随情境变化。
- 断言分三层：执行前的工作流可行性、执行后的运行进展、收尾时的目标完成。每个断言结果决定继续、调整、重新编排、询问还是停止，并说明作用范围。
- 机制（agent team、Ralph 循环、DAG、专职 agent、上下文隔离、单写入者）是可选手段，只有在值得其成本时才选择，并不构成工作流的定义。
- 有界调查、事实的单一权威来源，以及每个行动的完成判据、检查方式与失败处理可以迁移；锻造特有的刚性——固定 SOP 阶段、单一中央记录、不问规则——不能照搬。
- 对话后段明确命名了这套可迁移的元方法，并警告照搬锻造的领域流程是错误的做法。

### Workflow deconstruction

这是驾驶员要求在重组之前完成的四产物。它由完善后的 `dsh-spec-analysis` 产出。

**1. 对象定义。** 类别：工作安排。本质：目的为在约束下把当前状态朝目标推进；机制是表示情况、选择行动、行动、验证并重新决策的闭环控制。定义：工作流是把当前状态在约束与预算下朝已宣告目标推进的、推导出的可执行工作单元安排，连同让该安排可被判断并依据证据修订的验证与决策规则。正例：一个三单元计划，每个单元有可观察验证、运行断言，以及验证失败时修订计划的决策规则。反例：目标陈述没有安排；没有验证的活动清单无法被判断；请求逐字规定的流程不是推导出来的。边界情形：带成功证据的单一动作是退化的工作流，以最低深度运行。

**2. 要素与归属条件。**

| 要素 | 定义 | 归属条件 | 支撑的子句 |
|---|---|---|---|
| 目标与成功证据 | 目标条件，以及标记其达成的可观察结果 | 陈述一个目标条件与一项可观察结果 | 已宣告目标 |
| 情况模型 | 约束性与可权衡约束、预算、能力与限制、当前状态与影响决策的未知 | 记录上述各项，未知按影响与可决定性标注 | 约束、预算、状态 |
| 工作单元 | 改变状态的动作 | 每个点名动作、预期结果与验证 | 可执行安排 |
| 依赖 | 单元之间的顺序、数据、权威或资源关系 | 每个点名种类与它连接的单元 | 安排 |
| 验证 | 判断单元与目标的可观察输出 | 每个点名输出、它判断的单元结果与它贡献的成功证据 | 被判断的进展 |
| 断言 | 对安排、运行与目标的检查 | 三项检查存在：执行前、执行后、收尾时 | 被判断与修订 |
| 决策规则 | 从断言结果到下一个行动与范围的映射 | 每种结果映射到继续、调整、重新编排、询问或停止，并带范围 | 依据证据修订 |
| 权威状态与证据 | 下一个决策需要的事实与真实输出 | 每个事实带来源与版本；输出被保留 | 状态与修订 |
| 治理约束 | 写入所有权、身份与生命周期、任务上下文范围、权限与风险限制 | 每条适用于点名的单元或资源 | 约束性约束 |
| 预算 | 成本、时间与质量限制，以及其中的优化对象 | 陈述限制、优化对象与花费 | 预算 |
| 收尾与升级 | 带所需证据的单一终止状态 | 点名一个状态与支撑它的证据 | 被判断的完成 |

断言：覆盖（每个子句都有要素）、精确（没有多余要素）、划分（每部分属于一个要素）与等价（要素构成定义）。

**3. 关系、规则与重组方式。**

| 关系 | 判断条件 | 组合效果 |
|---|---|---|
| 目标到情况 | 情况模型引用目标与成功证据 | 界定情况 |
| 情况到单元 | 每个单元都被记录的能力、权限、约束与预算允许 | 界定执行 |
| 单元到依赖 | 依赖图有效，每个前置都在位 | 排列单元 |
| 单元到验证 | 每个单元恰有一项可观察验证 | 使进展可判断 |
| 验证到断言 | 断言汇总验证与成功证据 | 产出运行状态 |
| 断言到决策规则 | 每种断言结果映射到一个行动与一个范围 | 选择下一个行动 |
| 决策规则到状态 | 决策、证据与来源被记录 | 保持状态权威 |
| 治理到单元 | 写入所有权、上下文范围、身份与权限约束执行 | 保持行动受控 |
| 预算到情况、单元与决策 | 预算界定调查、执行与继续 | 保持花费在限内 |
| 断言与决策到收尾 | 恰好一个收尾状态连同其证据 | 诚实结束工作 |

规则：没有单元缺少目标追溯或验证；工作流断言有阻塞性未知时不执行；没有成功证据不收尾；机制可选；每个共享可变资源一个写入者；任务上下文取最小充分集；环境限制被陈述，不被假设。重组方式：框定目标、成功证据与情况（要素 1、2、8）；推导单元、依赖与验证（3、4、5）；在治理与预算下选择最简单结构与机制（9、10）；运行工作流断言（6）；执行并更新状态（8）；运行运行断言（6）；重新决策并记录（6、7、8）；收尾（11）。每一步都有输入、条件与输出。充分性：按此顺序构建的测试实例通过断言，且不需要未陈述的关系。

**4. 评判标准。** 来源路线：主流闭环规范（plan-do-check-act）适配 agent 工作，加上仓库的证据与单一写入者规范。

| 标准 | 定义 | 证据方法 | 优先级 | 来源 |
|---|---|---|---|---|
| 定义忠实 | 实例是推导的、可执行的、已验证的、可修订的 | 在实例上检查四项性质 | 必须 | 主流闭环实践 |
| 覆盖 | 每个目标子句都有单元，每个单元都有验证 | 子句到单元、单元到验证的矩阵 | 必须 | 目的推导 |
| 依赖有效 | 顺序、数据、权威与资源关系成立 | 依赖图检查 | 必须 | 主流实践 |
| 证据充分 | 每次声称的通过都有可观察输出，收尾状态匹配其证据 | 断言记录与运行输出 | 必须 | 仓库证据规范 |
| 修订能力 | 断言结果改变行动，决策范围被点名 | 第 5 步映射检查 | 必须 | 主流闭环实践 |
| 边界完整 | 约束、权限、预算、写入所有权与上下文范围成立 | 每个单元的治理检查 | 必须 | 仓库单一写入者规范 |
| 简单 | 结构是最简单可靠的，每个机制都有理由 | 机制到需要的检查 | 必须 | 目的推导 |
| 诚实 | 未验证项、风险与环境限制被点名，停止不被报告为完成 | 收尾状态复核 | 必须 | 仓库证据规范 |

充分性：每个定义子句与每个关系都至少被一条标准判断，且没有标准复述另一条。

**5. 断言与重组。** 定义、归属、关系与评判断言都在模型上运行过。技能从四件产物重组：定义到引言与释义；要素与归属条件到工作流要素表；关系与规则到全局准则；重组方式到六个步骤；评判标准到成果断言。技能自身的结构映照四件产物。

外部触发质量、冷启动和代表性任务效用尚未验证：本环境没有为技能的目标受众安装该技能的 harness。它们记录为缺口，不记为通过。

### Review and landing

四次审查修正塑造了这次锻造。第一次否决框架漂移、提高精度并缩短名称。第二次要求先完成分析方法，再从其四产物分析重新锻造工作流技能。第三次放宽分析方法的对象范围、修好格式并把它提到锻造技能的精度。第四次移除独立的自我分析表面，并把分析方法的抽取重建成每步一份 reference，因此本记录的分析是用完善后的方法重跑的。审查草稿在 `.agents/dsh-spec-skill-forge/review/dsh-spec-workflow/`，中文正文加英文触发。它提交给驾驶员，等待接受、修改或否决。落地把工作草稿复制到 `skills/dsh-spec-workflow/`，只删除本技能的草稿与审查目录，并把本 note 移到 `implemented/`。

## Alternatives considered

**交付带固定状态模型、注册表与写入租约的框架。** 它落败，因为应用分析把这些 schema 解除为原则；框架会限制它本应服务的编排。

**只保留原则，不写 SOP 步骤。** 它落败，因为只陈述原则的技能不给执行者完成判断、检查方法和失败恢复。

**与解构技能合并。** 它落败，因为驾驶员让两者独立；分析方法在意图阶段可选，不是工作流技能的基础。

**把 agent team 设为默认机制。** 它落败，因为分析把团队当作独立工作且需要分开角色时的选项，而不是方法的形状。

**把 Ralph 循环当作核心。** 同样落败：循环是方法可以选择的机制，不是方法本身。

**附带工作流账本脚本。** 它落败，因为不存在通用的状态 schema；分析的重组没有选择代码产物。

**保留名称 `dsh-spec-adaptive-workflow`。** 它落败，因为驾驶员的审查指出它太长；`dsh-spec-workflow` 保留前缀与工作流意图。

**两个被锻造技能共用一份记录。** 它落败，因为 `AGENTS.md` 按技能名命名记录，且两个技能各自独立验收。

## Acceptance criteria

- 工作草稿以给定参数通过 `verify-skill-spec.mjs` 的严格预算。
- 审查草稿把工作草稿转写为中文且不引入新概念，驾驶员接受它。
- 落地后 `skills/dsh-spec-workflow/` 等于被接受的工作草稿，本 note 位于 `implemented/`。
- description 在需要推导路径、有预算的多步工作时触发，在单一动作或请求已固定步骤时不触发。
- 十一个要素及其归属条件在技能中在场，且 `dsh-spec-analysis` 只在第 1 步被引用。

## Risks

- 它的触发边界与要求驾驶员显式请求的 agent team 工作流、以及锻造技能的规划阶段重叠；description 与否决行降低重叠，但触发质量尚未验证。
- 方法给执行者很大余地；准则 12 与 13 约束它，但弱模型可能询问得太晚或太少。
- 没有脚本，没有机械门禁强制预算核算、状态版本或写入所有权；方法依赖执行者的证据纪律。
- 应用分析只来自一次设计推演；在真实任务上再做一次，可能让要素在技能的层之间移动。
