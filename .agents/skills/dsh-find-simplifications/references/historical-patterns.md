# Historical simplification patterns

Use these to calibrate a candidate whose value an unused-symbol search does not settle. They are shapes that recur, each with the lesson that made it worth recording, not a current removal inventory. Where a project keeps decision records, read the specific record a candidate cites rather than following links out of a frozen one, and verify current owners and released-data obligations before applying a pattern.

## Require a complete effect path

A declaration, a serializer branch, and a test can form convincing-looking support without an effective feature. Trace both ends: something must produce the value, and an implementation must honour it. Reserved union members and cache hints with no emitter, and request knobs every adapter rejects, are deletions that include the declarations, the forwarding, the rejection-only tests, and the generated documentation.

Zero fixed callers is weaker evidence than unreachability. A deliberate third-party registration path can be preserved by a rejection even though the repository calls it nowhere, and for a catalogued service the generic plugin invocation and its returned values have to be inspected before the service is called dead. A working extension point and a field no provider can honour require different verdicts.

## Reduce distinctions where consumers decide

Map every public variant to the consumer action it enables. Several internal residency or state distinctions may need to project to one usable target, while internal routing keeps the identity that authorization and durability depend on. Two approximate capability registries can be replaced by truthful conditional wording, with exact availability left in the schemas that already carry it; the gain includes registration methods, disposal state, invalidation, and the combination tests.

Do not erase distinct durable facts merely because one renderer ignores them. Explicit start and completion markers may be needed for empty failed steps, crash repair, and inspection; simplify the projection, not the underlying distinction.

## Trade general behavior for a smaller explicit promise

A used feature can still be an expensive way to satisfy the required outcome. Giving up calendar recurrence and missed-occurrence replay can remove a parser, an evaluator, a cross-record gate, durable variants, and backlog states together; giving up automatic rollback can remove transactions while keeping failure reporting and consumer-owned activation checks.

State the loss as clearly as the deletion. A simpler recovery algorithm can be rejected because an unfinished unit of work may contain substantial real work; convenience, smaller unions, or fewer tests alone do not justify losing required data or behavior. A survey can propose the trade-off without implying permission to implement it.

## Make assumptions explicit at their consuming operation

Look for a local default that has acquired shared storage, synchronization, or confirmation machinery. Keeping a browser fact on the originating request and requiring an explicit zone in the scheduling operation removes stored defaults and cross-tab conflict state; leaving framing with the caller removes envelope controls threaded through unrelated layers. Both reduce the number of owners that must interpret one assumption.

Do not move a requirement past the place that must enforce it. Removing duplicate client-side validation is fine while the server keeps validating before lookup and invocation, and the documented cost — later failure on malformed input — is part of the proposal.

## Derive at use or reuse an existing delivery owner

For each cache or event subscription, ask when the consumer needs the value and whether an authoritative source already retains it. Reading the canonical prefix at use deletes a continuously copied buffer and its listeners; sorting current summaries deletes a persisted promotion history; reusing a shared stream and projection store deletes feature notifications, repeated reads, and a second membership cache.

The timing promise decides whether this works. Redaction at feedback time is not redaction at capture time, manual placement cannot be derived from activity timestamps, and an initial historical read may remain necessary when a baseline is absent. Name those residual obligations instead of declaring every cache redundant.

## Remove accidental composition owners

Inspect the actual launch and resolution paths before trusting a name such as demo, support, or example. Removing duplicate compositions and pass-through settings, assigning tests, guides and shipped assets to their owners, and replacing an inferred deployment policy with an explicit one can each delete a resolver-only workspace or a control service — while optional dependencies inside the same design stay.

A smaller package count is not sufficient evidence. Separate caller intents may have different ownership and completion timing, and a retained service definition may serve independent providers. Prove the replacement's real composition and dependency behavior, and account for the remaining configuration and lifecycle glue.

## Use rejected experiments to test parity claims

A replacement that deletes generic framing and its conformance tests is still a simplification when the provider-specific shim stays and the stricter truncated-tail behavior is documented. A nominally equivalent builtin is not, when it defeats deterministic fake-clock tests for a small deletion. An audit of dependency swaps distinguishes replaceable generic code from configured bounds, security rules, lifecycle ownership, and deployment behavior a library does not implement.

A past rejection is a scoped falsifier, not a permanent blacklist. Revisit it only with new evidence that addresses the failed premise, and measure the implementation, the glue, the tests, the dependencies, and the supported behavior together.
