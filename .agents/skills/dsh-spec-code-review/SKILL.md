# Reviewing a proposed change

**This skill is guidance, not a complete checklist.** Verify and fetch the proposed change's live base and exact head, establish the changed scope — the changed paths and any uncommitted, staged, or untracked work — then read the diff and enough surrounding code to understand the design. Use the project's declared scope tooling (when available, use the `dsh-spec-pre-push-checks` skill); derive the scope from version control otherwise. The scope output does not replace semantic review. Re-establish the base and rerun the scope step after a retarget or merge. Prioritize correctness, lifecycle, security, and broken required behavior over style; a short review with one substantiated blocker is better than a list of nits.

**Read the requirements before judging the diff.** Map the changed paths to the artifacts that own them, open each owning page listed under Sources of truth, and only then read the diff against those requirements. Judging a diff against memory of the rules is how a violation passes review.

## Sources of truth

The adopting project's standing instructions — its `AGENTS.md` (or the file it cites) — name the standards a change must satisfy. Read the standing instructions first; when the project has no standing instructions, read its README and module documentation for the same categories and record the gap. The categories below are what to find there, not fixed paths; the standards may live in standing instructions, documents, installed skills, or records, and the standing instructions say where.

- The standing instructions at the root and in each changed subtree: standing repository, module, and package authoring rules.
- The design or architecture rules the standing instructions cite: the requirements a change must satisfy and the habits behind them. Map each changed artifact to the page that owns it; read every page the diff touches.
- The documentation standard: placement and prose discipline.
- The prose standard the standing instructions name (when available, use the `dsh-spec-prose-standard` skill): required coverage and editorial judgment for comments, docs, prompts, and visible strings.
- The test-reliability rules it names: isolation and regression-proof requirements for resource-owning, asynchronous, or flaky tests and fixtures.
- The UI and UX rules it names, when the change touches product-user-visible GUI: for example feedback-surface choice, overlay safety, platform window adaptation, and visual token discipline.
- The error-handling standard it names (when available, use the `dsh-spec-error-handling` skill): failure classification, handling ownership, containment, state guarantees, and actionable reports.
- The testing policy and quality gates: the required test tiers and gates.
- The decision records and the contract beside them (when available, use the `dsh-spec-agent-notes` skill): design rationale. Treat disagreement with a decision record as a design discussion, not an automatic veto.
- The language and terminology policy, for paired or translated changes; an extended translation workflow (when available, use the `dsh-spec-translate-docs` skill) runs only when the project declares one and the user asks for it. Where the project declares no such policy, review the content on its merits.

## Blocking requirements

1. **New prose receives semantic review.** Apply the declared prose standard (when available, use the `dsh-spec-prose-standard` skill) to critically review every added or changed Markdown passage, API documentation, comment, prompt, description, diagnostic, and visible string. Verify required coverage, accuracy, placement, and editorial quality against the owning code or behavior; automated checks do not establish those properties. Where the project declares no prose standard, review the prose against the documentation rules it does declare and record the gap.
2. **Docs match the code.** Configuration, defaults, errors, wire fields, events, and public behavior update the documentation that owns them in the same change. Comments state non-obvious contracts; flag implementation narration, test walkthroughs, review history, and duplicated rationale for deletion or a link to their one home. Where the project documents no behavior, record the absence rather than inventing a documentation obligation.
3. **Documented vocabulary stays current.** A change to a documented type, interface, or core term updates the page that owns it in the same change, and any documented type block the project verifies mechanically is updated with it. Internal types need no such entry. Where the project documents no such vocabulary, record the absence.
4. **Contributions clean up.** Where the project has a registration, subscription, or effect mechanism, review the changed behavior and its consumers against the project's ownership rules: no process-wide or module-level singleton state whose identity or lifetime comes from module loading; every registered effect or subscription has a matching teardown that runs on disposal; a dependency needed to release other resources stays usable until the consumer has settled. Each new contribution passes the disposal expectations the project's owning rules state.
5. **Required evidence exists.** Verify the author ran the checks the standing instructions require for the diff (when available, use the `dsh-spec-pre-push-checks` skill to select them) and that CI covers the exhaustive matrix where the project has one; review the semantic gaps neither can detect. Where the project declares no checks, ask what evidence the change owes and record the absence instead of inventing a gate.
6. **User-facing copy is locale-owned.** Where the project declares user-visible copy and a localization mechanism: reject product text embedded in code, templates, helper returns, attribute strings, or primitive defaults; require the declared typed localization mechanism, the project's verification command, and behavior evidence in each affected locale; preserve the data outside the copy's ownership — user, wire, or model data — and code tokens verbatim. Where the project declares no such mechanism, the requirement does not apply and the review says so.

## Manual checks

- **Intent and interface contracts:** trace both sides of every changed interface. Confirm the implementation matches the proposed change and any decision record, including errors, cancellation, ownership, and disposal.
- **Error handling:** apply the declared error-handling standard (when available, use the `dsh-spec-error-handling` skill) to changed failure paths, including their state guarantees and final user-visible reports. Reject catch-and-continue unless the state owner establishes that subsequent work's preconditions hold, including after recovery. Where the project declares no standard, review the failure paths on their merits and say so.
- **Lifecycle and concurrency:** for async setup, callbacks, processes, or teardown, apply the declared design rules and check races before publication, cancellation during awaits, independent error reporting, callback containment, ownership before reentry, complete detach cleanup, and quiescent disposal.
- **Scope, ownership, and necessity:** first identify the required behavior behind each new distinction, field, adapter, state machine, option, defensive copy, and compatibility path. A requirement, check, or decision record introduced by the proposed change is a design choice to assess, not independent evidence of necessity. Compare the existing source fields, discriminants, and their consumers before accepting another representation; distinguish deleting a concept from relocating its declaration. Moving an unnecessary concept closer to its owner is not a simplification. Challenge unrelated features and speculative generality against the standing rules.
- **Capability and consumer fit:** trace every current consumer, then flag consumer-specific behavior leaking into the interface under the project's rules for its public surface. For required behavior, prefer an existing extension point near its producer or consumer when the local implementation adds little complexity; compare a producer-owned extension point with a change to a distant shared declaration. Flag the inverse too: a new public method on a generic service whose only caller is one internal consumer is an unnecessary API expansion — require a private capability closure handed to that consumer at construction.
- **Configuration and public choices:** trace authoritative reads and precedence before accepting another CLI or configuration pass-through; a forwarded value may be shadowed before use. Ask what current-consumer evidence or prior art supports each default, public operation set, format, or imported external concept. Require an explicit choice or deferral when that evidence is absent.
- **Machine-facing surfaces:** where the change touches a machine-facing surface, inspect the exact inputs, outputs, and diagnostics its consumer receives across affected modes — prompts and tool results for an agent, request and response fields for a service, output and diagnostics for a CLI. Flag concepts outside that consumer's task; verify stable text verbatim and dynamic behavior through snapshots or end-to-end coverage.
- **Enforcement:** follow every denial path to the operation that executes it; exercise direct and alternate callers that can bypass schemas, prompts, facades, wrappers, or listener ordering.
- **Retained and derived state:** every value the change keeps beyond the operation that produced it has one authoritative owner; every derived copy — cache, projection, notification, echo, replay, view — traces to that source and to the point where it is refreshed or invalidated. A copy that can drift from its source without that point is a second source of truth.
- **Bounds cover the final operation:** locate the owner of the complete emitted or retained result, including wrappers and metadata. Probe tiny and exact limits, oversized single chunks, and multibyte text for byte limits.
- **Real entry path:** where the project ships a launcher, binary, worker, or subprocess, tests exercise it. A fixture that mounts the module by hand does not catch an invalid entry contract.
- **Test strength:** assertions fail on the intended regression and verify external state, logs, events, or disposal rather than restating the implementation or trusting an agent's report. Coverage is necessary but not evidence that the scenario is correct.
- **Test reliability:** for a resource-owning, asynchronous, platform-sensitive, or flaky test, apply the declared test-reliability rules to the real worker or job topology, resource allocation, global-state restoration, synchronization, timeout budget, and quiescent teardown. Where the project declares none, record the gap and review the test's isolation on its merits.
- **Negative controls:** verify a deliberately invalid case fails through the real runner for each changed acceptance rule.
- **Decision records match shipped reality:** when a change implements a proposed decision record (when available, use the `dsh-spec-agent-notes` skill), move and rewrite it as present-tense shipped state in the same change, then verify paths, names, and mechanisms against the implementation.
- **Expected-output changes:** user-visible or machine-visible changes update the project's snapshots, or explain why no snapshot applies. Review expected-output diffs as behavior changes, not formatting noise.
- **Paired or translated content:** compare meaning and terminology on both sides (when available, use the `dsh-spec-translate-docs` skill for the update brief); a green pairing check does not prove translation quality. Where the project declares no paired content, the check does not apply.

## Reporting findings

State the defect, location, impact, and evidence. Place a localized defect inline on the tightest relevant diff range; use a change-level comment for cross-cutting architecture, scope, or review-wide synthesis. Separate blockers from suggestions and omit issues already enforced by a green gate. Use the existing review thread for replies. When receiving review, verify each claim and fix or rebut it on technical grounds without performative agreement.
