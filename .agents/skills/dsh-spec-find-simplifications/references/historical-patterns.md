# Historical simplification patterns

Use these examples to calibrate a candidate whose value an unused-symbol search does not settle. They describe recorded decisions, not current removal opportunities. Verify the current owner and the released-data obligations before applying a pattern. Archived records are frozen snapshots, not current authority: never inspect, verify or repair their outbound links.

## Require a complete effect path

A declaration, a serializer branch and a test can form convincing-looking support without an effective feature. Trace both ends: something must produce the value, and an implementation must honor it. A recorded decision removed reserved union members and cache hints that no emitter produced; another distinguished request knobs that every adapter rejected from working request fields available to hooks. The deletion covered declarations, forwarding, rejection-only tests and generated documentation.

Zero fixed callers is weaker evidence than unreachability. A recorded decision preserved a deliberate third-party registration path despite no in-repository caller. For catalogued services, inspect generic plugin invocation and returned values before calling them dead; a working extension point and a field no provider can honor require different verdicts.

## Reduce distinctions where consumers decide

Map every public variant to the consumer action it enables. A recorded decision gave consumers a single usable selection and projected several internal states to the same availability, while internal routing kept the distinction it needed; another replaced two approximate capability registries with truthful conditional policy wording, while exact availability stayed in the schemas. The gain included registration methods, disposal state, invalidation and combination tests.

Do not erase distinct durable facts merely because one renderer ignores them. A recorded decision kept explicit start and completion facts needed for empty failed steps, crash repair and inspection, and simplified the projection instead. Simplify a projection only when the underlying distinction remains necessary.

## Trade general behavior for a smaller explicit promise

A used feature can still be an expensive way to satisfy the required outcome. A recorded decision gave up calendar recurrence and missed-occurrence replay for a fixed-rate schedule, removing a parser, an evaluator, a cross-record gate, durable variants and backlog states. Another gave up automatic rollback in a non-transactional extension loader while keeping failure reporting and consumer-owned activation checks; moving generic rollback to another package would have retained its cost.

State the loss as clearly as the deletion. A recorded rejection kept a more detailed recovery algorithm because an unfinished unit of work can contain substantial real work. Convenience, smaller unions or fewer tests alone do not justify losing required data or behavior. A survey can propose the trade-off without implying permission to implement it.

## Make assumptions explicit at their consuming operation

Look for a local default that has acquired shared storage, synchronization or confirmation machinery. A recorded decision kept browser facts on the originating request and required an explicit time zone in the scheduling operation, removing stored defaults and cross-tab conflict state; another left framing with the caller and removed envelope controls threaded through unrelated layers. Both reduce the number of owners that must interpret one assumption.

Do not move a requirement past the place that must enforce it. A recorded decision removed duplicate client-side schema execution but kept server-side validation before lookup and the business operation, plus local arity and binding checks; its documented cost is later malformed-input failure and the loss of client parsing as accidental redaction.

## Derive at use or reuse an existing delivery owner

For each cache or event subscription, ask when the consumer needs the value and whether an authoritative source already retains it. One recorded decision reads the authoritative record at the point of use instead of maintaining a continuously copied buffer, deleting that buffer and its listeners. Another sorts current entries instead of persisting promotion history, while explicit user ordering remains separate state. A third reuses a shared stream and projection store instead of a second membership cache, removing change notifications and repeated reads.

The timing promise determines whether this works. Feedback-time redaction differs from capture-time redaction; manual placement cannot be derived from activity timestamps; an initial historical read may remain necessary when a stream baseline is absent. Name such residual obligations instead of declaring all caches redundant.

## Remove accidental composition owners

Inspect actual launch and resolution paths before trusting names such as demo, support or example. A recorded decision removed duplicate compositions and pass-through settings where the actual loading behavior put the override; another removed a module-resolution-only workspace by assigning tests, guides and shipped assets to their owners; another used explicit deployment policy instead of inferring it from an installed provider or a neighboring tool, while preserving optional dependencies internally.

A smaller package count is not sufficient. Separate caller intents may have different ownership and completion timing, and a retained interface may serve independent providers. Prove the replacement's real composition and dependency behavior, and account for all remaining configuration and lifecycle glue.

## Use rejected experiments to test parity claims

A recorded parser replacement deleted generic framing and its conformance tests while retaining the protocol-specific termination shim and documenting stricter truncated-tail behavior. In contrast, a recorded rejection found that a nominally equivalent builtin defeated deterministic fake-clock tests for a small deletion. A dependency-swap audit distinguished replaceable generic code from configured bounds, security rules, lifecycle ownership and deployment behavior a library does not implement.

A past rejection is a scoped falsifier, not a permanent package blacklist. Revisit it only with new evidence addressing the failed premise, and measure the implementation, glue, tests, dependencies and supported behavior together.
