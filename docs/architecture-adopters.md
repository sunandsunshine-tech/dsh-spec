# 架构

本文档面向采用者，界定本机制集合的契约边界、核心不变量及组件协同逻辑。

维护者视角下的代码分工参见[架构：维护者视角](architecture-maintainers.md)，代码仓库布局见 [README](../README.md)。

## 1. 价值主张、不变量与公理

### 1.1 它为了什么

集合由配套的命令行工具驱动，入口见 [README](../README.md)。它做三件事——把一个项目初始化为采用态、把规范与受管文本更新到当前修订、执行项目所声明的自动化检查。命令怎么用由工具自己的 `--help` 与参考页负责。

**会话是有界的，项目不是。** agent 的上下文有限、活不过会话，而项目活得比碰过它的每一次会话都久。由此有两个必然失效，且都不是工具缺陷：

1. **决策与方向在会话之间丢失。** 下一次会话分不清哪些已经定下，于是重新推一遍——或者把它推翻。
2. **上下文被污染。** 过期的计划、会话叙述、中间态留在树里，下一次会话把它们读成现状。

整座架构只为这件事而建：给一个项目一处耐久的地方，存放一次变更必须承载的东西——为什么走这条路、放弃了什么、什么能证明它。于是人或 agent 能在许多次会话之间朝一个长期方向工作，而每次迭代都可复现、稳定。

一句话：*项目记得的东西，分布在许多短命的执行者身上。*

### 1.2 四条不变量及其取舍

整套机制由四条不变量守护。前三条面向采用者的核心诉求，第四条让它们成立：

| # | 不变量 | 没有它会怎样 | 什么在维持它 |
|---|---|---|---|
| 1 | **单一真值源。** 一个事实一个家，其余从它派生。 | 同一事实记两处就会漂，漂到公开处才被发现。 | 每一类事实各有唯一的真值归宿：决策在 `notes`、进度在 `plans`、语言在术语表、受管文本在集合发布的那一份。 |
| 2 | **主干只有现状。** 中间态在主干上不存留。 | 去年的计划被读成今天的意图。 | 临时工件在合并前整理时清除；决策被吸收进耐久记录。 |
| 3 | **区别可见。** 读者一眼能分当前与历史。 | 过期与现行的东西并排躺着。 | 生命周期状态可读：状态行、目录、封冻清单。 |
| 4 | **系统能自证。** 每条义务有一个可执行判据。 | 正确性取决于谁记得那条规矩。 | 一个门禁由两个要素组成：**记录中的名字**与**背书它的那个程序**。缺了哪一个，工具就把缺的报出来并中止，什么都不运行。 |

**第四条是地基。** 没有它，前三条只是意向；所以在这个仓库里，**一条判不了的规矩等于没人拥有它**。

**不变量 2 刻意采用物理表述：** *中间态不存留*。若换成*只清除下一次会话不再需要的内容*，听起来更准，却把一个谁看都一样的约束换成取决于意图解释的准则。

**一条刻意的例外。** 收口时允许把一个未决事项合入主干，形态是一条 `proposed` 笔记。它看着像中间态，其实不是：`proposed` 是**决策的一个状态**（已决定、尚未建成），不是工作的残留；它带着它的理由与验收标准进入主干，正因如此下一次会话读得到它、而不必重推一遍。判据的分界在这里——**留在主干的是决策，不是进度**。进度（计划、工作副本）在收口时消失。

### 1.3 两条公理

**关系公理——释放，而不是调用。** 集合从不运行一个项目，它往项目里**释放**：钩子、契约文件、能力目录。钩子是指针，定义在集合发布的契约里，而实例归项目。依赖只有一个方向：项目依赖集合。

**分层公理——内核随包生效，切面各自可选。** 内核是**决策的那套机制**（笔记）连同其配套执行技能、钩子与契约：它随集合安装即生效，不可拆分，也不是一个可以挑选的项——**内核不可单独拆下**，退出采用是整体退出，移除只针对内核之外的切面。内核之外的一切皆为可选切面：上游提取的技能虽随包分发，采用者仍可按需取舍，其有无不影响内核的完整。可选面之间的关系写成契约里的条件句，不是安装器里的依赖。

## 2. 采用态拓扑：装进项目长什么样

根据「释放而非调用」公理，集合进入项目后，项目的空间被划分成两部分：**集合写下的文件**与**项目自持的内容**。集合在升级时按规则刷新自己释放的受管文本；项目自持的内容由采用者全权拥有，更新过程遇到人工修改会中断报错，不予覆盖。

```
你的项目/
├── AGENTS.md                你的常驻指令 ＋ 集合渲染的三个钩子块（笔记／计划／规范红线）
├── .rgignore                让归档笔记不进入递归检索
├── .agents/
│   ├── skills/              安装的集合本身（多集合共享，按元数据认领）
│   └── dsh-spec/
│       ├── notes/           契约 ＋ proposed/ implemented/ rejected/ archived/
│       │                    （每条笔记由中英双语正文与一份记录构成）
│       ├── plans/           契约 ＋ <slug>.md ＋ <slug>-progress.md
│       └── norms/           norms.md（生成物）＋ applied.yaml（哈希记录）
└── docs/
    ├── terminology.md       双语术语表（语言维度的真值源）
    └── AGENTS.md            这份表的规矩
```

**三个钩子块长这样**（`AGENTS.md` 里，成对标记之间是集合写的，之外是你的）：

```
<!-- dsh-spec:agent-notes -->  … 笔记树在哪、怎么写一条  <!-- /dsh-spec:agent-notes -->
<!-- dsh-spec:plans -->        … 计划树在哪、怎么开工    <!-- /dsh-spec:plans -->
<!-- dsh-spec:norms -->        … 你选了哪些规范的红线     <!-- /dsh-spec:norms -->
```

标记块是**指针**：它指向定义，自己不是定义。**块落在根上。** 集合只往根那份指令文件里写；至于多份指令文件之间如何合并，由采用者所用的运行环境按它自己的规则处理，集合不假定也不干预。

## 3. 核心组件与反转控制

组件按**信息的寿命与变化频率**划分——不是按它们由什么构成。契约、钩子、能力、判据是机制手段；一个组件用其中哪几样维持自己的不变量，是它的实现选择，不是划分它的依据。

| 组件 | 寿命 | 层级 | 它覆盖哪一段，交给谁 |
|---|---|---|---|
| `notes` | 跨交付 | **内核，随包生效** | **交付结束它仍在**，被下一次交付读取；`implemented` 成为后续前提，`rejected` 挡住重复的诱人错误 |
| `plans` | 单次交付 | 自研，可选 | **从构建到收口**；执行中产出的决策移交给 `notes`，收口时把"现实改动了什么"移交给复盘 |
| `norms` | 跨项目，常驻 | 项目从中选择 | **全程**，从计划构建到合并；约束其余三者，自己不产出工件 |
| `skills` | 按需加载 | 笔记配套的必然安装；其余随包或可选 | **某一刻被加载，用完即退**；它是做法，不改状态，状态的改变由前三者承载 |

四个组件不是并列的功能块，而是一条链上的四段。接缝处的传递是这条链的关键：**谁在什么时候把什么交给下一步**（上表最后一列）；至于接缝上的位置由谁来填，下面那条 IoC 规则交代。

```
norms ──(全程约束)──▶ plans ──(产出决策)──▶ notes ──(引为做法)──▶ skills
                        │                     │
                        ├─(现实改动)─▶ 复盘   ├─(做成了)──▶ implemented
                        │                     ├─(被否决)──▶ rejected
                        │                     └─(失去指导)─▶ archived
```

### 3.1 IoC：契约规定接口，实现由谁提供

**契约固定位置与语义，实现留给采用者。** 以计划的任务规划部分为例：契约规定这几个位置必须存在，并规定各自回答什么（团队怎么配、工作怎么排、卡怎么分），但**不规定它们填成什么样**。填法取决于谁来做这件事。三个角色因此各管一层：

1. **契约管位置与语义**：这几个位置叫什么、在哪、各自回答什么；交付的收口处要有一个审查环节；决策要沉淀。
2. **集合管一个默认实现**，且以**可选**形态提供：让采用者开箱可用，而不是替他决定。
3. **采用者管实现**：取用默认的、换成自己的、或者不提供，三种都合法。

**采用者交付实现的方式，由他在自己的 `AGENTS.md` 里声明。** 那处位置按什么要求办、或交给哪个技能去办，两种写法都可以——把要求直接写在那里，或者只写一行指向那个技能。这两个文件因此各说一半：契约说这个位置要有东西，项目的 `AGENTS.md` 说这里的东西由谁负责。后者是项目自己的常驻指令文件，也是集合的钩子落下的地方。

**契约不需要知道那一行写了什么，只需要那个位置有人负责。**

**不提供时不干涉**：那个位置就是空的，机制不启动，集合不报错也不代填。这是"释放而非调用"的直接后果——集合不在采用者的项目里替他做决定。

| 契约规定的位置 | 集合的默认实现（可选） | 采用者可以 |
|---|---|---|
| 计划的任务规划部分 | 团队工作流技能 | 取用／换掉／留空 |
| 收口的审查环节 | 验收＋评审（登记在 PR 生命周期技能里） | 取用／换掉／留空 |
| 交付计划机制（plans 面） | 契约＋工作副本（释放进项目） | 取用／换掉／留空 |

前两行的默认实现都是**技能**：装了团队工作流就按它的要求填，没装就按采用者自己的设计要求填；PR 生命周期同理。它们落在技能这一层，因为技能是按需加载的做法，而扩展点要的只是"这里有人负责"。

**技能本身不属于契约扩展点。** 扩展点解决的是"某个流程位置由谁负责"，而技能是"按任务需要即时调用的工具"——加载由任务驱动，不由交付结构决定。两者性质不同：采用者可以只用随包技能，也可以带自己的技能进来，互不排斥。

### 3.2 `notes` —— 决定过什么、为什么

**一次交付的抽象就长在这里**：笔记在四个状态之间流转，而这就是"一次交付"本身。

```
proposed ──▶ implemented        做成了：决策成为当前真值，并持续与现状保持一致
    │
    └─────▶ rejected            提案被否决：冻结为负向知识

implemented ──▶ archived        日后不再指导任何事时封冻
```

**`notes` 是本集合唯一整类都来自上游的组件**，而且它的**机制自身闭环**：四个状态不依赖任何其它组件。因此一个采用者**只用笔记，就已经拥有一套完整的交付闭环**。

| 状态 | 它是什么 | 何时移动 |
|---|---|---|
| `proposed` | 已达成的决策，尚未建成。 | 在计划成形时写下，或在执行中发现决策时写下。 |
| `implemented` | 已经发布的东西。 | 工作落地时；此后靠**改准事实**保持与现状一致，绝不改写判决本身。 |
| `rejected` | 一个**曾被提出、后被否决**的决策（它是提案冻结后的形态，不能直接写成一条 `rejected`）。 | 提案被否决时，只给 `Status:` 加一行理由并冻结；只在它的理由还能挡住一个诱人的错误时保留。 |
| `archived` | 已被取代的记录。 | 日后某次交付发现它不再指导任何事时；此后封冻，门禁不再读它。 |

没有从计划直接写成一条笔记的写法——笔记只从提案转来，这正是笔记机制自身的形状。

笔记的文件格式、类别与归档规则由笔记契约拥有。它来自上游提取，因此与它来自的那一版对齐。

### 3.3 `plans` —— 这次打算做成什么样，以及实际走到了哪

`plans` 是上面那个抽象的一个**参考实现**，不是它的骨架。集合提供它，是因为一个只带笔记的项目仍缺"这次要做成什么样"的冻结意图与"实际走到哪"的活记录；但采用者可以不用它，也可以用自己的方式满足同一抽象。

**一个组件，两个部分**，像笔记的四个状态同属一个组件那样；两个部分不能单独选择：

- **`<slug>.md`，计划。** 开工时冻结、此后不再改动，从而始终是"现实拿去对照"的那个东西。它带摘要、背景、目标、约束、引用、设计、团队、拓扑与预规划卡——形状固定，内容归交付自己。计划在构建阶段定稿，并与各项提案一同提交到分支，等待开工信号。
- **`<slug>-progress.md`，工作副本。** 寿命与工作等长，分两半：**上半是计划的修订副本**，每阶段的偏差折进来，所以任何时刻读它就知道当前方向，不必读历史；**下半是阶段记录**，每阶段收口时精炼成两样东西——*完成了什么*，以及*校准到了什么*（哪条判据变了、为什么、哪次尝试失败了）。

一个阶段是一个循环：记下本阶段要做什么 → 调度工作，同时记下要紧的事 → 把偏差折上去、把记录精炼下来。**阶段记录刻意不是流水账：** 修订副本越改越准，阶段记录按期收口。计划完成时，冻结的计划与修订副本之间的差异，正好是现实改动了什么——**那就是复盘**。

**阶段记录里那两样东西是刻意并列的。** "完成了什么"记录产出，"校准到了什么"保存过程校准：当初的拓扑、卡片划分与工期估计为什么在现实摩擦下失效。后者既不是系统决策（进不了笔记），也不是未完成的工作（不会变成新计划）；一旦丢掉，交付换来的对系统复杂度的体感就无处可寻。

**中途停工不设状态。** 一次交付暂停——等一次讨论、等一个依赖、插播一次紧急修复——就是暂停，不需要额外区分。但**基底变了**要分流：

- 计划的**意图仍成立** → 冻结的计划**不动**，在工作副本里**加一个阶段**；该阶段本身就是"基底变更"，偏差因此有据可查；
- 计划的**前提被推翻** → 这已不是调整：把两个工件一并删掉，不留给下一次会话一个像"未开工"的残迹；各提案的流转按交付流里那条定义清算。若方向仍在，另立一份新计划。

不修改冻结的计划，是因为它是唯一的对照物；改掉它，复盘就没有基准。

**未决事项**——执行中发现、不影响当前工作、但需要有人过目的东西——记在工作副本里，寿命与交付等长：它不独立成一个组件，也不进笔记（它不是决策）。它的归宿是收口的第二条准出条件。

### 3.4 `norms` —— 什么绝不能做

跨会话、跨项目的不变量。集合发布一份目录；项目从中选择，选中的规则落进项目自己的树（它可以在那里编辑），钩子再把它们的红线渲染进项目的指令文件。目录是数据：每条规则有稳定的 id、分组、规则本身、为什么是规则、如何察觉自己正在违反它，以及哪份文档拥有它的理由。

`norms` 按定义是常驻内容。这正是它与其余一切的分界线：**带着流程的规则不是红线**。红线陈述"什么绝不能发生"，一两句话说完；流程陈述"动作的次序"，属于按需加载的能力。这条缝对应一对经典区分：红线是安全性——一个针对状态快照的、可以纯函数判定的边界；流程是活性——状态在时间上的迁移路径。

### 3.5 `skills` —— 一件事怎么做

技能一律**按需加载**——这是它这一类东西的固有性质，与装不装、选不选无关。一次会话开始时只有常驻指令在上下文里；某个技能在它被需要时才进来，用完即退。所以这一层不需要额外说明"什么时候用"。

**不要把它与可选混为一谈**：按需加载说的是**运行时怎么进来**，可选说的是**采用时拿不拿到**。两回事，两个轴：

| 轴 | 它决定什么 | 取值 |
|---|---|---|
| **采用时** | 你有没有这件能力 | 笔记的配套技能**必然安装**；自研的**由你选** |
| **运行时** | 它什么时候进上下文 | **一律按需加载**——技能这一类都是如此，与上一条无关 |

**采用这一轴上的分界，只问一个问题：它承载内核吗？**

- **承载内核的**：笔记的配套技能。它与机制一起来、必然安装：它承载笔记状态机要走的那些动作，缺了它，机制无法闭环。
- **不承载内核的**：其余全部。它们随包自带或由采用者选，但都只是做法，用完即退。上游提取的那些与它来自的那一版对齐（差异只许有出厂布局要求的引用改动、或去掉某个项目专有内容的泛化两种，来源与许可面**永不泛化**）；集合自研的那些各自独立，两者之间若有关系，写成契约里的条件句。

本仓skills如下，按来源分两档列在下面。

| 来源 | 名称 | 作用 |
|---|---|---|
| 上游提取 | `dsh-agent-experience` | 设计 agent 工具、技能与工作流，让信息可被发现、上下文用在刀刃上。（上游名为 `agent-experience`） |
| 上游提取 | `dsh-archive-agent-notes` | 审计、修剪、归档与恢复决策记录。 |
| 上游提取 | `dsh-translate-docs` | 双语文档的翻译工作流与配对校验。 |
| 上游提取 | `dsh-code-review` | 把评审人带到本仓库的标准上，并做代码本身看不出的评审检查。 |
| 上游提取 | `dsh-find-simplifications` | 找出有证据支撑的简化，写成或合并成提案。 |
| 上游提取 | `dsh-pre-push-checks` | 推送前挑出覆盖本次改动的最小检查集合。 |
| 上游提取 | `dsh-prose-standard` | 判断各类文本该写成什么样、哪里的注释与文档是必需的。 |
| 上游提取 | `dsh-trim-cot-leakage` | 清理读起来像泄漏推理过程的文本。 |
| 自研 | `dsh-spec-manager` | 集合的引擎：初始化采用态、安装与更新技能集合、挑选规范、运行检查。 |
| 自研 | `dsh-spec-team-workflow` | 把一次多步交付当作团队来做，每项义务都有对应门禁。(plans-IoC-任务规划) |
| 自研 | `dsh-spec-pr-lifecycle` | 走一次改动的 PR 生命周期：开发／验收／评审／合并四态。(plans-IoC-收口审查) |

### 3.6 与组件配套的东西怎么交付

四个组件不是同一种东西，而它们的**配套机制**也以两种方式交付——这一层分清了，才能回答"我到底会拿到什么"。

| 组件 | 配套机制怎么来 |
|---|---|
| `notes` | **有原生配套技能，且是捆绑的**：笔记机制与它的配套技能都来自上游，随包自带，**采用时必定安装** |
| `plans` | **释放性**：`plans/README.md` 与 `plans/AGENTS.md` 两份契约**释放进项目**，两个部分（计划与工作副本）随之成立；它不配套一个专属技能 |
| `norms` | **目录 ＋ 渲染**：集合发布规范目录，项目从中选择，钩子把红线渲染进项目的指令文件 |
| `skills` | **就是能力本身**：上面那一节 |

**笔记机制是最小内核，随采用原子生效。** 它植入钩子，钩子被读，机制即生效——没有"装了但停用"这一档，也没有可替换的实现：配套技能就是执行这套闭环的做法，与机制一起来。其余的面与技能是**挂载在这个内核上的可选切面**。

由此，采用本集合即确立一个基于笔记的跨会话决策真值源；其余机制都建立在这个底座之上，脱离它而只引入零散技能不在本架构的保证范围之内。

**为什么三种"缺失"不能统称"都可以选"**：

| 缺失 | 落在哪 | 机制是否在场 | 代价 |
|---|---|---|---|
| 不选某条规范 | 数据——目录里挑行 | 机制始终在场 | 低（配置级） |
| 不装某个自研面 | 领域——状态机挂载与否 | 该面缺席 | 中（决定一次交付以何种形态推进） |
| 不加载某个技能 | 运行期——按需即退 | 不留状态 | 零 |

统称"可选"会把这三层压成一层，掩盖它们在代价上的差别：挑行是配置，卸载一个面是拆结构。

## 4. 交付生命周期

### 4.1 一次交付怎么流

一次交付从想法走到落地，经过的位置与每个位置留下的东西如下。

```
想法 ──▶ 计划构建：建一个分支，计划与提案都落在这里（否则它们无处落脚）
           ├─ 与用户讨论、逐轮收敛，直到双方同意
           ├─ 已达成的决策就地落为 proposed 笔记（决策不留在对话里）
           └─ 构建由规划角色承担：装了工作流则直接扮演 lead；
              没装则遵从采用者自己在工作流中设定的规划角色
    │
    ▼ 用户发出开工信号（计划在此之前不产生任何工作）
冻结 <slug>.md（对照物，此后不改）──▶ 建 <slug>-progress.md（上半修订副本／下半阶段记录）
    │
    ├─ 每阶段：记要做的 → 调度（记要事）→ 折偏差、精炼记录（完成了什么＋校准到了什么）
    │           随时：读修订副本知方向；与冻结计划 diff 知偏离
    │           执行中发现的决策落为 proposed 笔记
    ▼
收口：跑门禁 → 审查（验收＋评审）→ 未决清空、决策落笔记
    │
    ├─ 复盘：拿冻结的 <slug>.md 与修订副本对比
    │        └─ 差异＝现实改动了什么；阶段记录里的"校准到了什么"提供过程视角
    ▼
复盘若需整改 ──▶ 落为 proposed 笔记，或另起一份新计划（整改由此开始）
复盘若无整改 ──▶ 无事发生，不留产物
    │
    ▼
删除计划与工作副本（决策已落笔记，复盘已发生）
    │
    └─(前提被推翻)─▶ 两个工件一并删除；各提案各走各的迁移（否决的入 rejected，仍成立的入 implemented）
```

**计划构建在开工之前，并且需要一个落脚点。** 构建发生在一个分支上：计划本身、以及讨论中定下的 `proposed` 笔记都提交在那里——否则它们在开工之前无处可存。构建由**规划角色**承担：装了工作流，这个角色就是工作流里的 lead；没装，则遵从采用者在自己工作流里设定的规划角色（IOC：集合给参考，采用者给实现）。

讨论中已经定下的决策**当场**落为 `proposed` 笔记——契约的判据是"会话里达成的结论要落成提案，否则它只活在那一场对话里"。用户发出开工信号之前，交付**不进入实质执行**：不建交付专用的工作树、不建卡、不组建持久团队。

**但探索是允许的**，它的边界与工作一样清楚：**只调研，不变更生产源**——这与负责交付的人所受的那条限制是同一条。

探索通常由**要用这个结论的人就地完成**，信息因此最内聚：不会出现一次转述。临时的探索角色则是并行的探索版 lead，把情况摸清、把结论交回来；真正的改动仍由负责交付的人完成。

契约禁止的是**未获授权就开工**，不是未获授权就了解情况。

**复盘严格发生在删除之前。** 阶段记录里的"校准到了什么"在此刻提供过程依据，让复盘能定位先验估算与现实摩擦的成因；据此识别出系统性偏差，就沉淀为一条 `proposed` 笔记或另立一份新计划，否则收口即结束、不留中间产物。

复盘之后，两个工件被移除；留下的东西是笔记（决策）、rejected（负向知识）与交付物。**移除由谁执行、用什么命令，属于采用者自己的工作方式**——机制只规定它发生在收口之内、审查之后。

**计划被移除不是交付的一个状态。** 契约只认三种读法：只有计划＝未开工，计划与工作副本并存＝进行中（in flight），两者都不在＝已落地。一份进行中的计划若前提被推翻，做法是把两个工件一并删掉，而不是把它转成第四种状态；删掉之后工作区读作已落地——**这只说工件不在，不说这次交付做成了**，它的结论落在笔记树里。需要区分的是**提案的迁移**：构建与执行中产出的每个提案各走各的——被否决的从 `proposed` 移入 `rejected`（只给 `Status:` 加一行理由并冻结该文件），仍成立的照常进入 `implemented`。

这条流是**参考实现**：采用者可以只用笔记（那本身闭环），也可以用自己的方式满足交付抽象。

### 4.2 三条准出条件

**一个交付要走向落地，除任务完成外还必须满足三条准出条件**：

1. 谈定的每个决策已落进笔记；
2. **未决事项已清空**——交给用户，由他当场裁决、要一条 `proposed/` 笔记先承载它，或者另立一份新计划；
3. **收口前跑门禁，并经过审查**。门禁是这条时间轴上的一个**硬性拦截点**：交付在提请收口之前，必须全数通过这个项目配置的检查；任何一项不通过，即阻断准出。由谁在什么时刻触发它，属于采用者自己的工作方式（有 PR 生命周期时，它落在那个生命周期的状态里）。
   审查则是**验收与评审两个步骤**——实现者验收交付，仓库维护者评审——两者是不同的行为，各自需要被请求与答复。集合若未提供它，该环节由采用者自己提供，集合不干涉。

第三条是刻意的：可执行的那一半由门禁保证；剩下"这次收口有没有漏掉一项未决"取决于人的判断，判不了，只能审。架构因此只要求两件事——**审查这个环节存在**，并且**它发生在删除之前**。

### 4.3 多个交付同时进行

状态由**文件是否存在**读出，不写状态行：

| 计划树里 | 读作 |
|---|---|
| 只有 `<slug>.md` | 未开工（在等信号、等讨论、等一个依赖） |
| `<slug>.md` ＋ `<slug>-progress.md` | 进行中（in flight） |
| 都没有 | 已落地 |

**只用笔记的项目里，状态长在笔记上。** 上面这套读法是 `plans` 面的；若采用者没装它，同一条时间轴仍然成立，只是标记落在笔记的四个状态上：一条决策处于 `proposed` 就是进行中，转到 `implemented` 就是落地，被否决则 `rejected`。

因此**同一时刻可以有多个 `<slug>` 各自处于不同状态**，而每一个的状态从它自己的两个文件读出，不需要任何中心登记。

**并发发生在分支上，不在主干上。** 每份交付在自己的分支上展开：计划与工作副本随那条分支走，主干只在它落地时接受结果。所以多个 `<slug>` 同时"进行中"，指的是多条分支各自带着自己那一对文件——它们互不覆盖，因为每个只碰自己的两个文件；而主干任何时候只看到已经落地的东西，不变量②因此不被触碰。

**决策侧不需要隔离，因为它本来就是共享的**：`notes` 是跨交付的，两份交付产出的决策都落进同一棵树。这不是冲突，而是它的用途——第二份交付读得到第一份定下的东西。

## 5. 治理契约与升级保护

### 5.1 双语：术语表是语言那一侧的真值源

机制的文字往往成对出现——同一份契约有中英两侧。**两侧共用的词由一张表定死**：`docs/terminology.md`，英语原词一列、中文一列、首次出现时的说法一列。它解决的是同一个词在两侧被译成不同说法的问题，所以它是**语言维度的真值源**，与四个组件不是同一类东西——它约束的是文本，不是交付。

它的归属照旧是两半：**表头与行是项目的**（加一行、改一个译法是采用者的决定），说明段是集合的。表随项目长大，集合不碰它写过的行。

它对**配对**生效：成对的文本由机器判据校验两侧是否对齐；单侧发生变更而对侧未同步，检查会报出来。所以这张表不是倡议，是判据。

### 5.2 外部规格对齐

**为什么对齐外部规格，而不是采用集合自有的格式？** 如果指令面与能力面用本集合私有的格式，采用者就被绑在这套工具链上——读它的 agent 得先装它，写它的项目换不走，一个事实因此有了第二个家。所以这两层各自对齐一个**开放、无版本号、由外部托管**的事实标准（其发布页即真值）：指令面对齐 AGENTS.md，能力面对齐 Agent Skills。

| 内容 | 规格 | 要求（其发布页即真值） |
|---|---|---|
| **项目指令文件** | [AGENTS.md](https://agents.md/) | 标准 Markdown、**无必填字段**，标题随写；由 Agentic AI Foundation（Linux Foundation）托管 |
| **能力** | [Agent Skills 规范](https://agentskills.io/specification) | 一个目录至少含 `SKILL.md`（另有可选的 `scripts/`、`references/`、`assets/`）；`name` 与 `description` 必填——`name` ≤64 字符、仅小写字母/数字/连字符、不以连字符开头或结尾、无连续连字符、**须与父目录同名**；`description` ≤1024 字符；`license`、`compatibility`、`metadata`、`allowed-tools` 可选 |

**随包自带的上游技能不在此列**——它们忠实对齐上游的那一版，只做跨项目的通用化适配，不引入本集合的私有扩展。

### 5.3 升级时你的修改会怎样

采用者会改项目里的一些东西，所以让机制知道**谁写了哪个文件**：

| 谁写的 | 升级时 |
|---|---|
| 集合（模板渲染的契约与钩子块） | 带来新版：模板替换实例，钩子块按新文本重渲染 |
| 你（笔记本身、计划、术语表的行、标记块以外的指令、以及你手改过的规范块） | **永不触碰** |

集合更新遵循**保守覆盖**：只刷新自己写下的机制文本。规范那一处多一层保护：`applied.yaml` 记着每条规范块**上次由集合写入时的哈希**；你手改过某个块，哈希就对不上，规范更新会把差异报出来并停下，不覆盖它，直到你显式让它覆盖。其余受管文件同一原则——集合只重写自己写过的文本，遇到没见过的文件不创建也不覆盖。升级的安全来自机制而不来自承诺：**它只动自己写过的文本，会冲突就报出并停下。**
