# 架构：维护者视角

这一页写给**本仓库的维护者与贡献者**：仓库由什么组成、代码怎么分工、以及为什么是这个形状。采用者要的"装进我的项目后长什么样、机制怎么生效"，在 [架构：采用者视角](architecture-adopters.md) 里。

两页分开，是因为读者关心的事不同：采用者关心他拿到什么、能否改、升级会不会静默覆盖他的内容；维护者关心这些文本与检验各自存放在哪里、一项改动要动几处才不致互相矛盾。

## 仓库结构

```
dsh-spec/
│
├── skills/                    【集合的定义】随包发布给每个采用者
│   ├── dsh-spec-manager/       唯一带代码的包，也是集合的引擎
│   │   ├── SKILL.md            包自己的入口
│   │   ├── references/         manifest.json（门禁名字）· norms.json（规范目录）
│   │   │                       cli.md（由 --help 渲染）· 生命周期各页
│   │   ├── scripts/            ★ 引擎：入口 + verify-*.ts + 共享模块
│   │   └── templates/          契约的真值源（notes / plans / docs / AGENTS.md 的模板）
│   └── dsh-<…>/（其余九个）    各自 SKILL.md ＋ references/（个别带 templates/）
│
├── .agents/                   【本仓的采用态】本仓库自己也采用这套集合
│   ├── skills/                 安装副本：多集合共享的命名空间，按元数据认领
│   └── dsh-spec/
│       ├── notes/              笔记树：契约 ＋ proposed / implemented / rejected / archived
│       ├── plans/              计划树：契约 ＋ <slug>.md ＋ <slug>-progress.md
│       └── norms/              norms.md（生成物）＋ applied.yaml（哈希记录）
│
├── scripts/                   【本仓自己的判据】不随包发布
├── tests/                      那些判据自身的功能测试
├── .github/                    CI 与 PR／发布模板
├── docs/                       采用者文档与双语术语表；目录整体无人托管，
│                              术语表本身参与配对门禁
├── submodules/dsh/             钉住的提取基线
├── AGENTS.md                   常驻指令：本仓专有规则 ＋ 三个钩子块
└── README.md / README.zh.md     人这扇门
```

三条归属决定这个形状：

1. **判据分两处，因为不变量分两类。** 一类对**每个采用者项目**都成立——判据随集合发布，采用者各自在本地执行；一类只对本仓库的**自举与提取对账**成立——它读的是钉住的上游基线，采用者没有那份基线，所以判据留在 `scripts/`、不随包走。
2. **契约的定义与实例分处两地。** 定义在 `skills/dsh-spec-manager/templates/`，实例在采用者自己的 `.agents/dsh-spec/` 与根 `AGENTS.md` 里。改动契约若未同步模板，下一次刷新会以模板的真值覆写实例。
3. **安装副本不是作者树。** `skills/` 是作者树，`.agents/skills/` 是安装点，两者逐字节相等由门禁守着。该目录是**多个集合共享的命名空间**——一个项目可以同时装下本集合与别的兼容集合，各自靠注入的元数据认领自己那些技能目录。

## 代码架构

```
┌── 入口（统一收口，唯一） ────────────────────────────────────────────────────────────────────┐
│ dsh-spec.ts                                                                                  │
│ · 动手前对账「记录的门禁名字」⇄「旁边的程序」：不一致就报出缺的一方，什么都不跑              │
│ · 每个命令 = 一个用例：<入参> → <出参>                                                       │
│ · 用法：动词直接执行（install · upgrade · uninstall · status · check）                       │
│         名词带动词（notes check · translation-pair write · md-links check，余同）            │
│         flag 只做修饰；默认只读最小作用域；一个操作只有一种拼法                              │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
        │ 只编排，不直接碰文件系统
        ▼
┌────────────────────────────────────────────────────┬─────────────────────────────────────────┐
│ 领域（规则与状态；纯，可独立验证）                 │ 基础设施（副作用）                      │
│ · 托管登记表：模板→实例、三种 merge                │ · 读写文件、遍历目录                    │
│ · 「持有」的定义、内核与切面的边界                 │ · 执行命令（gh skill install 等）       │
│ · 笔记树的规则、状态与类别                         │ · git 读取（diff、sha、commits）        │
│ · 配对规则、链接解析、渲染与哈希                   │ · 终端交互（询问与答案）                │
│ · 移植来的判断逻辑：无状态                         │                                         │
└────────────────────────────────────────────────────┴─────────────────────────────────────────┘
        │ 一个模块：按职责类别组织，不做物理分层
        ▼
   本仓自己的判据（不发布，读钉住的基线）
   移植外壳：轻量封装无状态的判断逻辑，逻辑本身可独立验证
```

**一个入口。** 每个命令都走它。动手之前它先把**记录的门禁名字**与**旁边的程序**对账：有名字没程序、或有程序没被记录，都把缺的那一方报出来，什么都不跑。所以系统既不会悄悄持有一道并不存在的检验，也不会遗漏一道存在的检验；第四条不变量的机械化就落在这里。

**三种 merge 说的是「一条受管文本如何被刷新」**，不是三种算法：**整份替换**（这类文本完全由集合拥有）、**带记录的安全更新**（文本由集合写入，刷新时比对记录里的哈希；不一致说明它被人工改过，此时报出差异并停下，不做覆盖）、**按结构合并**（文本里有一部分属于项目，刷新只改写集合维护的区块）。哪一种适用于哪个文件由登记表决定；具体用 diff 还是 patch、如何切分，那是实现。

**一个命令是一个用例。** 它有入参和出参，与同级的其他命令不共享隐式状态；两层语法的意义正在于读者能从旁边命令的形状推知这一条的用法。**默认只读最小作用域**：缺参数即打印提示并退出，不做静默的全树遍历；一个操作只有一种拼法。

**规则与副作用分开。** 领域侧汇集纯规则：契约的登记表与三种 merge、内核与切面的判定边界、笔记树的状态与类别、配对与渲染规则，以及移植来的判断逻辑。移植逻辑因无状态而可被外壳轻量包裹，并能独立自测。基础设施侧封装文件系统、git、子进程与终端交互。用例只负责编排，既不内嵌纯规则，也不直接产生副作用。

**作者树与安装副本之间的流向是单向的。** 改动发生在作者树（`skills/`），安装副本由安装器重放生成——维护者从不直接编辑 `.agents/skills/`，因为它会被下一次重放覆盖。重放用哪条命令是实现，流向是契约。

**移植的是判断逻辑，不是整段代码。** 与上游源的差异只许有引用改动与泛化两种；`ports.json` 记着每个移植件与它的上游路径和修订，独立门禁对账两边。

**并行是调度器的能力，不是每个命令的能力。** 每一道检验都是一个**单一操作**的子进程——`check` 为每道检验启动一个普通子进程，命令自身不含任何并行逻辑。并行只存在于**入口的公共池**里：`check` 把选中的检验交给一个有界工作池，`manager` 对 `gh` 调用用同一个池。工作池的并发宽度是一处可调的值；具体暴露哪个开关、默认值怎么算，属于实现。

这不是"不需要并行"，而是把并行**从命令里挪到调度器**：每个命令保持单一操作、可单独运行与单独验证；需要并发时由入口统一提供，而不是让每个命令各写一套。
