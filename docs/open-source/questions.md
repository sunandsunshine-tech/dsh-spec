## F 事实筛查

事实题不改仓库,只决定后面出现哪些题。全部单选,除非另注。

### Q-F1 仓库归谁所有?

**类型** 单选 · **适用** 任意 · **作答** 实测 · **依据** [S02][S05][S38][S39]

> **为什么问(tips)** 归属决定谁能改可见性、能用哪些组织级功能,以及企业策略是否会直接挡住公开动作;选错归属后迁移要重建仓库与全部引用。[S02][S38]
>
> **社区主流(tips)** 个人作品与单人工具放个人账号;预期有外部贡献者、要用团队/组织级 rulesets 的项目放组织。[S39][S92]

- **个人账号**
  - **意味(tips)** 仓库属于一个 user,协作者按仓库单独邀请;没有组织级安全策略与团队。
  - **主流何时选(tips)** 单人维护、以个人身份署名、暂时不想建组织。
  - **代价(tips)** org 级 rulesets、团队、组织级默认 health file 都用不上。
  - [共识] · [S38] · → `PRE-01`

- **组织**
  - **意味(tips)** 仓库属于 org,可用团队、组织级 rulesets、成员权限与默认 health file;`admin` 角色可做安全与破坏性操作。
  - **主流何时选(tips)** 预期多人或长期维护,或希望归属与个人账号解耦。
  - **代价(tips)** 多一层成员与权限管理。
  - [共识] · [S38] · → `PRE-01`

- **企业托管用户(EMU)**
  - **意味(tips)** 账号由企业身份源管理,组织仓库只能 private/internal。
  - **主流何时选(tips)** 受合规约束的企业内部;开源项目实际不选,选了就无法公开。
  - [平台规则] · [S46] · → 无(该选项下本表单其余内容不适用)

### Q-F2 仓库当前处于什么状态?

**类型** 单选 · **适用** 任意 · **作答** 实测 · **依据** [S01][S04][S23]

> **为什么问(tips)** 从未公开、曾公开后转私有、已公开待审计,三种情况的代价完全不同;曾经公开过的仓库要额外处理已分离的 fork 与第三方归档,而这些不可撤回。[S04][S27]
>
> **社区主流(tips)** 绝大多数开源仓库是「从未公开」;从内部仓库转公开是第二大类,公开方法论(NHS Digital、OSPO Alliance)主要针对这一类。[S86][S87]

- **从未公开**
  - **意味(tips)** 没有 fork、没有第三方归档、没有公开缓存;历史清洗在公开前一次性完成。
  - **主流何时选(tips)** 新项目或一直私有的内部项目。
  - **代价(tips)** 无额外历史包袱。
  - [共识] · [S23] · → `PRE-10`、`PRE-20`

- **曾公开后转私有**
  - **意味(tips)** 可能已有被分离的 public fork 与第三方归档数据;重新公开不会恢复 stars/watchers,旧 fork 仍公开。
  - **主流何时选(tips)** 事实状态,不是选择。
  - **代价(tips)** 必须把 fork 与归档视为已泄露面。
  - [平台规则] · [S04] · [S27] · → `PRE-10`、`PRE-12`

- **已公开待审计**
  - **意味(tips)** 按持续合规处理,重点是可发现性、安全功能与响应流程。
  - **主流何时选(tips)** 事实状态。
  - **代价(tips)** 历史已公开,能改的只有未来。
  - [共识] · [S23] · → `DAY-02`–`DAY-12`

### Q-F3 现在有几个人能合并、能发布?

**类型** 单选 · **适用** 任意 · **作答** 实测 · **依据** [S63][S64][S38][S56]

> **为什么问(tips)** 本题的「维护者」指拥有 write 或 admin 权限、并承担合并、发布或安全响应的人;只提 PR 的贡献者不算。OSPS Baseline 的 Level 2 门槛(≥2 名维护者且有一批稳定用户)按这个定义判定,它决定签名发布、每 commit 权利声明、CI 测试套件与带时限 CVD 是义务还是建议。这是实测题:看协作者列表与 CODEOWNERS 就能回答;对未来投入的预期在 Q-G1 问。[S63][S38]
>
> **社区主流(tips)** 起步阶段几乎都是 1 人;本报告抽样里 92% 的项目在受资助期结束时才补齐核心安全功能。[共识] [S63][S56]

- **只有我一人**
  - **意味(tips)** 只需满足 Level 1 语义;响应能力是最大变量。
  - **主流何时选(tips)** 事实状态。
  - **代价(tips)** 安全报告与 issue 会挤占开发时间,需明确承诺边界。
  - [共识] · [S63] · → `PRE-14`、`P30-08`、`LONG-05`

- **2–5 人**
  - **意味(tips)** 进入 Level 2 的定义域,签名发布、DCO 语义、CI 测试、CVD 政策成为预期项。
  - **主流何时选(tips)** 事实状态。
  - **代价(tips)** 需要评审与权限分配规则。
  - [共识] · [S63] · → `PRE-06`、`DAY-06`、`P30-08`

- **6 人以上**
  - **意味(tips)** 需要 CODEOWNERS、治理文件与明确的合并权限。
  - **主流何时选(tips)** 事实状态。
  - **代价(tips)** 协作成本高于技术成本。
  - [共识] · [S63] · [S92] · → `PRE-06`、`P30-03`、`LONG-02`

- **有权限的人多于实际在做的人**
  - **意味(tips)** 协作者权限给了不止一个人,但合并、发布与安全响应实际仍压在一人身上。
  - **主流何时选(tips)** 事实状态,常见于把 collaborator 权限当信任信号而不是职责分配。
  - **代价(tips)** Level 2 的「≥2 名维护者」名义成立而实际不成立,出事时职责不清。
  - [少数] · [S63] · [S38] · → `DAY-06`、`LONG-02`、`LONG-05`

### Q-F4 公众通过什么拿到你的东西?

**类型** 多选 · **适用** 任意 · **作答** 实测 · **依据** [S29][S13][S59][S62]

> **为什么问(tips)** 分发形态决定后面哪些供应链题出现:有注册中心发布才谈版本号、发布凭据、attestation 与包可见性;只通过 git 与 tag 分发的仓库没有注册中心凭据,那些题跳过,而 AI 时代的 skill、插件与模板仓库多属于后者。包一旦公开就不能再转私有。[S29][S13]
>
> **社区主流(tips)** 文档、技能与配置类仓库多数不发布到注册中心;npm 生态正在从长期 token 转到 OIDC;窗口内的供应链事件集中在注册中心发布的包上,而 skill 仓库的风险点是「谁能在 main 上推送 tag」。[共识] [S59][S62][S51]

- **不发布,直接读源码**
  - **意味(tips)** 使用者按源码或 release 使用;供应链决策退化为 release 完整性。
  - **主流何时选(tips)** 纯粹的工具、文档或技能集合。
  - **代价(tips)** 没有注册中心的可见性与分发便利。
  - [共识] · [S29] · → `DAY-10`

- **通过 git 或 gh 安装的技能、插件、模板仓库**
  - **意味(tips)** 没有注册中心,分发单位是 tag 或 release;风险从发布凭据变成谁能推送 tag 与 main。
  - **主流何时选(tips)** agent skill、编辑器插件、模板仓库——AI 时代最常见的一类。
  - **代价(tips)** 没有注册中心的版本索引与 attestation,使用者只能按 ref 固定版本。
  - [材料稀薄] · [S41] · [S29] · → `DAY-08`、`DAY-10`

- **npm**
  - **意味(tips)** 进入 npm 的 2FA、provenance、install script 与 trusted publishing 规则域。
  - **主流何时选(tips)** JavaScript/TypeScript 库。
  - **代价(tips)** 发布凭据是高价值目标,需要 OIDC 与 staged publishing。
  - [共识] · [S59] · [S60] · → `PRE-21`、`P30-05`

- **PyPI**
  - **意味(tips)** 可迁移到 Trusted Publishing 与 PEP 740 证明;长期仓库 secret 是主要风险。
  - **主流何时选(tips)** Python 库。
  - **代价(tips)** 维护者个人账号被控即可绕过 CI 直发。
  - [共识] · [S51] · [S83] · → `PRE-21`、`P30-05`

- **Maven 或 Gradle 制品**
  - **意味(tips)** 进入 JVM 生态的发布签名与凭据规则,中央仓库对 groupId 所有权与签名有额外要求。
  - **主流何时选(tips)** Java/Kotlin 库。
  - **代价(tips)** groupId 与发布凭据是账号级高价值目标,恶意包告警同样覆盖 Maven。
  - [共识] · [S62] · [S31] · → `PRE-21`、`P30-05`

- **crates.io**
  - **意味(tips)** build script 与 proc-macro 是额外执行面。
  - **主流何时选(tips)** Rust 库。
  - **代价(tips)** 依赖链中的 build.rs 需要有意识地审查。
  - [共识] · [S84] · → `PRE-21`、`P30-05`

- **容器镜像或 GHCR**
  - **意味(tips)** 包可见性与仓库可见性相互独立,默认 private,公开后不可逆。
  - **主流何时选(tips)** 分发可执行环境。
  - **代价(tips)** 镜像层与基础镜像成为额外供应链面。
  - [平台规则] · [S29] · → `PRE-21`、`DAY-10`

- **模型、数据集或其他二进制产物**
  - **意味(tips)** 通过 release asset 或 LFS 分发,需要哈希与来源说明。
  - **主流何时选(tips)** AI 产物仓库。
  - **代价(tips)** OSPS Level 1 明确要求仓库不含生成的或不可审查的二进制,大文件同时推高克隆成本。
  - [共识] · [S63] · [S41] · → `DAY-10`

- **其他**
  - **意味(tips)** 按对应注册中心的规则另算。
  - **主流何时选(tips)** 语言特定生态。
  - **代价(tips)** 本表单不覆盖其特殊条目。
  - [材料稀薄] · → `PRE-21`

### Q-F5 仓库里有没有 GitHub Actions workflow?

**类型** 单选 · **适用** 任意 · **作答** 实测 · **依据** [S18][S63][S64]

> **为什么问(tips)** 没有 workflow 时 Actions 加固题不出现;一旦有 workflow,工作流卫生就是 OSPS Level 1 的义务,且 Scorecard 权重最高的 Dangerous Workflow 与次高的 Token Permissions 都在这个面上。[S63][S64]
>
> **社区主流(tips)** 样本里 11/14 有 workflow,没有的两个用自有 CI(Prow、Go builder);小仓库「完全没有 CI」在 Level 1 语义下仍可接受。[S63][S92]

- **没有**
  - **意味(tips)** 攻击面更小,但也就没有自动检查;可考虑显式禁用 Actions。
  - **主流何时选(tips)** 纯文档/技能仓库或已有外部 CI。
  - **代价(tips)** 门禁靠本地执行,贡献者可能不跑。
  - [共识] · [S63] · [S92] · → `DAY-06`

- **有**
  - **意味(tips)** 进入 fork PR 审批、token 权限、SHA pinning、触发事件与 cache 的完整决策域。
  - **主流何时选(tips)** 需要测试或发布的仓库。
  - **代价(tips)** CI 本身成为首要攻击面。
  - [共识] · [S58] · [S85] · → `DAY-06`、`DAY-07`

### Q-F6 是否包含第三方、vendored 或派生内容?

**类型** 多选 · **适用** 任意 · **作答** 实测 · **依据** [S70][S87][S61]

> **为什么问(tips)** 抽取、fork 与 vendored 内容触发许可与声明义务:MIT 只要求保留版权与许可全文,Apache-2.0 还要求 NOTICE 与标注修改过的文件;而 GitHub 现在按版本区间记录上游许可,relicensing 会留痕。[S70][S61][S87]
>
> **社区主流(tips)** 抽取式仓库通常用一份 THIRD_PARTY_NOTICES 加逐文件 SPDX 头;纯原创仓库不需要。[共识] [S66][S87]

- **无**
  - **意味(tips)** 只需 LICENSE。
  - **主流何时选(tips)** 完全原创。
  - **代价(tips)** 无。
  - [共识] · [S70] · → `PRE-02`

- **vendored 依赖**
  - **意味(tips)** 必须携带其许可与版权声明,并锁定版本。
  - **主流何时选(tips)** 为免运行时依赖而内联第三方代码。
  - **代价(tips)** 上游许可变化不会自动到达。
  - [共识] · [S61] · [S66] · → `PRE-05`

- **抽取或派生自其他项目**
  - **意味(tips)** 除许可外还要声明出处与偏离方式,并保留上游通知。
  - **主流何时选(tips)** 把内部或上游项目重做成独立仓库。
  - **代价(tips)** 上游每次变化都可能需要重新对账。
  - [共识] · [S87] · → `PRE-03`、`PRE-05`

- **git submodule**
  - **意味(tips)** 超项目只存指针,但被钉的仓库必须公开可达,否则使用者无法克隆。
  - **主流何时选(tips)** 需要固定基线的抽取项目。
  - **代价(tips)** 浅克隆与 tag 语义容易踩坑。
  - [共识] · [S87] · → `PRE-05`、`PRE-20`

### Q-F7 是否已经有 release 或 tag?

**类型** 单选 · **适用** 任意 · **作答** 实测 · **依据** [S41][S13][S63]

> **为什么问(tips)** 有 release 才谈 immutable releases、签名与变更日志;没有 release 的仓库这些题跳过,但 OSPS Level 1 仍要求公开的变更记录(谁、何时、改了什么)。[S13][S63]
>
> **社区主流(tips)** 多数公开仓库用 GitHub Releases 承载变更记录;immutable releases 是零成本开关,值得直接开。[共识] [S57]

- **没有**
  - **意味(tips)** 版本面是空的,公开后从第一个 release 开始定义规范。
  - **主流何时选(tips)** 新项目。
  - **代价(tips)** 使用者无法引用稳定版本。
  - [共识] · [S41] · → `P30-01`

- **有**
  - **意味(tips)** 已有 tag 与 release 会随公开对所有人可见,并成为使用者引用的稳定点。
  - **主流何时选(tips)** 事实状态。
  - **代价(tips)** 已发布的不可变 release 无法回收。
  - [平台规则] · [S13] · [S41] · → `DAY-10`、`P30-01`

### Q-F8 文档主体用什么语言?

**类型** 单选 · **适用** 任意 · **作答** 决定 · **依据** [S20][S77][S92]

> **为什么问(tips)** 语言决定贡献者范围与翻译维护成本;若两种语言都有正文,就需要一个结构一致性机制,否则两边会漂移。[S20][S77]
>
> **社区主流(tips)** 英文是开源默认;中文项目常以中文为主并附英文 README。双语配对是少数派,且没有形成共识——[材料稀薄]:本次调研没有找到关于双语仓库的高信号一手材料,只有「允许 AI 改善非母语者表达」这类相邻规则。[S77]

- **英文为主**
  - **意味(tips)** 面向最大贡献者群体,中文内容降为可选。
  - **主流何时选(tips)** 希望被国际采用。
  - **代价(tips)** 母语读者体验下降。
  - [共识] · [S92] · → `PRE-22`

- **中文为主**
  - **意味(tips)** 读者以中文社区为主,英文可后补。
  - **主流何时选(tips)** 主要受众在中文圈。
  - **代价(tips)** 英文贡献者需要额外门槛。
  - [材料稀薄] · [S92] · → `PRE-22`

- **双语配对**
  - **意味(tips)** 两侧同时维护,需要一个配对记录与结构检查,否则一侧改了另一侧不知道。
  - **主流何时选(tips)** 读者明确分成两个语言群体且有维护能力。
  - **代价(tips)** 每次改动都要动两份。
  - [材料稀薄] · [S77] · → `PRE-22`

### Q-F9 历史上有外部贡献者或 fork 吗?

**类型** 单选 · **适用** 任意 · **作答** 实测 · **依据** [S23][S04]

> **为什么问(tips)** 一旦有他人 clone 或 fork,敏感数据就无法从这些副本中移除;这决定「改写历史」是不是一个有效手段。[S23][S04]
>
> **社区主流(tips)** 新公开仓库通常从「仅本人」开始;有外部协作后,行业口径统一为先轮换凭据而不是重写历史。[共识] [S23]

- **仅本人提交**
  - **意味(tips)** 公开前改写历史代价最低,没有历史遗留的公开对象。
  - **主流何时选(tips)** 事实状态。
  - **代价(tips)** 无。
  - [共识] · [S23] · → `PRE-08`

- **有外部贡献者**
  - **意味(tips)** 改写历史会打断他人工作,且旧提交可能被重新推回。
  - **主流何时选(tips)** 事实状态。
  - **代价(tips)** 轮换凭据成为唯一可靠手段。
  - [共识] · [S23] · → `PRE-08`、`PRE-10`

- **已有 fork**
  - **意味(tips)** 网络内提交即使 fork 被删除也仍可访问。
  - **主流何时选(tips)** 事实状态。
  - **代价(tips)** 无法撤回,只能按已泄露处理。
  - [平台规则] · [S04] · [S23] · → `PRE-10`

### Q-F10 是否含有可能敏感的材料?

**类型** 单选 · **适用** 任意 · **作答** 实测 · **依据** [S07][S23][S24]

> **为什么问(tips)** 这是最短的筛查题,也是最重要的一道:公开后 secret scanning 会重扫全历史与所有分支,partner secret 会被自动通报服务商吊销,而 GitHub 无法从他人 clone 中移除数据,Support 也只处理轮换无法缓解的风险。[S07][S23]
>
> **社区主流(tips)** 成熟做法是「公开前先扫描、再决定」;NHS Digital 与 OSPO Alliance 都要求把凭证与 PII 检查列为公开前必过项。[共识] [S86][S87]

- **否**
  - **意味(tips)** 仍需一次机械扫描作证,不能只凭印象。
  - **主流何时选(tips)** 纯代码且无内部文本。
  - **代价(tips)** 扫描成本很低。
  - [共识] · [S73] · → `PRE-10`

- **不确定**
  - **意味(tips)** 必须先扫全历史与 PR/issue 文本,再决定是否公开。
  - **主流何时选(tips)** 内部文档、示例配置、测试数据混在仓库里。
  - **代价(tips)** 扫描可能发现历史命中,需要轮换凭据。
  - [共识] · [S07] · [S43] · → `PRE-10`

- **是**
  - **意味(tips)** 先移除或轮换,或改走快照方案(丢历史重建);部分内容只能移出仓库而不是删除。[S23][S24]
  - **主流何时选(tips)** 含客户数据、内部架构文档、长期凭据。
  - **代价(tips)** 公开时间推迟,且已泄露部分不可撤回。
  - [平台规则] · [S23] · [S24] · → `PRE-10`、`PRE-19`

## L 许可与来源

### Q-L1 采用哪个许可证?

**类型** 单选 · **适用** 任意 · **作答** 决定 · **依据** [S68][S63][S70]

> **为什么问(tips)** LICENSE 是公开仓库里唯一一件「每个副本都带走」的法律文件;缺失或选错会让使用者无法合法使用,而事后改许可需要所有版权人的同意,并且 GitHub 会按版本区间永久记录这次变更。[S63][S61]
>
> **社区主流(tips)** 小型库与工具以 MIT 为主,带专利敞口或公司主导的项目偏向 Apache-2.0;强 copyleft 多见于希望衍生作品继续开源的项目。[共识] [S70][S92]

- **MIT**
  - **意味(tips)** 最短的宽松许可,只要求保留版权声明与许可全文,不提供显式专利授权。
  - **主流何时选(tips)** 个人或小团队的库、工具、模板,希望最大化采用率。
  - **代价(tips)** 没有专利报复条款,贡献者与使用者之间的专利风险未在许可内处理。
  - [共识] · [S70] · → `PRE-02`

- **Apache-2.0**
  - **意味(tips)** 宽松许可加显式专利授权与专利报复条款,并要求保留 NOTICE、标注修改过的文件。
  - **主流何时选(tips)** 有专利组合、有法务敞口或预期吸引企业贡献。
  - **代价(tips)** 需要维护 NOTICE 与变更标注。
  - [共识] · [S70] · → `PRE-02`、`PRE-03`

- **GPL-3.0**
  - **意味(tips)** 强 copyleft,衍生作品分发时须以同许可开源,并含专利授权条款。
  - **主流何时选(tips)** 希望衍生作品保持开源。
  - **代价(tips)** 与闭源产品的集成被限制,部分企业不会采用。
  - [共识] · [S68] · → `PRE-02`

- **AGPL-3.0**
  - **意味(tips)** 在 GPL 基础上把「通过网络提供服务」也纳入分发义务。
  - **主流何时选(tips)** 服务端软件,担心被云厂商闭源包装。
  - **代价(tips)** 采用门槛最高的一类宽松度。
  - [争议] · [S68] · → `PRE-02`

- **MPL-2.0**
  - **意味(tips)** 文件级 copyleft,修改过的文件须开源,其余可闭源。
  - **主流何时选(tips)** 希望核心保持开放但允许周边闭源。
  - **代价(tips)** 需要按文件追踪修改与许可边界。
  - [少数] · [S68] · → `PRE-02`

- **双许可或自定义**
  - **意味(tips)** 同时提供两套条款或自拟条款。
  - **主流何时选(tips)** 商业公司用「开源 + 商业许可」模式。
  - **代价(tips)** 条款解释成本高,OSI 认可情况需逐条确认。
  - [少数] · [S68] · → `PRE-02`

- **暂不确定**
  - **意味(tips)** 没有 LICENSE 时默认保留全部权利,任何人都无权使用。
  - **主流何时选(tips)** 尚在内部评估。
  - **代价(tips)** 不满足 OSPS Level 1 的许可要求,community profile 也会缺一项,公开前必须补齐。
  - [平台规则] · [S63] · [S20] · → `PRE-02`

### Q-L2 是否为每个文件标注许可?

**类型** 单选 · **适用** F6 含 vendored 或派生内容,或 L1 选择和 Apache-2.0 · **作答** 决定 · **依据** [S66][S63][S70][S69]

> **为什么问(tips)** 仓库级 LICENSE 说明的是整体,而抽取与 vendored 场景里每个文件的来源与许可可能不同;逐文件标注让信息在文件被单独拷走后仍然保留。[S66]
>
> **社区主流(tips)** 多数仓库只放根 LICENSE;抽取/vendored 类项目更常见 SPDX 头,REUSE 合规是更严格的少数派,且 OSPS Level 1 并不强制它。[共识] [S63][S66]

- **不逐文件标注**
  - **意味(tips)** 许可只有仓库级一份,单文件被拷走后信息丢失。
  - **主流何时选(tips)** 完全原创、无第三方内容的仓库。
  - **代价(tips)** 派生文件的许可边界不清楚。
  - [共识] · [S70] · → 无

- **SPDX 标识符**
  - **意味(tips)** 在每个文件头部写 `SPDX-License-Identifier`,与根许可证配合。
  - **主流何时选(tips)** 含抽取或 vendored 内容,需要逐文件说明来源。
  - **代价(tips)** 新增文件要记得加。
  - [共识] · [S66] · → `PRE-04`

- **REUSE 合规**
  - **意味(tips)** 按 REUSE 3.3 为每个文件提供完整、机器可读的许可与版权信息。
  - **主流何时选(tips)** 需要向第三方证明逐文件合规的项目。
  - **代价(tips)** 要引入检查工具与 `LICENSES/` 目录。
  - [少数] · [S66] · → `PRE-04`

### Q-L3 第三方声明写到什么程度?

**类型** 单选 · **适用** F6 非「无」 · **作答** 决定 · **依据** [S70][S61][S66]

> **为什么问(tips)** MIT 只要求保留版权与许可全文,Apache-2.0 还要求 NOTICE 与修改标注;不写清会让下游无法判断他们继承了什么义务。[S70][S61]
>
> **社区主流(tips)** 内联第三方代码的项目通常会生成一份第三方通知,并在其中锁定版本与许可。[共识] [S66]

- **仅根 LICENSE**
  - **意味(tips)** 只声明本项目许可,不提第三方。
  - **主流何时选(tips)** 无 vendored 与派生内容的纯原创仓库。
  - **代价(tips)** 一旦加入第三方代码就必须回来补。
  - [共识] · [S70] · → `PRE-02`

- **NOTICE 文件**
  - **意味(tips)** 按 Apache-2.0 第 4 条保留归属声明与修改标注。
  - **主流何时选(tips)** 许可为 Apache-2.0,或上游是 Apache-2.0。
  - **代价(tips)** 需要随上游变动维护。
  - [共识] · [S70] · → `PRE-03`

- **第三方通知清单**
  - **意味(tips)** 列明每个 vendored 包的名称、版本与许可全文,并写出它们的来源。
  - **主流何时选(tips)** 内联第三方包或抽取自其他项目。
  - **代价(tips)** 依赖变化时要重新生成。
  - [共识] · [S66] · → `PRE-05`

- **清单加生成器**
  - **意味(tips)** 用脚本从依赖或 bundle 记录里重新生成清单,避免手工漂移。
  - **主流何时选(tips)** vendored 内容较多、更新频繁。
  - **代价(tips)** 多一个要维护的脚本。
  - [少数] · [S61] · → `PRE-05`

### Q-L4 外部贡献怎么确认权利?

**类型** 单选 · **适用** 任意 · **作答** 决定 · **依据** [S63][S88][S81]

> **为什么问(tips)** 没有权利声明时,项目对合并进来的代码是否可再许可没有把握;OSPS Level 2 把「每个 commit 由贡献者声明有权提交」写成明确要求。[S63]
>
> **社区主流(tips)** DCO 比 CLA 更轻、采用更广;CLA 主要出现在需要保留 relicensing 能力或公司主导的项目。[共识] [S88]

- **不设机制**
  - **意味(tips)** 依赖默认的贡献许可(如 inbound=outbound)。
  - **主流何时选(tips)** 单人项目、暂不接受外部贡献。
  - **代价(tips)** 权利链不明,未来改许可或商用会有顾虑。
  - [少数] · [S63] · → 无

- **DCO(`Signed-off-by`)**
  - **意味(tips)** 贡献者在每个 commit 上声明有权提交并同意项目许可。
  - **主流何时选(tips)** 希望低摩擦接受贡献,同时保留可追溯的权利声明。
  - **代价(tips)** 需要检查 trailer,Linux 明确要求 AI agent 不得代加 `Signed-off-by`。
  - [共识] · [S63] · [S81] · → `PRE-06`

- **CLA**
  - **意味(tips)** 贡献者签署协议,通常包含版权或专利授权,项目因此保留 relicensing 能力。
  - **主流何时选(tips)** 公司主导、预期双许可或商业化的项目。
  - **代价(tips)** 贡献摩擦最大,且这是单向门,未来回退到 DCO 会失去该能力。
  - [少数] · [S88] · → `PRE-06`

### Q-L5 是否为将来改许可留余地?

**类型** 单选 · **适用** L4 已作答 · **作答** 决定 · **依据** [S88][S61]

> **为什么问(tips)** 改许可需要所有版权人同意;把版权集中于一处(CLA 或单一雇主)是保留该能力的唯一常见手段,而 GitHub 会按版本区间记录许可变化,改过就抹不掉。[S88][S61]
>
> **社区主流(tips)** 多数项目不留余地,接受「许可一旦发布基本固定」;明确预期商业化或双许可的项目才用 CLA 保留。[共识] [S88]

- **不留余地**
  - **意味(tips)** 接受当前许可为长期许可。
  - **主流何时选(tips)** 社区项目、无商业化计划。
  - **代价(tips)** 将来改许可需要逐个联系版权人。
  - [共识] · [S88] · → 无

- **保留(配合 CLA)**
  - **意味(tips)** 通过 CLA 集中版权,使 relicensing 在法务上可行。
  - **主流何时选(tips)** 计划双许可、闭源版本或公司产品化。
  - **代价(tips)** 贡献者门槛提高,且回退是单向门。
  - [少数] · [S88] · → `PRE-06`

## P 身份、隐私与归属

### Q-P1 版权署名主体写谁?

**类型** 单选 · **适用** 任意 · **作答** 决定 · **依据** [S70][S87][S61]

> **为什么问(tips)** LICENSE 第一行会随每一份副本、每个 fork 与第三方归档永久存在,事后改名要动所有副本;它同时决定外界把项目视为个人作品还是公司项目。[S87][S27]
>
> **社区主流(tips)** 公司主导的项目署公司名,社区或个人项目署个人或中立实体;抽取自公司内部的项目通常保留公司署名。[共识] [S87][S92]

- **公司法定全名**
  - **意味(tips)** 权利与责任明确落在该法人,品牌与法律实体一致。
  - **主流何时选(tips)** 公司作为项目的所有者。
  - **代价(tips)** 公司全名永久公开,个人开发者与雇主的关系也随之可见。
  - [共识] · [S87] · → `PRE-02`

- **公司品牌名或英文名**
  - **意味(tips)** 对外用品牌,法律实体不写进 LICENSE。
  - **主流何时选(tips)** 希望公开署名与内部法务实体解耦。
  - **代价(tips)** 权利归属在文本上不如法定名清晰,重大维权时需另有依据。
  - [少数] · [S87] · → `PRE-02`

- **个人署名**
  - **意味(tips)** 版权归个人。
  - **主流何时选(tips)** 个人作品,或以个人身份长期维护。
  - **代价(tips)** 与雇主之间的职务作品问题需要自行厘清。
  - [共识] · [S92] · → `PRE-02`

- **基金会或中立实体**
  - **意味(tips)** 版权归中立组织,便于长期治理与多公司协作。
  - **主流何时选(tips)** 捐赠给基金会或成立独立实体的项目。
  - **代价(tips)** 需要治理与移交流程。
  - [少数] · [S87] · → `PRE-02`、`LONG-02`

### Q-P2 提交作者邮箱怎么处理?

**类型** 单选 · **适用** 任意 · **作答** 决定 · **依据** [S26][S23][S82][S91]

> **为什么问(tips)** 公开后每个提交的作者邮箱都可查,历史中所有提交一并暴露;而公开前改写历史是代价最低的时刻,一旦有 fork 或外部 clone 就基本失效。[S23][S26]
>
> **社区主流(tips)** 标准做法是使用 GitHub 提供的 noreply 地址并开启「阻止命令行推送暴露邮箱」;接受个人邮箱公开也很常见,但属于个人选择。[共识] [S26][S91]

- **保留现状**
  - **意味(tips)** 接受个人邮箱永久公开。
  - **主流何时选(tips)** 邮箱本身已是公开联系方式,或不介意。
  - **代价(tips)** 邮箱进入爬虫与社工目标列表,且无法事后收回。
  - [共识] · [S26] · → 无

- **改用 noreply 地址**
  - **意味(tips)** 后续提交用 `<id>+<user>@users.noreply.github.com`。
  - **主流何时选(tips)** 希望隐藏个人邮箱。
  - **代价(tips)** 只影响新提交,历史仍是旧邮箱,需要配合改写。
  - [共识] · [S26] · → `PRE-07`、`PRE-08`

- **改写全部历史**
  - **意味(tips)** 用 `git filter-repo` 改写作者与 committer 后强推,并重打 tag。
  - **主流何时选(tips)** 仓库尚无 fork 与外部 clone,且邮箱需要隐藏。
  - **代价(tips)** 所有提交 SHA 变化;已关闭 PR 的引用与签名失效;必须先备份分支。
  - [共识] · [S23] · [S26] · → `PRE-08`

### Q-P3 账号与组织怎么加固?

**类型** 单选 · **适用** 任意 · **作答** 决定 · **依据** [S63][S35][S83]

> **为什么问(tips)** 公开仓库把维护者账号变成高价值目标;npm 与 GitHub 的 2026 年供应链事件都以账号被控为入口,而 OSPS Level 1 把敏感资源的 MFA 写成最低要求。[S63][S83]
>
> **社区主流(tips)** 个人账号开 2FA 是底线;组织强制成员 2FA 是组织级公开仓库的常见配置。[共识] [S63][S35]

- **仅个人 2FA**
  - **意味(tips)** 维护者本人账号有第二因素,组织没有强制策略。
  - **主流何时选(tips)** 个人账号下的仓库。
  - **代价(tips)** 一旦协作者加入,没有组织级兜底。
  - [共识] · [S63] · → `PRE-09`

- **组织强制 2FA**
  - **意味(tips)** 所有成员必须启用 2FA 才能访问组织资源。
  - **主流何时选(tips)** 组织持有的公开仓库。
  - **代价(tips)** 失去 2FA 设备的成员会被挡在组织外,需要恢复流程。
  - [共识] · [S63] · → `PRE-09`

### Q-P4 谁能改仓库可见性?

**类型** 单选 · **适用** 任意 · **作答** 决定 · **依据** [S02][S45]

> **为什么问(tips)** 公开仓库最危险的单次操作是把可见性改回去或改错;组织与企业都可以把这项权限收窄到 owner,而拥有 admin 权限的人仍能改既有仓库的可见性。[S02][S45]
>
> **社区主流(tips)** 组织持有的公开仓库通常收窄为仅 owner;个人账号或单一 admin 的场景保持默认。[共识] [S02]

- **允许 admin 修改**
  - **意味(tips)** 任何有 admin 权限者都能改可见性。
  - **主流何时选(tips)** 个人账号或信任度极高的小团队。
  - **代价(tips)** 一次误操作即可把仓库转私有并中断外部使用。
  - [共识] · [S02] · → `PRE-01`

- **仅组织 owner 可改**
  - **意味(tips)** 可见性变更收窄到 owner,admin 仍可做其他安全操作。
  - **主流何时选(tips)** 组织持有的公开仓库。
  - **代价(tips)** 变更需要 owner 介入。
  - [共识] · [S02] · [S45] · → `PRE-01`

## H 公开范围与历史

### Q-H1 历史怎么发布?

**类型** 单选 · **适用** 任意 · **作答** 决定 · **依据** [S86][S87][S23]

> **为什么问(tips)** 完整历史包含每一次中间状态的代码、提交信息与作者信息;快照方案能一次性去掉这些,但会丢失归因与演进记录。选错方向的返工成本很高。[S86][S87]
>
> **社区主流(tips)** 开源项目默认发布完整历史;政府与受合规约束的场景更常用「取快照、丢历史」;公开方法论把「用未清洗的完整历史发布」列为两大常见错误之一。[共识] [S86][S87]

- **完整历史**
  - **意味(tips)** 保留全部提交、作者与演进过程,便于追溯与归因。
  - **主流何时选(tips)** 历史已扫描干净、希望保留公开的演进记录。
  - **代价(tips)** 任何历史中曾出现的内容都会公开,且不可撤回。
  - [共识] · [S23] · [S87] · → `PRE-10`、`PRE-20`

- **快照后丢历史**
  - **意味(tips)** 取当前树的快照,在新的仓库或新历史里发布,旧提交不出现。
  - **主流何时选(tips)** 历史含内部讨论、作者信息或无法逐条审查的内容。
  - **代价(tips)** 丢失归因与历史;已发布引用需重建。
  - [共识] · [S86] · → `PRE-19`

- **新建仓库迁移**
  - **意味(tips)** 另建一个仓库承载公开内容,原仓库保持私有。
  - **主流何时选(tips)** 公开内容只是内部仓库的一个划分子集。
  - **代价(tips)** 需要决定两边如何同步。
  - [共识] · [S87] · → `PRE-19`

### Q-H2 分支与 tag 怎么处理?

**类型** 多选 · **适用** 任意 · **作答** 决定 · **依据** [S72][S44][S92]

> **为什么问(tips)** 公开后所有分支与 tag 都可见,过时的长驻分支既有安全风险也会误导使用者;Packagist 的经验是「不再维护的分支应该删掉而不是留着」。[S72][S44]

  - **意味(tips)** 所有分支与 tag 公开,使用者可检出任意历史。
  - **主流何时选(tips)** 分支都有明确用途且已审查。

- **先清理未维护分支**
  - **意味(tips)** 删除过期分支,只留主分支、发布分支与 tag。
  - **主流何时选(tips)** 内部开发留下的实验分支。
  - **代价(tips)** 删除前需确认没有未合并的必要内容。
  - [共识] · [S72] · → `PRE-11`

- **只留主分支与发布 tag**
  - **意味(tips)** 最小公开面,发布点由 tag 固定。
  - **主流何时选(tips)** 希望公开面尽量小。
  - **代价(tips)** 并行开发要么在 fork 里,要么公开可见。
  - [共识] · [S92] · → `PRE-11`

- **为保留分支加规则集**
  - **意味(tips)** 对 release 或维护分支加 tag/分支规则,防止误改与误删。

### Q-H3 已关闭的 PR 与 issue 怎么处理?

**类型** 单选 · **适用** 仓库已有 issue 或 PR · **作答** 决定 · **依据** [S07][S43][S23][S25]

> **为什么问(tips)** 公开后所有历史 PR 与已关闭 issue 的标题、正文与评论都会公开,secret scanning 也会扫描这些文本;其中常混有内部链接、临时凭据与不便公开的讨论。内容涉及版权而不是敏感数据时,处理渠道不同——DMCA 只管版权。[S07][S43][S25]

> **社区主流(tips)** 多数项目原样公开并接受这些文本成为历史;受合规约束的项目会先迁移或删除敏感讨论。[共识] [S43][S86]

- **原样公开**
  - **意味(tips)** 完整保留协作历史,包括已关闭的讨论。
  - **主流何时选(tips)** 讨论内容可公开。
  - **代价(tips)** 任何残留的敏感文本都会公开且难以回收。

- **先清理敏感讨论**
  - **意味(tips)** 编辑或删除含凭据、内部链接与客户信息的评论。
  - **主流何时选(tips)** 历史上出现过临时凭据或内部信息。
  - **代价(tips)** 编辑会留下痕迹,删除会破坏讨论上下文。
  - [共识] · [S07] · [S43] · → `PRE-12`

- **迁移到私有仓库继续**
  - **意味(tips)** 把敏感讨论移到不公开的仓库,公开仓库只留结果。
  - **主流何时选(tips)** 内部协作与公开协作长期并存。
  - **代价(tips)** 需要维护两个追踪系统。
  - [少数] · [S87] · → `PRE-12`

### Q-S2 push protection 怎么开?

  - [共识] · [S08] · [S55] · → `DAY-02`

- **加购 Secret Protection 后开启**
  - **意味(tips)** 私有仓库也获得仓库级 push protection。
  - **主流何时选(tips)** 组织级统一策略。
  - **代价(tips)** 付费,且需要配套绕过流程。

### Q-S3 除了平台扫描,还用什么密钥检测?

**类型** 多选 · **适用** 任意 · **作答** 决定 · **依据** [S73][S23][S63]

> **为什么问(tips)** 平台扫描在推送后运行,本地与 CI 层的工具能在提交前拦住;而泄漏处置的第一原则是先轮换,检测的意义是把发现时间往前移。[S73][S23]
>
> **社区主流(tips)** 分层部署——push protection 加 pre-commit 的 gitleaks,CI 只扫新提交,历史扫描用 trufflehog 的活体验证;在历史发现上阻塞构建的团队通常很快会关掉扫描。[共识] [S73]

- **不加**
  - **意味(tips)** 只依赖平台扫描。
  - **主流何时选(tips)** 仓库没有凭据面、贡献者极少。
  - **代价(tips)** secret 会先进入远端再被发现。
  - [少数] · [S73] · → 无

- **gitleaks 作 pre-commit**
  - **意味(tips)** 提交前在本地拦截,可被 `--no-verify` 绕过。
  - **主流何时选(tips)** 多人协作、希望零远端污染。
  - **代价(tips)** 每个贡献者都要装钩子。
  - [共识] · [S73] · → `PRE-10`

- **gitleaks 进 CI(只看新提交)**
  - **意味(tips)** 按 diff 范围扫描,历史命中用 baseline 冻结。
  - **主流何时选(tips)** 已有 CI 且不希望历史命中阻塞合并。
  - **代价(tips)** 需要维护 baseline 文件。
  - [共识] · [S73] · → `PRE-10`、`DAY-07`

- **trufflehog 做历史与活体验证**
  - **意味(tips)** 对全历史扫描并验证凭据是否仍然有效,用于公开前的一次性复核。
  - **主流何时选(tips)** 公开前审计或事故响应。
  - **代价(tips)** 速度较慢,不适合每次推送都跑。
  - [共识] · [S73] · → `PRE-10`

## A Actions 与 CI

### Q-A1 启用 Actions 吗?

**类型** 单选 · **适用** 任意 · **作答** 决定 · **依据** [S18][S63][S64]

> **为什么问(tips)** 公开仓库的标准 runner 免费,但 Actions 也是近年供应链攻击的首要入口;不启用可以显著缩小攻击面,却也失去自动化检查。[S19][S64][S85]

> **社区主流(tips)** 多数代码仓库启用;纯文档/技能类仓库有的直接禁用。OSPS Level 1 不要求 CI,但只要有 workflow,其卫生就是义务;Scorecard 把 Dangerous Workflow 列为最高风险项。[共识] [S63][S64]

  - **意味(tips)** 仓库内不能运行 workflow,fork PR 无法触发任何执行。

- **启用但受限**
  - **意味(tips)** 只允许选定 action、默认只读 token、审批外部 fork PR。
  - **主流何时选(tips)** 需要 CI 但写入面很小。

  - [共识] · [S18] · → `DAY-06`、`DAY-07`

- **完全启用**
  - **意味(tips)** 任何 action 与触发都可运行,仅依赖审批设置防护。
  - **主流何时选(tips)** 成熟的内部 CI 配置。
  - **代价(tips)** 一旦 workflow 配置出错,影响面最大。
  - [少数] · [S58] · [S85] · → `DAY-06`、`DAY-07`

### Q-R3 用什么合并方式?

**类型** 单选 · **适用** 任意 · **作答** 决定 · **依据** [S48][S92]

> **为什么问(tips)** 合并方式决定公开历史的形状与可追溯性:merge commit 保留分支拓扑,squash 让每个 PR 成为一个提交,rebase 保持线性但重写 SHA。[S48]
>
> **社区主流(tips)** [材料稀薄] 本次调研没有对主流仓库的合并策略做系统测量;可观察到大量项目只开 squash 以保持线性历史,同时保留 PR 作为讨论记录。[S48]

- **Squash**
  - **意味(tips)** 每个 PR 折叠为一个提交,主分支历史线性且每个提交对应一个评审单元。
  - **主流何时选(tips)** 希望历史可读、按 PR 回溯。
  - **代价(tips)** 丢失 PR 内的提交粒度与作者细分。
  - [共识] · [S48] · → `DAY-09`

- **Merge commit**
  - **意味(tips)** 保留分支拓扑与全部原始提交。
  - **主流何时选(tips)** 需要保留贡献者提交与合并点。
  - **代价(tips)** 历史噪声较多。
  - [共识] · [S48] · → `DAY-09`

- **Rebase**
  - **意味(tips)** 把 PR 提交线性重放到主分支,不改单个提交但改其父提交。
  - **主流何时选(tips)** 要求线性历史又希望保留提交粒度。
  - **代价(tips)** 冲突处理成本高,提交 SHA 变化。
  - [少数] · [S48] · → `DAY-09`

- **混合**
  - **意味(tips)** 允许贡献者按 PR 选择。
  - **主流何时选(tips)** 贡献者习惯差异大。
  - **代价(tips)** 历史形状不统一。
  - [少数] · [S48] · → `DAY-09`

### Q-R4 要求签名提交吗?

**类型** 单选 · **适用** 任意 · **作答** 决定 · **依据** [S16][S63][S65]

> **为什么问(tips)** 签名提交让「谁写的」在密码学上可验证,但它不判断内容好坏,SLSA 的经验也说明有效签名不等于可信;是否要求取决于威胁模型。[S65][S63]

> **社区主流(tips)** 多数项目不要求签署提交,只要求签署发布或使用 release attestation;要求签名提交的多为安全敏感或受合规约束的项目。[共识] [S63][S16]

- **不要求**
  - **意味(tips)** 提交身份按 GitHub 账号归属判断。
  - **主流何时选(tips)** 多数开源仓库。
  - **代价(tips)** 伪造作者身份在技术上仍可行(示例:伪造 noreply 身份混入历史)。
  - [共识] · [S82] · → 无

- **要求**
  - **意味(tips)** 所有进入主分支的提交必须签名。
  - **主流何时选(tips)** 安全敏感、需要强归属保证的项目。
  - **代价(tips)** 贡献者配置门槛明显上升,部分工具链不友好。

### Q-R5 发布完整性做到哪一档?

**类型** 多选 · **适用** 任意 · **作答** 决定 · **依据** [S13][S57][S14][S63]

> **为什么问(tips)** immutable releases 让已发布的 tag 与 asset 不可改,是最低成本的发布完整性开关;更高一档是签名与构建来源证明,但 SLSA 的经验表明它只能提供证据,不判断好坏。[S13][S65]

- **不做**
  - **意味(tips)** release 与 tag 仍可被移动或替换。
  - **主流何时选(tips)** 无发布流程的实验仓库。
  - **代价(tips)** 下游无法把版本钉死在不可变对象上。

- **Immutable releases**
  - **意味(tips)** 启用后新 release 的 tag 与 asset 不可改,自动生成 release attestation。
  - **主流何时选(tips)** 有正式发布的仓库。
  - **代价(tips)** 发布后无法修正 asset,只能发新版本。

- **签名 tag 或提交**
  - **意味(tips)** 用 GPG/SSH 签名证明发布点。
  - **主流何时选(tips)** 需要离线可验证的发布链。
  - **代价(tips)** 密钥管理成本与轮换流程。
  - [少数] · [S63] · → `DAY-10`

- **构建来源证明(attestation)**
  - **意味(tips)** 为构建产物生成可验证的来源记录。
  - **主流何时选(tips)** 发布二进制或包,且下游会校验来源。
  - **代价(tips)** 只证明「由谁构建」,不证明内容安全。
  - [共识] · [S14] · [S65] · → `DAY-10`
