<h3 id="cn-v0.2.0">首个发布:一个可安装的技能集合</h3>

把 DeepSeek Harness 团队干活的那套范式抽出来,做成一个项目能安装、能运行、能更新的东西:九个技能加一个门禁引擎,零运行时依赖——仓库里连 `package.json` 都没有。它给项目的是一个地方,放下一次改动必须携带的三样东西:为什么这样改、放弃了什么、什么证明它成立。

**装什么**

| 技能 | 负责 |
|---|---|
| `dsh-spec-manager` | 拥有整套集合:初始化项目、在单一修订上安装与刷新、挑选并应用规范、按改动分派门禁 |
| `dsh-archive-agent-notes` | 决策记录的保留判断、冻结归档与封存 |
| `dsh-translate-docs` | 双语配对、翻译简报与用词表 |
| `dsh-prose-standard` | 各类散文该写什么:README、API 文档、注释、提示、诊断、CLI 与界面文案 |
| `dsh-trim-cot-leakage` | 清掉读起来像推理记录泄漏的散文 |
| `dsh-code-review` | 按仓库自己的标准审一个 pull request |
| `dsh-pre-push-checks` | 推送前选出覆盖这次改动的最小检查集 |
| `dsh-find-simplifications` | 找有证据支撑的可简化之处,并写成可评审的决定 |
| `dsh-agent-experience` | 设计 agent 工具、技能、上下文加载与多步工作流,让信息可发现、上下文用得省 |

**怎么装**

```sh
gh skill install sunandsunshine-tech/dsh-spec dsh-spec-manager@v0.2.0 --dir .agents/skills
node .agents/skills/dsh-spec-manager/scripts/dsh-spec.ts install --root .
```

第一条把 manager 装在你点名的那条修订上;第二条按**同一个 ref** 装其余八个技能,并创建项目需要的文件:常设指令、决策记录树、术语表。装在哪条 ref 上,整套技能就钉在哪条 ref——`gh` 把这条 ref 注入 manager 自己的 `SKILL.md`,`status` 拿每个技能与它比对,`upgrade` 也按它刷新。项目级安装在 `.agents/skills/` 并提交进 git,于是每位协作者、每个 agent、每次 CI 跑的都是同一个修订。

前置只有三样:Node ≥ 22.19、git,以及带 `skill` 命令的 `gh`。

**这一版里有什么**

- **规范目录**:这套集合积累的通用规范合成一册可挑选的目录,20 条分 5 组(pull request 5、散文 5、测试 4、归属 3、证据 3)。每条有稳定的 id、写进项目的英文正文,以及供挑选界面用的中文标题;项目用 `norms list` 挑、用 `norms install` 应用,应用进项目的文本可以自己改,`norms update` 分得清「没人动过」「项目改过」「两边都改过」。
- **门禁与一个入口点**:六道门禁(笔记的分类与格式、冻结归档、双语配对、链接与链接语法)都是代码,住在集合唯一的代码落点里,由 `dsh-spec.ts` 按 manifest 记录的名字分派;记录与脚本对不上时它拒绝运行任何东西。`check --all` 是整树形式,`check --base <ref>` 只跑这次改动欠的检查,并打印每一个跳过及其原因;空语料一律判失败。
- **决策记录树**:一份契约加一棵树——项目自己的类与生命周期、每个决定的英中两侧加一条配对记录、以及冻结归档;写什么、什么时候写、什么时候删,都由契约与工作流定。
- **双语契约**:每一篇纳入范围的文档都是一个完整的配对;配对门禁比的是结构签名(标题深度、代码块、列表、表格、链接目标),不比措辞——两种语言说不说同一件事,是评审人的那一半。
- **合并与发布**:合并与发布是需要授权的行为,申请要指明**那一次**行为并带上改动说明;发布说明有模板,发布 PR 与其它 PR 走同一种合并,而发布提交自带它发布的那份副本。

**边界与代价**

- 零运行时依赖,但需要 Node、git 与 `gh`;`gh` 只在安装与读取修订索引时用得上。
- 门禁全部在本地跑。它证明的是**跑过什么**,不是这次改动该不该落地——那一半是评审人的。
- 门禁只读树里的文件:PR 正文、issue 与对话都不在任何门禁的语料里。
- 配对门禁只判结构,不判两种语言说的是不是同一件事。
- 归档是冻结的:归档里的三件套按路径离开所有门禁的视野,永不修改。

**出处与许可**

- 抽取自 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness),基线钉在 `dsh-v0.1.7-alpha.2`(`00102833`);16 个移植文件各自在头部写明上游路径、修订与偏离方式,`scripts/ports.json` 是登记表,`verify-port-provenance` 让登记表、文件头与钉住的基线三方向对账。
- MIT。上游与内嵌包的通知随副本同行:`LICENSE` 与 `THIRD_PARTY_NOTICES.md`,而技能集合内另有一份自足的通知副本。

<h3 id="en-v0.2.0">First release: a skill set you install</h3>

The development pattern the DeepSeek Harness team works by, extracted into something a project can install, run and update: nine skills and one check engine, with no runtime dependency at all — the repository does not even carry a `package.json`. What it gives a project is a place to keep the three things a change has to carry: why it went that way, what it gave up, and what proves it holds.

**What you install**

| Skill | Owns |
|---|---|
| `dsh-spec-manager` | The set itself: initializing a project, installing and refreshing it at one revision, choosing and applying norms, and dispatching the checks a change owes |
| `dsh-archive-agent-notes` | Retention decisions for decision records, the frozen archive and its sealing |
| `dsh-translate-docs` | Bilingual pairing, translation briefings and the vocabulary table |
| `dsh-prose-standard` | What each kind of prose owes: READMEs, API documentation, comments, prompts, diagnostics, CLI and UI strings |
| `dsh-trim-cot-leakage` | Prose that reads like a leaked reasoning transcript |
| `dsh-code-review` | Reviewing a pull request against the repository's own standards |
| `dsh-pre-push-checks` | Choosing the smallest set of checks that covers the outgoing change |
| `dsh-find-simplifications` | Evidence-backed simplifications, written as reviewable decisions |
| `dsh-agent-experience` | Designing agent tools, skills, context loading and multi-step workflows so information is discoverable and context is spent well |

**How you install it**

```sh
gh skill install sunandsunshine-tech/dsh-spec dsh-spec-manager@v0.2.0 --dir .agents/skills
node .agents/skills/dsh-spec-manager/scripts/dsh-spec.ts install --root .
```

The first command installs the manager at the revision you name; the second installs the other eight skills **at that same ref** and creates the files a project needs: its standing orders, its decision-record tree and its vocabulary table. The ref the manager was installed at is the pin for the whole set — `gh` injects it into the manager's own `SKILL.md`, `status` compares every skill against it, and `upgrade` refreshes from it. A project-scoped copy lives in `.agents/skills/` and is committed to git, so every collaborator, every agent and every CI run works from one revision.

Three prerequisites, and no more: Node ≥ 22.19, git, and `gh` with its `skill` command.

**What is in this version**

- **The norm catalog**: the general norms the set accumulated, as one catalog a project chooses from — 20 norms in 5 groups (pull request 5, prose 5, tests 4, ownership 3, evidence 3). Each has a stable id, English text that lands in the project, and a Chinese title for the surface that offers it. A project lists them with `norms list` and applies them with `norms install`; what lands in the project may then be edited, and `norms update` tells an untouched block from a personalized one and from a block where both sides moved.
- **The checks and their one entry point**: six checks (note classification and format, the frozen archive, bilingual pairing, links and link syntax) are code in the collection's single code home, dispatched by `dsh-spec.ts` against the names its manifest records; when that record and the scripts disagree it refuses to run anything. `check --all` is the whole-tree form, `check --base <ref>` runs only the checks a change owes and prints every skip with its reason, and an empty corpus is a failure rather than a pass.
- **The decision-record tree**: a contract and a tree — the project's own classes and lifecycle, both language sides of each decision plus a pairing record, and a frozen archive. What to write, when to write it and when to delete it are the contract's and the workflow's calls.
- **The bilingual contract**: every document in scope is a complete pair; the pairing check compares structural signatures — heading depth, code blocks, lists, tables, link targets — and not wording, because whether the two sides say the same thing is the reviewer's half.
- **Merging and publishing**: both are acts that need authorization, and the request names that act and carries the change's description. Release notes have a template, a release pull request takes the same merge as any other, and the release commit carries the copy of what it publishes.

**Boundaries and costs**

- No runtime dependency, but Node, git and `gh` are required; `gh` is needed only to install and to read the revision index.
- Every check runs locally. It proves what was run, not that the change should land — that half is the reviewer's.
- The checks read files in the tree: a pull-request description, an issue and a conversation are in no check's corpus.
- The pairing check judges structure only, not whether the two sides say the same thing.
- The archive is frozen: the triplets inside it leave every check's corpus by path and are never edited.

**Where it comes from, and its licence**

- Extracted from [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) and pinned to the `dsh-v0.1.7-alpha.2` baseline (`00102833`); the 16 ported files each name their upstream path, revision and kind of deviation in their header, `scripts/ports.json` is the registry, and `verify-port-provenance` reconciles the registry, those headers and the pinned baseline.
- MIT. The notices of the upstream and the bundled packages travel with the copy: `LICENSE` and `THIRD_PARTY_NOTICES.md`, with a self-contained copy of the notices inside the skill set.
